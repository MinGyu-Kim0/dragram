# LLM 결과는 SSE가 아니라 ASGI 위 NDJSON 스트림으로 보낸다

분석 LLM 작업을 RQ 작업자로 옮기면서(#98), 결과 전달은 문서가 처음 정한 SSE 대신 **지금의 NDJSON 스트림 약속(`previous`·`grammar`·`translation`·`analysis`·`error`)을 그대로 두고 서버를 uvicorn(ASGI)으로 바꾸는 방식**을 택했다(2026-10-24 사용자 결정). 분석 요청 하나가 연결 하나다. DB만으로 정해지는 `previous`(stale 옛 결과)와 `grammar`(확정 문법)는 요청 쪽이 바로 보낸다. 작업자는 Redis pub/sub으로 소식을 보내고, 요청 쪽이 그것을 `translation`·`analysis`로 바꿔 흘려보낸다. `error`는 요청 쪽(대기 상한 초과 등)과 작업자 실패 소식 양쪽에서 나온다. 비동기 서버에서는 기다리는 연결이 서버 작업자를 붙잡지 않으므로, 큐로 옮기는 이유(LLM 대기가 서버를 막는 것)가 해결된다. 패널 코드는 거의 바뀌지 않는다. 화면 위치와 숫자 복원에 필요한 원문은 요청 쪽에만 있고, 작업자 소식에는 넣지 않는다.

## Considered Options

- **SSE(`EventSource`)**: POST로 작업을 만든 뒤 받은 작업 ID만 SSE 주소에 넣으면 원문은 주소에 남지 않는다. 하지만 요청이 두 번 필요하다. 또 `EventSource`는 `Authorization` 헤더를 보낼 수 없어서, 확장의 Bearer 토큰(#109)을 주소나 쿠키로 옮겨야 한다. 끊긴 뒤 다시 붙을 때의 인증과 작업 ID 처리도 따로 만들어야 한다. 동기 Gunicorn에서는 열린 연결마다 서버 작업자가 묶이므로 어차피 ASGI가 필요했다.
- **폴링(같은 요청을 짧은 주기로 다시 보내기)**: 서버를 동기로 둘 수 있다. 하지만 문장 수 상한이 없어 요청 수가 크게 늘어나고, 묶어 묻기·점점 느리게 묻기 같은 장치를 더 만들어야 하며, 번역이 최대 한 주기 늦게 보인다. 나중에 바꿀 걸 알면서 만드는 셈이라 택하지 않았다.

## Consequences

- 운영과 로컬 모두 uvicorn만 쓴다(Gunicorn 없음). 예전 Gunicorn 120초 시간 제한의 역할은 RQ 작업 시간 제한(120초)이 맡는다.
- 요청 연결은 130초까지 기다린다. 이 시간은 큐에 넣은 때부터 세므로 큐 대기도 포함된다. 큐가 밀리면 작업이 제 시간 안에 끝나도 요청이 먼저 `error`로 닫힐 수 있고, 그때는 다시 요청해 저장된 결과를 받는다. 큐 대기 상한은 #99에서 정한다.
- 소식을 놓치지 않으려면 **먼저 구독하고**, 그다음에 선점·큐 넣기(처음 요청한 쪽)나 DB 상태 읽기(처리 중에 들어온 쪽)를 한다. 큐에 넣은 뒤 구독하면 빈 큐에서 작업자가 먼저 보낸 번역 소식을 잃는다.
- 운영 nginx를 만들 때 이 경로의 응답 버퍼링을 끄고, 읽기 제한 시간(`proxy_read_timeout`, 기본 60초)을 130초보다 길게 둔다.
