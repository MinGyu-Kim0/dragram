# LLM 결과는 SSE가 아니라 ASGI 위 NDJSON 스트림으로 보낸다

분석 LLM 작업을 RQ 작업자로 옮기면서(#98), 결과 전달은 문서가 처음 정한 SSE 대신 **지금의 NDJSON 스트림 약속을 그대로 두고 서버를 uvicorn(ASGI)으로 바꾸는 방식**을 택했다(2026-10-24 사용자 결정). 분석 API가 작업을 큐에 넣은 뒤 연결을 열어 두고, 작업자가 Redis pub/sub으로 보내는 소식을 `translation`·`analysis` 이벤트로 흘려보낸다. 비동기 서버에서는 기다리는 연결이 서버 작업자를 붙잡지 않으므로, 큐로 옮기는 이유(LLM 대기가 서버를 막는 것)가 해결된다. 패널 코드는 거의 바뀌지 않는다. 문장을 POST 본문으로 보내므로 원문이 주소나 서버 로그에 남지 않는다. 화면 위치와 숫자 복원에 필요한 원문은 요청 쪽에만 있고, 작업자 소식에는 넣지 않는다.

## Considered Options

- **정식 SSE(`EventSource`)**: GET만 쓸 수 있어 문장을 주소에 넣어야 하고, 그러면 원문이 로그에 남을 수 있다. 동기 Gunicorn에서는 열린 연결마다 서버 작업자가 묶여 큐로 옮긴 의미가 없어서, 어차피 ASGI가 필요했다.
- **폴링(같은 요청을 짧은 주기로 다시 보내기)**: 서버를 동기로 둘 수 있지만, 문장 수 상한이 없어 요청 수가 크게 늘어난다. 묶어 묻기·점점 느리게 묻기 같은 장치를 더 만들어야 하고, 번역이 최대 한 주기 늦게 보인다. 나중에 바꿀 걸 알면서 만드는 셈이라 택하지 않았다.

## Consequences

- 운영과 로컬 모두 uvicorn만 쓴다(Gunicorn 없음). 예전 Gunicorn 120초 시간 제한의 역할은 RQ 작업 시간 제한(120초)이 맡고, 요청 연결은 130초까지 기다린다.
- 소식을 놓치지 않으려면 "먼저 구독하고, 그다음 DB 상태를 읽는" 순서를 지켜야 한다.
- 운영 nginx를 만들 때 이 경로의 응답 버퍼링을 꺼야 한다.
