# 설계 결정

지금 유효한 설계 결정과 그 이유를 주제별로 모은다. 무엇을 하는지(동작 계약)는 `requirements.md`, 테이블·칼럼은 `schema/schema.md`가 기준이고, 이 문서는 "왜 그렇게 정했나"를 짧게 적고 그쪽을 가리킨다.

- 결정이 바뀌면 이 문서의 해당 항목을 직접 고친다. 큰 결정이나 바뀌기 전 맥락은 `adr/`에 남긴다.
- "이력 N절"은 동결한 이력 [`design-decisions.md`](design-decisions.md)의 절 번호다. 바뀌기 전 맥락이 필요할 때만 본다.
- "보류:"는 아직 정하지 않은 것이다. 결정으로 읽지 않는다.
- 용어는 `GLOSSARY.md`를 따른다.

## 프로젝트 범위·진행 방식

### 목적과 언어 범위
사용자가 고른 글(기술 문서·뉴스·게임·소설 등)에서 필요한 일본어를 배우게 한다. 범위는 표준어와 회화체이고, 시드 문법 없이 시작해 처음 보는 문법은 분석 중 LLM이 찾아 미검수 패턴·용법으로 등록한다. 문법·한자 모두 JLPT 급수를 두지 않는다.
- 이유: 시드는 사용자 결정이 아니었고 JLPT는 공식 목록이 없다.
- 근거: 이력 0·13절 · requirements 1장 · ADR 0001
- 보류: 방언·인터넷 말투·신조어, れる 세분, colloquial 밖 말투 값, JLPT 라벨.

### 범위 밖
확장 문장(축약어 원형 복원), 다국어·역방향, PDF 전용 분석, 불연속 문법.
- 근거: 이력 8·17절 · requirements 1·8장

### 도구와 단계
형태소 분석은 SudachiPy core·분할 모드 C, 관리 화면은 Django admin. 분석 → 회원 → 결제 순이고 Phase 1 안의 순서·미룰 것은 requirements 8장을 따른다.
- 근거: 이력 0·11절 · requirements 8·9장
- 보류: core → full 전환.

### 칼럼은 쓰는 티켓에서
새 테이블은 지금 쓰는 칼럼만 만들고 나머지는 쓰는 티켓의 마이그레이션으로 더한다.
- 근거: 이력 32절 7

- 보류: 애매한 히라가나 단어, 〜の 표시, 일본어 없는 입력, SudachiPy 입력 한도 초과 문장, Phase 완료 기준, 비기능 목표치(이력 10절 · requirements 8장).

## 정규화·문장 해시

### 정규화는 서버만 한다
확장은 루비·보이지 않는 글자를 뺀 원문만 보내고, 분석 텍스트·키 텍스트·해시는 서버가 만든다.
- 이유: 확장 버전마다 해시가 갈리면 안 되고, 공용 캐시 키를 클라이언트가 정하면 안 된다.
- 근거: 이력 28·31절 · FR-A03

### 분석 텍스트와 키 텍스트
분석 텍스트(숫자 그대로)는 형태소 분석에만, 키 텍스트(아라비아 숫자 → ⟨N1⟩)는 해시·LLM 입력·번역 저장·구간 위치에 쓴다. 한자 숫자는 바꾸지 않는다.
- 이유: 숫자만 다른 문장이 캐시를 함께 쓰되, 二枚目 같은 관용 표현은 지킨다.
- 근거: 이력 1절 · requirements '정규화 규칙' · `sentence_analysis.sentence_hash`

### 숫자의 뜻을 지키는 기호는 남긴다
NFKC 대신 NFC와 폭 통일만 한다. 숫자 사이 기호, 숫자 앞 부호, 단위·통화 기호, 숫자 범위의 물결표는 지우지 않는다. 부호와 통화 기호가 겹친 금액은 알려진 한계다.
- 이유: 1.5倍가 15倍, 50%가 50과 같은 키가 되면 숫자가 틀린다.
- 근거: 이력 1·30절 · requirements '정규화 규칙'

### 자리표시자가 모두 남은 결과만 공용 캐시에
번역(대안 번역 포함)에 자리표시자가 빠짐없이 있을 때만 저장한다. 숫자 표기는 원문 모양대로 두게 하고, 되돌릴 때 숫자 뒤 조사를 숫자 읽기에 맞춘다.
- 이유: 숫자만 다른 문장이 같은 번역을 쓰므로 어느 숫자에도 틀리지 않아야 한다.
- 근거: 이력 1·30·40절 · requirements '정규화 규칙'

### 공용 지식에는 원문 숫자를 넣지 않는다
패턴의 숫자 토큰은 '아무거나'만, 용법 글에는 자리표시자 금지, 판별 규칙 lemma에는 숫자 금지, 숫자열과 겹치는 토큰은 단어로 고르지 않는다.
- 이유: 원문 숫자가 공용 행에 굳으면 숫자만 다른 문장에서 틀린다.
- 근거: 이력 31·32·45·54절

### 구간 위치는 키 텍스트 코드포인트
LLM은 서버가 매긴 ID만 답하고, 위치는 서버가 키 텍스트 코드포인트 [start, end)로 계산해 저장한다(숫자열 가운데서 나뉘면 숫자열 전체를 덮는다). 응답할 때 서버가 요청 원문의 UTF-16 위치로 바꾼다.
- 이유: 공용 행에 원문이 없고, LLM이 위치를 짓지 못하게 한다.
- 근거: 이력 2·31절 · `span_match` · `sentence_analysis.word_spans`

### 보류: 정규화 규칙을 바꿀 때
`normalize_version`은 기록용이고 규칙이 바뀌면 해시를 다시 계산하기로 했지만, 공용 행에는 원문이 없고 개인 원문으로 다시 잇던 경로도 ADR 0006으로 사라졌다.
- 근거: 이력 1·26절 · `sentence_analysis.normalize_version` · ADR 0006

## 저장·캐시·최신성

### 공용 분석은 해시 하나로만 유일
`sentence_analysis`는 UNIQUE(sentence_hash)이고 원문 칸이 없다. 번역과 구간·단어·이름의 위치·ID만 두고, 설명·검수 상태는 조회할 때 읽는다.
- 이유: 원문을 두지 않고, 승인·반려·설명 수정이 모든 문장에 바로 반영되게 한다.
- 근거: 이력 2·12·28·50절 · `sentence_analysis` · ADR 0003

### 분석 상태와 실패
`status`는 processing / complete / failed이고 `partial`은 없다. 미확정이 남아도 complete다. 실패한 시도는 아무것도 저장하지 않는다. 처리 중 번역은 `processing_translation_ko`에 따로 두어 옛 번역을 덮지 않는다.
- 이유: 일시 오류가 공용 캐시에 굳으면 안 된다.
- 근거: 이력 31·40·51절 · FR-A07 · `sentence_analysis.status`

### NULL 칸의 뜻
`word_spans`가 NULL인 옛 행은 다시 분석한다. `name_spans`의 NULL은 '판단하지 않음'이고, 이것만 얻으려고 다시 분석하지 않는다.
- 이유: 이름 구간은 유료 호출을 늘릴 만큼 중요하지 않다.
- 근거: 이력 50·58절 · `sentence_analysis.word_spans`·`name_spans`

### 최신성은 stale 표시로만
판정에 영향을 주는 사건(반려·반려 취소·승인 취소, 용법 완결 변경, 회화체 연결·해제·병합, 판별 규칙 승인·폐기, 매칭 정정)은 같은 트랜잭션에서 영향 범위 분석의 `is_stale`을 켜고 세대 번호를 올린다. 용법 설명·예문, `show_parts`, 추론 강도 변경은 stale을 만들지 않는다.
- 이유: 판 번호를 올릴 사건이 아직 없고, 조회 때 읽는 값은 바로 반영된다.
- 근거: 이력 3·35·44·45·64·70절 · FR-A13 · `sentence_analysis.is_stale`

### stale 분석은 통째로 다시 만든다
stale 분석은 다음 요청에서 처음부터 다시 분석한다. 그동안 옛 결과를 지금 조회 규칙으로 만든 `previous`로 보이고 '재분석 중'을 단다. 실패하면 옛 결과와 stale을 남긴다. 일괄 재처리는 없다.
- 이유: 실제로 다시 보는 문장에만 비용이 든다.
- 근거: 이력 35·38절 · FR-A07

### 패턴 세트 버전
`pattern_set_version` 한 행을 `is_active` 변경, 활성 패턴의 조건 변경, 매칭 자격이 거짓→참일 때 같은 트랜잭션에서 잠가 올린다.
- 이유: 비활성 동안 분석된 문장은 stale로 찾을 수 없고, 메모리 값은 다중 서버에서 하나로 유지되지 않는다.
- 근거: 이력 29·41·42절 · `pattern_set_version`

### 재매칭: 조회할 때 새 구간만
`matcher_version`(매칭 직전 버전, 낮추지 않음)이 지금보다 낮으면 그 요청 원문으로 다시 매칭해 저장되지 않은 구간만 더한다. 지금 후보에 본 적 없는 용법이 생긴 저장 구간도 함께 다시 판정한다. 판별 대상은 작업자의 `rematch_judge` 한 번으로 정하고 번역은 바꾸지 않는다.
- 이유: 새 패턴마다 버전이 올라, 일괄 재처리는 LLM 호출이 폭증한다.
- 근거: 이력 41·53·56절 · FR-A24 · `sentence_analysis.matcher_version`

### 재판정 실패는 저장하지 않는다
재판정 실패, 하루 한도 초과, 저장 직전 재확인 불일치면 `matcher_version`까지 아무것도 저장하지 않고, error 없이 다시 읽은 행으로 응답한다.
- 이유: 캐시 문장은 이미 볼 결과가 있고 다음 조회가 다시 시도한다.
- 근거: 이력 41·52·53절 · FR-A24

### 보류: 판 번호와 버전 상승 폭
`revision`·`usage_revision`·`basis_revision` 칼럼은 만들지 않았다. 용법 정의 변경을 판 번호로 다시 보는 일과 한 트랜잭션의 버전 상승 폭(지금 1)은 미정이다.
- 근거: 이력 32·36·45·56절 · requirements 8장

## 동시성·장애 복구

### 선점으로 한 번만 실행
새 문장은 LLM 전에 처리 중 분석 행을 만들고, 기존 행은 처리 중·fresh가 아닐 때만 조건부 UPDATE로 선점하며 세대 번호를 올린다. 다른 요청은 소식을 먼저 구독하고 결과를 함께 받는다.
- 이유: 중복 LLM 호출을 막고, 실패한 첫 시도의 사용 기록도 그 행에 잇는다.
- 근거: 이력 4·46·51절 · FR-A25 · ADR 0005

### 세대 번호로 늦은 결과를 막는다
작업은 시작 때 읽은 세대 번호가 저장 직전과 다르면 저장을 되돌리고 행을 failed로 둔다(stale 유지). 같은지만 비교한다.
- 이유: 사건 전에 시작한 작업이 옛 후보로 저장하며 stale을 푸는 것을 막는다.
- 근거: 이력 19·29·35·51절 · `sentence_analysis.generation`

### 선점 만료와 시도 확인
선점은 150초 뒤 다음 요청이 다시 잡는다. 미완료 작업을 다시 큐에 넣지 않는다. 작업은 행이 자기 시도(`processing_started_at`)로 처리 중일 때만 실행한다.
- 이유: DB에 분석 텍스트가 없어 재투입할 수 없고, 늦은 작업이 새 시도를 망치면 안 된다.
- 근거: 이력 51절 · FR-A25

### 재판정은 Redis 잠금으로 한 번
같은 문장·버전(·후보 상태)의 재판정은 `rematch:<해시>:<버전>[:<후보 상태>]` Redis 잠금을 잡은 요청만 큐에 넣고 나머지는 기다린다. 첫 분석 선점과는 따로이며, 겹치면 stale 재분석이 이긴다.
- 이유: 중복 재판정을 없애되 분석 행 스키마는 그대로 둔다.
- 근거: 이력 53·56절 · FR-A24

### 잠금 순서
원형 연결 advisory 잠금 → 패턴과 그 회화체(id 순) → 용법 → 패턴 세트 버전 → 분석 행(id 순), 모두 `FOR NO KEY UPDATE`. 구간은 분석 행을 잠근 뒤 쓰고, `span_match` 부분 UNIQUE(analysis, pattern, start, end)를 백스톱으로 둔다.
- 이유: FK의 KEY SHARE와 순서가 엇갈린 경로에서 교착이 재현됐다.
- 근거: 이력 32·35·41·42·43절 · `span_match`

### 저장 직전 판정 근거 재확인
원형 연결이 바뀌었거나, LLM 없이 확정한 근거(용법 완결·규칙)가 사라지거나 규칙이 새로 승인됐거나, 재판정 구간의 후보가 바뀌었으면 저장하지 않는다(첫 분석은 실패, 재매칭은 다시 읽은 행으로 응답).
- 이유: 사건의 stale 처리는 커밋 전 구간을 보지 못해 다시 분석될 계기가 없다.
- 근거: 이력 42·45·56절

### 공용 행은 비었을 때만 채운다
LLM이 채우는 공용 칸(한국어 뜻, 대응 표현·기능 태그, 접속 형태)은 비었을 때만 조건부 UPDATE로 쓴다.
- 이유: 잠금 없이 경합을 견디고 늦은 LLM 결과가 관리자 수정을 덮지 않게 한다.
- 근거: 이력 50·54·55·66절

### 보류: 사건과 겹친 첫 분석
처음 분석하는 문장의 처리 중 행은 구간이 없어 영향 범위에 들지 않아, 그사이 반려·병합이 있으면 옛 기준으로 저장될 수 있다(반려된 결과는 조회 때 빠진다).
- 근거: 이력 35·41·43·53절

## 매칭·판별·구간

### 형태소 조건과 lemma
조건은 lemma·품사 대·중분류·활용형이고 빈 칸은 정확히 1토큰이다. lemma는 조사·조동사면 SudachiPy 원형, 내용어면 정규형이다. 패턴은 연속 토큰만 다루고 불연속 문법(〜ば〜ほど)은 MVP에서 뺀다.
- 이유: 정규형을 쓰면 ちゃ→て처럼 기능어가 바뀌어 ちゃいけない와 ていけない가 한 패턴이 된다.
- 근거: 이력 5·17절 · FR-A05 · `pattern_morpheme`

### 탁음화 조건부 매핑
앞 토큰이 동사의 連用形-撥音便·イ音便이면 뒤 기능어를 청음형으로 본다(で→て, じゃう→ちゃう, だ→た, どく→とく 등, 목록은 schema). 형태소 단계에서 바꾸고 기존 패턴은 고치지 않는다.
- 이유: 패턴 조건과 매칭이 같은 lemma를 쓰고, 같은 회화체가 두 패턴으로 갈라지지 않게 한다.
- 근거: 이력 17·33·42절 · `grammar_pattern.morpheme_key`

### 수사 보정 형태소를 함께 쓴다
분석과 패턴 확인(예문 검사·검수)은 수사 경계·읽기를 JMdict로 바로잡은 같은 형태소를 쓴다.
- 이유: 둘이 다른 토큰을 보면 예문 검사와 실제 매칭이 어긋난다.
- 근거: 이력 69절 · FR-A04

### 패턴 동일성
형태소 조건을 이은 값의 해시(`morpheme_key`)가 같으면 같은 패턴이고 DB 유일성으로 동시 생성을 막는다. 이름만 다른 같은 패턴은 관리자가 합친다(FR-A27, 회화체 용법 병합과 별개, 티켓 없음).
- 이유: 형태소 순서가 같으면 이름이 달라도 같은 패턴이다.
- 근거: 이력 14·33·43절 · FR-A27

### 구간 판정 순서
활성 정정 → 용법 완결 → 판별 규칙 → (판정 통계, Phase 1은 끔) → LLM 순이다. LLM 없이 확정하는 근거는 승인된 지식만이다.
- 이유: 미검수 지식으로 확정하면 미검수가 검수처럼 보인다.
- 근거: 이력 5·7·36·45·70절 · FR-A06 · `span_match.decided_by`

### 새 문장의 LLM 판별 범위
DB로 확정하지 못한 후보 구간은 미검수 단일 용법을 포함해 모두 첫 LLM 요청에서 판정하고, 문장 전체의 새 구문 제안도 같이 받는다. 입력은 구간 ID·토큰 범위·후보 ID와 용법 이름·설명이다. 안 걸린 조사·조동사는 힌트일 뿐이다. 확정 구간은 `decided_spans`로만 알리고, 같은 자리·조건의 새 구문은 버린다.
- 이유: 번역 때문에 어차피 부르므로 입력 토큰보다 정확도를 우선한다. 확정 구간을 다시 제안받으면 유료 다시 묻기로 이어진다.
- 근거: 이력 13·14·17·32·36절 · FR-A08 · ADR 0001

### 후보 하나도 판정하고 확인 중으로 보인다
용법 완결이 아니면 후보가 하나여도 LLM이 판정한다. 판별 대상은 LLM 전에 '확인 중'으로 먼저 보이고, 후보가 하나면 그 용법 설명을 미리 채운다. 미검수 후보가 있으면 배지를 단다.
- 이유: 같은 형태소도 다른 용법일 수 있어, 건너뛰면 틀린 용법이 공용 캐시에 굳고 새 용법 등록이 막힌다. 후보 이름도 LLM 지식이다.
- 근거: 이력 37·60절 · FR-A10

### 판정 상태
구간에는 decided / not_applicable / divergent / unfound / unresolved만 저장한다. 해당 없음(새 문법을 찾지 않음)과 미발견(`unfound`, 새 문법 등록)을 나누고, 판별 대상은 저장하지 않는다. 대상 문법 없음은 실패와 구분해 "문법 요소 없음"으로 보인다.
- 이유: 둘을 합치면 쓸모없는 패턴·LLM 호출이 생기고 "조건이 너무 넓은 패턴" 신호가 사라진다.
- 근거: 이력 22·28절 · `span_match.state`

### 확정·미검수는 조회할 때 정한다
고른 용법, 그 소속 패턴, 실제 매칭 패턴, 그 연결 원형이 모두 approved면 확정, pending이 있으면 'AI 생성·미검수', rejected가 있으면 응답에서 뺀다. 대안·확인 중 후보도 하나씩 같은 규칙이다.
- 이유: 구간에 적으면 승인·반려 때마다 대량 갱신이 필요하고 하나만 놓쳐도 불변식이 깨진다.
- 근거: 이력 28·29·42절 · FR-A10 · ADR 0003

### 용법 완결 패턴의 단일 후보 확정
패턴이 승인·용법 완결이고 반려되지 않은 용법이 승인된 하나뿐이면 LLM 없이 확정한다(`single_usage`). 분석할 때 다시 확인한다.
- 이유: 표시와 분석 사이에 상태가 바뀔 수 있다.
- 근거: 이력 36·42절 · FR-A06

### 판별 규칙
관리자가 admin에서만 만든다. 구간 앞뒤 두 토큰까지의 AND 조건이고, 실제 매칭 패턴의 승인 규칙만 본다. 맞는 규칙들이 가리키는 후보가 하나면 확정(`rule`)하고 둘 이상이면 LLM으로 넘긴다. 승인된 규칙은 고치지 않고 폐기 뒤 새로 만든다.
- 이유: 판정 기록이 규칙을 가리키므로 내용이 바뀌지 않아야 한다. 회화체도 규칙은 패턴별이다.
- 근거: 이력 26·45절 · FR-A13 · `usage_rule`
- 보류: 연결된 회화체 규칙에 원형 승인도 요구하는 지금 구현(확인 필요).

### 해석 갈림과 미확정
첫 응답은 해석 갈림이면 주 용법(번역과 같은 해석)만 받는다. 해석 갈림·미확정 구간은 같은 조건 다시 묻기와 한 호출로 한 번만 다시 묻고 대안마다 용법·대안 번역·근거를 받는다. 근거가 빈 대안은 버리고 남은 대안이 없으면 미확정이며, 주 해석이 바뀌면 번역도 바꾼다. 재질문이 실패하면 미확정으로 굳히지 않고 분석 실패로 둔다.
- 이유: 근거는 문장을 풀어 쓴 글이라 어디에도 저장하지 않는다. 일시 실패가 공용 캐시에 굳으면 안 된다.
- 근거: 이력 14·17·40절 · FR-A08·A09 · `span_match.alternatives`

### 관리자 정정의 적용
정정은 평가 결과 항목에서만 만든다. 분석할 때 다른 판정보다 먼저 `admin`으로 확정하고 `decided_spans`로 번역도 따르게 하며, 매칭을 푼 구간은 뺀다. 정정 후 용법·소속 패턴·매칭 패턴·연결 원형 중 하나라도 반려면 건너뛰고 정정 상태는 그대로 둔다. 구간 새로 만들기·경계 정정은 하지 않는다.
- 이유: 공용 분석에 원문이 없다. 상태를 고쳐 쓰면 관리자가 멈춘 정정과 구분할 수 없다.
- 근거: 이력 29·70절 · FR-A21 · `match_correction`

## 문법 패턴·용법

### 설명은 용법마다 하나
설명은 용법 단위로 한 번 쓰고 모든 문장이 함께 쓴다. 문장 기준 해설은 넣지 않고, 같은 글자라도 용법이 다르면 따로 둔다.
- 이유: 문장별 설명은 중복 저장·공용 테이블의 문장 해설·반복 출력 비용을 낳는다.
- 근거: 이력 7·31절 · `grammar_usage`

### 새 구문 등록 규칙
LLM은 문법의 처음부터 끝까지 토큰을 빠짐없이 나열하고 토큰마다 lemma 고정 / 활용형도 고정 / 아무거나를 표시한다. 처음·끝은 아무거나일 수 없고, 고정 토큰에 조사·조동사가 없으면 등록하지 않는다. 어긴 제안만 빼고(그 자리는 미발견), 원래 문장에 다시 걸려야 저장한다.
- 이유: 빈틈 없는 나열이 검증이 단순하고, 내용어만 고정한 패턴은 그 구절에만 걸린다.
- 근거: 이력 14·32절 · FR-A11 · requirements '패턴 매칭 규칙'(#145)

### 활성화 근거와 패턴 세트 버전
원래 문장 재매칭과 새로 쓴 '걸려야 함' 예문 매칭을 둘 다 통과하면 활성화한다. `is_active`, 활성 패턴의 조건, 매칭 자격(활성 + 후보가 될 용법 1개 이상)이 바뀌어 매칭이 달라질 수 있으면 패턴 세트 버전을 올린다.
- 이유: 자동 등록 때는 test_cases를 쓸 주체가 없고, 비활성 동안 분석된 문장은 버전 비교로만 찾는다.
- 근거: 이력 28·29·35·41·42절 · FR-A05 · `pattern_set_version`

### 같은 조건 다시 묻기와 새 용법
새 구문의 `morpheme_key`가 이미 있으면 새 용법을 버리고 기존 용법으로 같은 요청 안에서 한 번 더 묻는다(반려 패턴은 묻지 않음). 기존 용법이 안 맞으면 이름·설명·예문을 받아 같은 패턴 아래 미검수 용법으로 더하되, 같은 이름이 있으면 더하지 않는다.
- 이유: 이름으로 묶으면 LLM이 같은 용법을 다른 이름으로 불러 어긋난다.
- 근거: 이력 33절 · FR-A11

### 공용 예문과 원문 복사 검사
공용 예문(`example_ja`, `test_cases`)은 LLM·관리자가 새로 쓴 문장을 매칭기로 확인한 뒤에만 넣는다. 원문과 같거나, 원문 전체를 포함하거나, 연속 `EXAMPLE_COPY_LENGTH`(기본 8자) 이상 베끼면 거부한다(고정 토큰 글자는 세지 않되 그 사이를 이은 복사는 셈). 베낀 예문만 한 번 다시 쓰게 하고 그래도 실패하면 예문 없이(비활성) 등록한다.
- 이유: 드래그 원문은 재매칭 검증에만 쓴다(불변식). 관리자는 이 예문으로 승인한다.
- 근거: 이력 26·28·29·32·34절 · `grammar_pattern.test_cases`
- 보류: 8자 기준을 실제 모델 예문으로 확인하지 않았다.

### LLM 글의 원문 인용 거부
LLM이 쓴 공용 글(용법 이름·설명, 대응 표현 등)이 문장 전체를 인용하면 거부한다. 기호·공백을 지우고 비교하고, 형태소 하나뿐인 문장은 예외다.
- 이유: 이 글들은 공용 테이블에 들어간다.
- 근거: 이력 31·54절 · FR-A09

### 승인·반려 상태와 승인 조건
패턴과 용법은 각각 pending / approved / rejected다(패턴 상태는 자기 용법 없는 회화체 때문). 반려 취소는 항상 pending이고, 용법은 자기와 소속 패턴이 모두 반려가 아닐 때만 유효하다. 패턴 승인·용법 완결 표시는 test_cases('걸려야 함'·'걸리면 안 됨' 각 1개 이상, 모두 통과)가 조건이고 용법 승인은 소속 패턴이 반려가 아니면 된다. 반려된 지식의 구간은 조회에서 바로 뺀다.
- 이유: 예문 없이 승인되는 길을 막고, 관리자가 틀렸다고 한 결과는 재분석 중에도 보이지 않는다.
- 근거: 이력 28·29·35절 · FR-A13 · requirements 전이표
- 보류: 승인 취소를 pending과 rejected 중 어디로 되돌릴지(지금 pending).

### 반려·전이의 영향 범위
용법 반려·승인 취소는 그 용법으로 정해진(대안 포함) 분석을, 패턴 단위 사건은 그 패턴과 그 회화체의 분석을 stale로 만들고 세대 번호를 올린다. 후보로만 든 용법은 넣지 않는다(용법 병합은 예외). 주 용법이 반려된 옛 번역은 숨기지 않고 '재분석 중'으로 덮는다.
- 이유: stale만으로는 전이 전에 시작한 작업이 옛 후보로 저장할 수 있다. 번역이 사라지면 문장을 이해할 수단이 없다.
- 근거: 이력 29·35·38·40·42·43절

### 용법 완결
패턴 승인 + test_cases 통과 + 반려되지 않은 용법이 승인된 하나뿐일 때만 붙이고, 용법이 늘 수 있는 사건(새 용법, 용법 반려 취소, 승인 취소·반려)마다 떼고 stale로 만든다.
- 이유: 용법이 둘이 될 수 있으면 LLM 없는 확정을 멈춰야 한다.
- 근거: 이력 5·35·42절 · `grammar_pattern.usage_closed`
- 보류: 어떤 패턴에 붙일지의 기준과 초기 대상.

### admin 편집 범위
`sentence_analysis`·`span_match`는 admin에 올리지 않는다. 패턴은 이름·접속 형태·test_cases·`show_parts`, 용법은 설명·예문·대응 표현·기능 태그만 고치고, 상태는 액션으로만 바꾼다. 패턴·용법은 admin에서 더하거나 지우지 않는다(회화체 합침 예외).
- 이유: 원문 비노출, 그리고 폼을 연 사이 액션이 바꾼 상태를 덮지 않기 위해서다.
- 근거: 이력 35·43·44·54·55·66절 · FR-A13

### 회화체 패턴의 원형 연결
회화체는 별도 패턴으로 두고 관리자만 원형에 연결한다(`variant_of` 1단계). 연결된 회화체는 원형 용법을 쓰고 새 용법도 원형 아래 만든다. `register`는 연결 때 colloquial이 되고 풀어도 남는다. 확정 근거는 실제 매칭 패턴 기준이고 원형 상태도 본다. 풀어도 원형으로 간 용법은 돌려받지 않는다.
- 이유: 설명을 복사하면 원형 정정이 전파되지 않고 학습 카드가 중복된다.
- 근거: 이력 14·18·19·42절 · FR-A28 · `grammar_pattern.variant_of`
- 보류: register에 방언 등 다른 값을 둘지.

### 연결 때 자기 용법 병합
남은 자기 용법은 관리자가 용법마다 합침(원형 용법으로, 원래 행은 지움) 또는 옮김(원형 아래로, 검수 상태 유지)을 고른다. 이름 자동 대응·기본 선택은 없다. 구간·규칙·정정의 용법 참조를 옮기고, 반려된 자기 용법은 남되 반려 취소할 수 없다.
- 이유: 이름이 같다고 같은 용법이 아니고, "반려되지 않은 자기 용법 없음"을 지켜야 한다.
- 근거: 이력 19·42·43·45·70절

### 구성 문법
긴 패턴 구간 안에 완전히 들어가는 구간은 바깥 패턴의 `show_parts`가 true면 하위 박스, false면 숨긴다. 관계는 위치로만 계산하고 판정·저장은 따로 한다. `show_parts`는 표시 전용이다.
- 이유: 화면 접기와 분석 제외를 나눠야 안쪽 후보를 잃지 않는다.
- 근거: 이력 5·44절 · FR-A10 · `grammar_pattern.show_parts`

### 대응 표현과 기능 태그
대응 표현(없으면 NULL)과 기능 태그(허용 목록 32개)는 용법에 두고 새 용법을 만드는 모든 LLM 경로가 함께 답한다. 틀린 값은 그 칸만 버린다. 각자 채움 여부와 검수 상태를 따로 두어, 승인된 용법에 나중에 채운 값만 그 줄에 배지를 단다. 품사 태그는 저장하지 않고 매칭 패턴 조건의 pos1로 계산한다.
- 이유: 채우기 명령이 승인된 용법을 채우면 검수 없이 승인된 것처럼 보인다.
- 근거: 이력 54·55절 · FR-A31 · `grammar_usage.korean_equivalent`·`function_tags`

### 기본형과 접속 형태
칩은 매칭 패턴의 저장 이름(기본형)이고 원문이 다르면 `문장 속 형태`를 붙인다. 접속 형태는 패턴 일반 지식으로, 새 패턴은 첫 응답에서, 없는 패턴은 작업자가 원문 없이 따로 채운다. 새 값은 별도 미검수이고 늦은 결과는 관리자 수정을 덮지 않는다.
- 이유: 원문 조각만으로는 배울 형태를 알기 어렵고, 보조 정보가 카드를 기다리게 하면 안 된다.
- 근거: 이력 65·66절 · FR-A10·A32 · `grammar_pattern.connection_form`

### 그림자 모드
자동 승인 기준에 맞는 용법은 '승인했을 것'만 기록하고 pending으로 둔다. 일치율이 충분해지면 실제 자동 승인을 따로 켠다.
- 이유: 기준을 검증하기 전에는 미검수를 승인으로 바꾸지 않는다.
- 근거: 이력 7절 · FR-A14
- 보류: 기준 횟수·일치율·켜는 시점(아직 구현 없음).

### 보류
- 보류: 판정 통계(4단계)와 confidence 기준값(이력 5절, FR-A15).
- 보류: LLM 응답 실패 범위(이력 32절).
- 보류: 〜の 표시 방식(이력 10절), 문법 JLPT 라벨(이력 13절).

## 단어·JMdict

### 단어 사전은 JMdict
단어 정보 표시, 문장에서 고를 뜻 후보, 그 뜻의 한국어 뜻을 한 번 만드는 근거로만 JMdict(EDRDG)를 쓴다. 문장 번역은 LLM이 문장만 보고 하며 JMdict를 근거로 쓰지 않는다.
- 이유: 단어 지식은 문장 없이 공용으로 쌓아 LLM이 덜 필요하게 한다.
- 근거: 이력 16·24절 · FR-A16 · `word` · `word_sense`

### JMdict 라이선스 표시
앱 화면 표시도 CC BY-SA 4.0의 공유로 본다. JMdict 기반 한국어 뜻을 보이는 곳에 CC BY-SA 4.0·출처(EDRDG)·변경 사실을 적고, 약관에 단어 뜻 데이터의 라이선스를 밝히며 재배포를 막지 않는다. 사전 근거가 없는 LLM 뜻에는 출처 각주를 달지 않는다.
- 이유: 이 해석으로 유료 서비스도 가능하고, 앱 코드·번역·문법 설명은 JMdict와 별개다.
- 근거: 이력 16·17·18·50절 · requirements 9장 '단어 사전' · DESIGN §5 'JMdict 출처 각주'
- 보류: 유료화 시점의 법률 확인

### 한 번만 적재하고 태그만 다시 계산
JMdict는 관리 명령으로 한 번 전체 적재하고 원본은 남기지 않으며, 판본 이름과 적재 직후 DB 백업만 남긴다. 예외로 `load_jmdict --update-tags`는 JMdict 단어·뜻의 `tags`만 지금 변환표로 다시 계산한다.
- 이유: 원본 보관·갱신 운영을 지지 않는다(사전 정정 미반영은 운영 한계로 감수).
- 근거: 이력 24·47·67절 · requirements '단어 사전과 단어 매칭'

### 단어 1개 = JMdict 항목 1개, 읽기까지 포함
단어는 표기가 아니라 읽기까지 포함해 구분한다(開く あく / ひらく). 사전에 없는 단어는 `jmdict_seq`가 NULL이고 (사전형, 읽기) 부분 UNIQUE로 중복을 막으며, 대표 표기는 처음 저장한 값으로 고정한다.
- 이유: 표기만으로는 다른 단어가 섞이고, 동시 생성이 같은 새 단어를 두 번 만들 수 있다.
- 근거: 이력 16·24·25·50절 · FR-A16 · `word`

### 뜻은 고정 ID로 가리킨다
단어 뜻은 `word_sense` 행 ID로 식별하고 JMdict 안의 순번은 참고로만 둔다. 사전에 없는 단어도 뜻 행을 하나 이상 갖는다. 내 일본어와 학습 카드는 이 ID를 가리킨다.
- 이유: 배열 순번은 JMdict 순서가 바뀌면 다른 뜻을 가리킨다.
- 근거: 이력 17·23절 · `word_sense` · ADR 0006

### 문장 단어는 모두 기록한다
조사·조동사·기호·공백·숫자를 뺀 토큰을 모두 사전에서 찾아, 키 텍스트 위치와 고른 뜻 ID만 `word_spans`에 둔다. LLM이 '모를 만한 단어'를 고르지 않는다.
- 이유: 사람마다 다른 수준을 추측하지 않고, 같은 문장은 저장 결과를 LLM 없이 다시 쓴다.
- 근거: 이력 50절 · requirements '단어 사전과 단어 매칭' · `sentence_analysis.word_spans`

### 단어 찾기 규칙
활용하지 않는 단어는 표기+읽기로, 활용하는 단어는 사전형 표기로 찾는다. 가나는 통일하고 가나로 쓴 단어는 읽기로도 찾으며, 못 찾으면 정규형·표층형으로 한 번 더 찾는다. JMdict의 읽기·뜻 적용 제한은 후보 거르기와 표기에 맞는 읽기 표시에만 쓴다.
- 이유: SudachiPy 읽기는 활용형 읽기(食べ=タベ)라 활용어를 읽기로 찾을 수 없다.
- 근거: 이력 24·50절 · requirements '단어 사전과 단어 매칭'

### 뜻 고르기는 첫 LLM 요청 안에서
후보 뜻이 하나면 LLM 없이 정하고, 여럿이면 새 문장 첫 LLM 요청 안에서 후보를 모두 넘겨 고르게 한다(상한 없음). 틀리거나 빠진 답은 그 단어만 빼고 번역·문법은 저장한다.
- 이유: 호출을 늘리지 않고, 단어 하나 때문에 문장 전체를 다시 부르지 않는다.
- 근거: 이력 17·31·50절 · FR-A08 · FR-A16

### 한국어 뜻은 뜻마다 한 번 만든다
분석을 저장한 뒤 한국어 뜻이 없는 뜻만 모아 `word_gloss` 한 번으로 만든다. 문장은 넘기지 않고, `meaning_ko`가 NULL일 때만 쓴다. 실패한 뜻은 `failed`로 두고 다른 새 문장에 나올 때 다시 만든다.
- 이유: 한국어 뜻은 모든 문장이 함께 쓰는 일반 뜻이고, 실패해도 분석 저장을 막지 않는다.
- 근거: 이력 24·50절 · `word_sense.meaning_status`

### 사전에 없는 단어는 두 단계로 만든다
첫 요청은 사전형·읽기만 받고, 서버가 다시 찾은 뒤 저장 전 `word_gloss`가 기존 단어면 뜻을 고르거나 미검수 뜻을 더하고, 없으면 새 단어와 뜻을 만든다. SudachiPy가 고유명사로 본 토큰은 넘기지 않는다. 웹 검색은 쓰지 않는다.
- 이유: 사전 항목이 있는데 LLM이 새 단어를 만드는 중복을 막는다.
- 근거: 이력 24·25·50절 · FR-A16 · requirements '새 단어 생성(두 단계)'
- 보류: 사전 항목과 같은 단어로 밝혀진 새 단어의 관리자 병합(티켓 없음)

### LLM 뜻은 같은 단어 아래 두고 따로 검수한다
LLM이 만든 뜻은 JMdict 단어 아래 붙어도 별도 단어로 떼지 않는다. 뜻 자체의 출처·검수(`sense_origin`·`sense_status`)를 한국어 뜻의 것과 따로 두고, 반려된 뜻은 후보·응답에서 빠진다.
- 이유: 단어가 쪼개지면 카드도 쪼개지고, 미검수 뜻이 검수된 뜻처럼 보이면 안 된다.
- 근거: 이력 24·50절 · `word_sense`

### 품사와 단어 전체 태그는 JMdict에서
`word.pos`와 단어 전체 태그(품사·동사 그룹·い/な형용사·고유명사·접미사)는 JMdict에서 만들고, 문장 속 활용형과 동사 그룹 표시는 SudachiPy가 문장마다 계산한다. 사전에 없는 단어의 태그는 LLM이 허용 목록 안에서만 고른다.
- 이유: 공용 행에 처음 만난 문장의 SudachiPy 값이 굳지 않게 한다.
- 근거: 이력 14·47·62절 · FR-A29 · `word.tags`

### 단어 전체 태그와 뜻 태그를 나눈다
자동사/타동사, 경어, 보통 가나로 씀, 의성어·의태어, 외래어, 문체는 뜻마다 저장하고 JMdict 태그를 먼저 쓴다(문체는 JMdict misc 코드를 옮기며 LLM을 부르지 않는다). 화면은 고른 뜻의 태그를 보인다. 허용 목록은 코드 상수다.
- 이유: 같은 단어도 뜻마다 다르다(夜が明ける 자동사 / ドアを開ける 타동사).
- 근거: 이력 14·17·24·47·67절 · FR-A29 · `word_sense.tags`

### 예외 1그룹
JMdict pos가 `v5r`인 뜻이 있고 읽기가 い단·え단+る로 끝나면 `group1` 대신 `group1_exception`을 붙여 '예외 1그룹'으로 보인다. 모양과 그룹이 어긋나지 않는 불규칙 단어(行く·する·来る·いい 등)는 그룹이나 품사만 보이고, 불규칙 활용은 활용표가 보인다.
- 이유: JMdict에서 帰る류도 일반 5단과 같은 `v5r`이라 모양으로 따로 가려야 한다.
- 근거: 이력 47·48절 · FR-A29 · DESIGN §5

### 자타 대응 동사
뜻마다 상대 표기 글자(`word_sense.pair_form`, NULL은 짝 없음 또는 미확인)만 두고, 웹 단어 화면에서만 "타동사: 開ける"처럼 관계로 보인다. 사이드 패널은 태그까지만 보인다.
- 이유: 상대 단어 행이 없을 수 있고 양쪽 동기화가 번거롭다. 패널은 가독성을 우선한다.
- 근거: 이력 14·15·22·24절 · FR-A29 · FR-M11 · `word_sense.pair_form`
- 보류: 이 칸을 채우는 경로와 웹 단어 화면은 아직 없다

### 활용표는 규칙 코드로 계산
ない형·ます형·て형 등은 그룹별 규칙과 예외 목록으로 계산하고 DB 칸을 두지 않는다. 웹 단어 화면에서만 보이고, 그룹별 설명문은 관리자가 검수한다.
- 이유: 규칙으로 정해지는 값이라 저장할 필요가 없다.
- 근거: 이력 14·20절 · FR-M11

### '보통 가나로 씀' 뜻은 가나를 표제로
고른 뜻에 `보통 가나로 씀` 태그가 있고 사전형에 한자가 있으면 읽기(가나)를 표제로, 사전형을 회색 글자 자리에 둔다.
- 이유: 실제 글에서는 가나로 나오는 단어라 한자 표제가 오히려 낯설다.
- 근거: DESIGN §3 단어 표제 · `word_sense.tags` · #367

### 같은 단어·같은 뜻은 한 행으로
같은 단어·같은 뜻인 행은 화면에서만 합치고 횟수는 보이지 않는다. 위치를 뺀 내용 전체가 같을 때만 합치고, 지정한 이름과 표기가 같은 자리는 따로 둔다.
- 이유: 같은 단어가 자리마다 반복되지 않게 하되, 합친 행이 다른 내용이나 미검수 배지를 가리면 안 된다.
- 근거: 이력 61절 · DESIGN §3

### 수사로 시작하는 말은 JMdict로 보정
한자 수사 + 바로 뒤 명사·접미사를 이은 표기가 JMdict에 있으면 한 단어로 합치고, 수사 글자로 시작하는 한 토큰의 읽기는 JMdict 읽기로 맞춘다. 분석과 패턴 확인이 같은 보정 결과를 쓴다. LLM이 만든 단어는 근거로 쓰지 않는다.
- 이유: SudachiPy가 一件을 나누고 一回를 소리 변화 없이 읽어 단어 카드와 루비가 틀렸다.
- 근거: 이력 69절 · FR-A04 · requirements '수사 보정'

### 보류 (단어)
- 히라가나만으로 쓴 단어의 처리, 중복 뜻 병합 후보 추천에 벡터 DB를 쓸지(단어 조회에는 쓰지 않는다, 이력 25절)

## 이름·경칭

### 고유명사는 주석만 붙인다
형태소와 문법 후보는 그대로 두고, 새 문장 첫 LLM 요청이 토큰 ID 묶음과 종류(사람·장소·조직·작품·기타)를 함께 답해 이름 구간(`name_spans`)으로 둔다. 위치는 서버가 계산한다. NULL(판단 안 함)을 채우려고 다시 분석하지 않는다. 이름의 뜻은 번역에 맡긴다.
- 이유: 호출을 늘리지 않고, 위치는 서버가 계산한다는 불변식을 지킨다.
- 근거: 이력 5·58절 · FR-A23 · `sentence_analysis.name_spans`

### 이름 지정은 개인 데이터
사용자가 단어 카드의 표기를 이름으로 지정하면(읽기는 선택) 그 사용자 화면에만 적용한다. 공용 분석·공용 단어·캐시·LLM 요청·admin·로그에 넣지 않고, 확장이 원문 자리의 표층형으로 맞춘다.
- 이유: 개인 판단이 공용 결과를 바꾸면 안 된다.
- 근거: FR-A30 · NFR-11 · `designated_name`

### 지정한 이름의 기본 보기
지정한 이름과 표층형이 같은 자리는 `name_spans`가 NULL이거나 자리가 그 안이면 이름 행, 밖이면 사전 단어 행으로 시작한다. `사전 단어 보기` 토글은 그 자리만 바꾸고 저장하지 않는다.
- 이유: 인물 이름 春을 지정해도 계절 春은 사전 단어로 보여야 한다.
- 근거: 이력 58절 · FR-A30

### 이름 종류 배지
`name_spans` 안에 드는 단어 카드의 배지 줄에 종류 배지(`인명`·`지명` 등)를 단다. 중립 배지이고 'AI 생성·미검수'를 달지 않는다. 이름 행, NULL·`[]`에는 달지 않는다.
- 이유: 새 지식(용법·뜻)이 아니라 문장 안의 선택 판단이고 검수 흐름도 없다.
- 근거: 이력 58·59절 · FR-A23 · DESIGN §5

### 이름과 경칭은 다른 카드
`西山さん`은 `西山`(고유명사, `인명` 배지)과 `さん`(접미사, 경어 뜻 태그 유지, `인명` 배지 없음) 두 카드다. 카드가 없는 이름 토큰은 응답할 때 보충하고(`is_name`) 공용에 저장하지 않으며 뜻을 만들지 않는다.
- 이유: 고유명사가 단어에서 빠지고 경칭만 사람 이름처럼 보였다.
- 근거: 이력 62절 · FR-A23 · requirements '이름과 접미사 카드'

### 이름의 한글 읽기
보충한 이름 카드는 추정 가나 읽기를 대조표와 장음·촉음 규칙으로 한글로 옮겨 뜻 자리에 보인다(사토·도쿄 같은 통상 표기). LLM을 부르지 않고, 옮길 수 없으면 줄을 생략한다. 응답할 때마다 계산하고 저장하지 않는다.
- 이유: 이름에는 뜻 대신 읽는 법이 필요하고, 개인 기록을 남기지 않는다.
- 근거: 이력 63절 · requirements '이름의 한글 읽기' · ADR 0006
- 보류: 지정한 이름 읽기 편집, 한글 읽기 교정

## 한자

### KANJIDIC2 선적재
`kanji`에 상용한자 약 2,100자를 KANJIDIC2(CC BY-SA 4.0)로 미리 채운다. 한국어 뜻(훈음)은 LLM이 만든 뒤 검수하고 검수 전에는 'AI 번역'이다. 연결 테이블 없이 단어 표기를 글자 단위로 잘라 조회한다.
- 이유: 표기에서 바로 찾을 수 있어 연결을 따로 관리하지 않는다.
- 근거: 이력 13·17절 · FR-A17 · `kanji`
- 보류: 모델·적재·한자 타일은 아직 없다(티켓 없음, 이력 50절)

### 보류: 내 일본어의 한자
원문을 저장하지 않아 원문에서 한자를 뽑을 수 없다. 내 일본어와 학습 카드에 한자를 넣는 방식은 넣을 때 정한다.
- 근거: ADR 0006 · FR-M10 · DESIGN §7

## LLM·비용

### 공급자·모델·추론 강도
OpenAI만 쓴다. 모델은 `OPENAI_MODEL`(현재 `gpt-6-luna`), 추론 강도는 `OPENAI_REASONING_EFFORT`(비우면 `low`, SDK 허용값 밖이면 시작 거부)로 모든 호출에 같게 준다. 프롬프트 캐싱은 고정 접두부 1,024토큰 이상으로 두고 `cached_input_tokens`로 본다.
- 이유: 코드 수정 없이 바꾼다. low의 품질은 아직 재지 않았다.
- 근거: 이력 8·46·64절 · requirements 9장 · `usage_log`

### 새 문장은 LLM 요청 한 번
번역·후보 구간 판정·새 구문 제안·단어 뜻 고르기·이름 구간을 structured output 한 번으로 받는다. 문장 하나만 넣고 문맥·웹 검색은 쓰지 않으며, 후보에는 용법 설명까지 넣는다(정확도 우선).
- 이유: 나누면 입력 비용이 두 배이고 번역과 해석이 어긋난다.
- 근거: 이력 2·14·17·24절 · 31절 20 · 32절 3 · 58절 · FR-A08

### 보조 호출은 필요할 때만
다시 묻기·예문 다시 쓰기·재판정·단어 2단계·접속 형태 채우기만 따로 부른다. 결과가 버려질 호출(다른 요청이 이미 저장, 같은 조건 패턴이 반려, 이미 통과한 예문)은 보내지 않고, 재질문은 구간을 모아 한 번에 묻는다. DB로 확정한 구간은 `decided_spans`로 알려 다시 제안하지 않게 한다.
- 이유: 새 문장당 토큰이 핵심 비용 지표다.
- 근거: 이력 33절 4 · 34절 6 · 36절 4 · 40절 3 · NFR-01

### 일시 오류만 한 번 다시 보내기
아무것도 받기 전의 연결 오류·429·5xx만 요청 마감 안에서 1회 다시 보낸다(`attempt=2`). 타임아웃·검증 실패·조각을 받은 스트림은 다시 보내지 않는다.
- 이유: 과금됐을 수 있는 호출은 반복하지 않는다.
- 근거: 이력 51절 5 · `usage_log`

- 보류: 사용자당 비용(NFR-02) 재검증, '에이전트'(나중 일괄 작업용, 이력 14절).

## 작업 큐·작업자·스트리밍

### LLM 작업은 큐와 작업자가
첫 분석·stale 재분석·재판정·접속 형태 채우기는 RQ 작업자가 한다. 큐 입력은 결과를 남기지 않고(`result_ttl=0`) 150초 안에 시작하지 못하면 버리며, Redis 영속화는 끈다.
- 이유: 선점 만료·세대 번호가 작업자 모델을 전제한다.
- 근거: 이력 9절 · 28절 5 · 51·53절 · 66절 3 · NFR-12 · ADR 0005

### NDJSON 스트림(ASGI)
분석 응답은 POST 한 번의 `application/x-ndjson` 스트림이고 서버는 uvicorn이다. 요청 쪽은 먼저 구독한 뒤 선점·큐 넣기를 한다.
- 이유: EventSource는 POST·Bearer를 못 쓰고, 비동기 서버는 기다리는 연결에 묶이지 않는다.
- 근거: 이력 31절 21 · ADR 0005

### 이벤트와 응답 칸 순서
`previous` → `grammar` → `translation` → `judged` → `analysis`(해당 없으면 건너뜀). 첫 LLM 응답 칸은 `translation_ko` → `spans` → `words` → `new_patterns` → `new_words` → `name_spans`이고, 앞 세 칸은 닫히는 대로 그 칸만 검증해 먼저 보낸다. 저장은 전체 검증 뒤다.
- 이유: 번역을 먼저 보인다. 구간 단위는 이득보다 복잡도가 크다.
- 근거: 이력 36~38·41·60절 · FR-A10

### 실패 알림
요청 쪽 실패(형태소 분석·한도·길이)는 상태 코드로, LLM 작업 실패는 번역 전이라도 `error` 이벤트로 알리고 저장하지 않는다. 응답에는 `도메인:이름` 코드만 싣고 화면 문구는 클라이언트가 정한다.
- 근거: 이력 31절 10·22 · 51절 · ADR 0005

### 시간 상한
LLM 스트림 60초(조각 사이 30초), 요청 하나의 LLM 대기 110초(소프트 마감), RQ 작업 120초, 요청 쪽 대기 130초, 선점·재판정 잠금·동시 요청 셈 150초.
- 이유: 안쪽이 먼저 끝나야 저장도 오류도 없이 끊기는 일이 없다.
- 근거: 이력 31절 23 · 34절 8 · 51~53절 · NFR-14 · ADR 0005

- 보류: 재접속 때 결과 버전으로 다시 읽기, 운영 nginx 버퍼링·읽기 시간, 재판정 반복 실패 상한.

## 한도·사용량

### 하루 토큰 한도
사용자마다 하루(`Asia/Seoul` 자정) LLM 토큰 200,000(입력+출력, 캐시된 입력 포함, `ANALYSIS_DAILY_TOKEN_LIMIT`). 넘으면 LLM을 새로 부를 때만 `ANALYSIS:USAGE_LIMIT`(429)로 거부하고, 작업자도 시작할 때 다시 본다. 재판정은 부르지 않고 저장 결과로 응답한다. 관리 명령의 사용자 없는 호출은 세지 않는다.
- 이유: 문장 수·길이 대신 사용자별 토큰으로 비용을 막는다.
- 근거: 이력 31절 11 · 52·53·56절 · 57절 5 · NFR-14

### 동시 분석 요청 제한
사용자마다 10(`ANALYSIS_MAX_CONCURRENT`, Redis, 150초 만료). 넘으면 형태소 분석 전에 `ANALYSIS:TOO_MANY_REQUESTS`(429). 사이드 패널은 따로 동시 5개(접속 형태 보조 요청 2개)까지 보낸다.
- 근거: 이력 31절 11 · 52절 2 · 66절 4 · NFR-14

### 원문 길이 상한
요청 하나(문장 하나)의 원문은 정규화 전 1,000자까지, 넘으면 `ANALYSIS:TEXT_TOO_LONG`(413). 문장 수 상한은 없다.
- 이유: 캐시 문장은 토큰 한도에 걸리지 않아, 토큰을 쓰지 않는 요청으로 서버 자원을 끝없이 쓰는 것을 막는다.
- 근거: 이력 31절 11 · 71절 · NFR-14

### 사용 기록
요청마다 request 행(경로 `cache`/`db`/`llm`, 성공 여부), LLM 호출마다 llm 행(목적·토큰·성공·`attempt`)을 남기고 원문은 남기지 않는다. 선점한 분석 행에 처음부터 이어 실패한 첫 시도도 문장 비용에 넣는다.
- 이유: 목적별 비용(재질문·예문 다시 쓰기·재판정)을 따로 본다.
- 근거: 이력 29절 5·13 · 46·51절 · FR-A18 · `usage_log`

- 보류: 집계 규칙(FR-M01), 처리 중 작업에 붙은 요청의 경로(지금 `llm`), 기록 수·요청 속도 제한, 확장 토큰 발급 속도 제한.

## 품질 평가

### 고정 평가 세트
관리자가 직접 쓴 문장(목표 50문장, NFR-09 유형별)을 `evaluate --yes`로 실제 분석 흐름에 돌린다.
- 근거: 이력 7·9·57절 · FR-A26 · `eval_sentence`

### 사람이 채점
정답을 미리 적지 않고 항목마다 맞다·애매하다·용법이 틀렸다·구간이 틀렸다로 채점하고 놓친 문법 수를 적는다. 같은 결과는 지난 채점을 이어받는다.
- 이유: 시드 없이 LLM이 용법을 만들어 정답을 미리 적을 수 없다.
- 근거: 이력 57절 1·6 · `eval_item`

### 지표
구간 정확도·용법 정확도·애매 비율·판별 보류 비율·문장당 호출 수·토큰·비용을 채점한 항목으로만 내고 실행끼리 비교한다. confidence는 정확도로 쓰지 않는다. 비용은 `EVAL_PRICE_*`가 모두 있을 때만 낸다.
- 근거: 이력 7절 · 57절 3·7 · FR-A26

### 평가 결과는 공용 캐시에 남음
평가 문장은 실제 요청처럼 선점·분석·저장하고 매번 새로 분석한다. 실패하면 선점 전 캐시를 되살린다.
- 이유: 분석 흐름이 저장까지 한 몸이고, 관리자 문장이라 원문 불변식에 걸리지 않는다.
- 근거: 이력 57절 2

- 보류: 정정을 자동 채점에 쓰기, 판정 통계·confidence 기준값, 정기 자동 실행.

## 계정·로그인·약관·확장 연결

### 커스텀 사용자 모델
`AbstractUser` + `google_sub`(UNIQUE)로 같은 사람을 가린다. 이메일은 UNIQUE가 아니고 로그인마다 갱신한다. Google 계정은 비밀번호를 쓰지 않고 admin은 `createsuperuser` 계정으로 들어간다.
- 이유: 이메일은 바뀌거나 겹치고, 사용자 모델은 처음에만 싸게 바꿀 수 있다.
- 근거: 이력 49절 2 · ADR 0004 · `users`

### Google 로그인
웹이 받은 ID 토큰을 서버가 검증한다(클라이언트 비밀값 없음). 웹과 API는 같은 출처의 세션·CSRF를 쓴다. 이메일 미인증 계정은 거부하고 허용 목록은 없다.
- 근거: 이력 49절 2·3 · FR-A01 · NFR-05

### 이용약관 동의 후 가입
동의 기록이 없으면 이용약관에 체크하고 '가입하기'를 눌러야 계정을 만든다. 처리방침은 고지이고, 약관·처리방침 시행일과 동의 시각은 서버가 정해 기록한다. 만 14세 이상은 안내로만 알린다. 가입 대기는 10분짜리 서명 쿠키에 둔다.
- 이유: 동의하지 않은 사람의 정보를 DB에 남기지 않는다. 회원 서비스는 계약 이행이라 처리방침은 고지로 충분하다.
- 근거: 이력 68절 · FR-A01 · `users`

### 분석은 확장 연결이 있는 사용자만
분석 API는 확장 토큰(Bearer)으로만 인증하고 그 밖에는 `AUTH:LOGIN_REQUIRED`(401)다.
- 이유: 사용량 한도와 기록을 사용자에 묶는다.
- 근거: 이력 49절 1 · FR-A01

### 확장 토큰과 로그아웃
웹 세션이 발급하고 DB에는 해시만 둔다. 마지막 사용 날짜부터 90일째 날까지 쓰고 재발급은 없다. 확장 로그아웃은 그 토큰만, 웹 로그아웃은 그 세션이 발급한 토큰을 폐기한다. 같은 세션에 다른 사용자(또는 동의 전 계정)가 로그인하면 이전 토큰을 폐기한다.
- 근거: 이력 49절 4~8·11 · 68절 7 · `extension_token`

### 탈퇴
계정과 개인 기록(내 일본어 항목·예문, 지정한 이름, 확장 토큰, 사용 기록)을 지우고 공용 분석은 남긴다. 그날 사용 기록만 `withdrawn_key`로 자정까지 남겨 같은 날 다시 가입해도 한도가 이어진다.
- 근거: 이력 68절 1 · FR-A01 · FR-M02 · `accounts/withdrawal.py`

- 보류: 약관 변경 시 재동의, 마케팅 수신 동의, 연결 목록·모든 기기 해제 화면.

## 사이드 패널 동작

### 시작
우클릭 메뉴 "Dragram으로 분석"으로 시작하고 그 탭에만 주입한다(`activeTab`). 주입할 수 없으면 고른 글자를 한 문장으로 분석한다.
- 이유: 모든 사이트 권한을 안 받는다.
- 근거: 이력 28절 10·15 · 29절 7 · 31절 14
- 보류: 드래그만으로 자동 분석, 선택 위 버튼.

### 여러 문장과 회차
드래그한 문장을 모두 분석해 문장별 페이지(1 / N)로 보인다. 새 회차가 오면 이전 회차의 늦은 응답·보내지 않은 요청은 버리고, 같은 문장은 한 번만 요청한다.
- 근거: 이력 31절 11·15 · FR-A10

### 확인 중과 재분석 중
판별할 구간은 '확인 중' 카드로 먼저 보이고(후보가 하나면 그 용법 내용을 채움), stale 분석은 옛 결과에 문장 단위 '재분석 중'을 달아 보인다. 재분석 중에는 중간 이벤트를 반영하지 않고 `analysis`가 오면 한 번에 바꾼다.
- 이유: 옛 결과가 스켈레톤으로 깜빡이지 않게 한다.
- 근거: 이력 37·38절 · 60절 1 · FR-A07 · FR-A10

### 실패와 다시 시도
번역 전 실패는 확정 문법만, 번역 뒤 실패는 번역을 남기고, 재분석 실패는 옛 결과를 남긴다. 모든 실패 문구 옆의 `다시 시도`는 그 문장만 비우고 처음부터 요청한다. 자동 재시도·횟수 제한은 없고 한도 오류에도 버튼을 둔다.
- 이유: 누를 때만 비용이 들고 한도로 막는다.
- 근거: 이력 31절 22 · 36절 6 · 37절 5 · 38절 5 · 39절 · 52절 6

### 도움말
헤더 `?` 버튼으로 각 화면 요소의 설명을 연다. 예시는 실제 패널 컴포넌트를 고정 예시 데이터로 그리고, 예시의 버튼을 눌러도 내 일본어·이름은 바뀌지 않는다. 처음 로그인한 뒤 빈 패널에서 한 번 저절로 열린다.
- 이유: 설명 그림과 실제 화면이 어긋나지 않게 한다.
- 근거: FR-A33 · DESIGN 도움말 · #365

### 로그인 안내
토큰이 없거나 401이면 로그인 안내를 보이고 웹 `/connect`를 연다. 연결되면 기다리던 문장을 다시 분석한다.
- 근거: 이력 49절 7·9

### 루비, 드래그 표시 없음
원문 한자에 SudachiPy 읽기로 루비를 단다(저장 안 함, 기본 켜짐, 끈 값을 기억). 드래그 핸들·'드래그한 부분'·겹친 카드 앞으로 올리기는 없애고, 문법은 한 색 형광펜으로 보인다.
- 이유: 드래그 표시가 원문 읽기를 방해했고 색에 뜻이 없었다(#354, PR #357).
- 근거: 이력 28절 14 · 31절 16~19 · FR-A10

- 보류: 오류 종류별 문구(DESIGN §7), 일괄 다시 시도.

## 화면 용어·표시 원칙

### 화면 문구
화면에는 '내 일본어', 'AI 생성·미검수', '회화체', '다른 해석: …', '판단하지 못함', '재분석 중', '예외 1그룹'을 쓰고, 확정은 배지 없이 보인다. 대상 문법 없음은 문법 칸을 숨기지 않고 '문법 요소 없음' 한 줄로 보인다.
- 이유: 실패·미확정과 정상 결과를 구분하고, 미검수가 검수처럼 보이지 않게 한다.
- 근거: 이력 22·38·48절 · DESIGN §5·§6

### 검수 배지는 두 가지
LLM이 만든 지식(용법, 패턴, LLM 뜻)은 'AI 생성·미검수', 사전(JMdict 뜻, KANJIDIC2 훈음)을 근거로 옮긴 검수 전 한국어 뜻은 'AI 번역'이다. 검수된 사전 뜻과 승인된 LLM 뜻에는 배지가 없고, 영어 뜻은 보이지 않는다. 뜻이 아직 없으면 '뜻을 준비하는 중', 생성 실패면 '뜻을 만들지 못했습니다'다.
- 이유: 사전 근거가 있는 번역과 근거 없는 생성을 구분해 보인다.
- 근거: 이력 6·31·50절 · DESIGN §5·§6
- 보류: 뜻 자리 두 문구는 초안이다

## 내 일본어

### 직접 추가한 용법·단어 뜻
내 일본어는 사용자가 사이드 패널 문법·단어 카드에서 직접 추가한 용법·단어 뜻이고, `my_item`에 ID와 상태만 둔다. 분석한 문장 원문은 저장하지 않는다. 분석 응답은 `usage_id`와 뜻 `id`를 실어 패널이 이 ID로 추가·숨긴다.
- 이유: 읽은 글 전부를 서버에 쌓는 저작권·개인정보 부담이 크고, 원하지 않는 항목까지 섞였다.
- 근거: 이력 14·22절 · ADR 0006(ADR 0002 대체) · FR-M10 · `my_item`

### 추가·제외와 숨김·복원은 따로
추가(내 일본어)와 숨김(패널 표시)을 따로 켜고 끄며, 둘 다 꺼지면 행을 지운다. 제외만 예문을 지우고, 복원은 숨김만 풀어 추가와 예문을 남긴다. 추가 없이 숨기기만 한 항목은 웹에 보이지 않는다.
- 이유: 보기 싫어 가리는 일과 배울 대상으로 담는 일은 다르다(#362).
- 근거: ADR 0006 · FR-M10 · `my_item` · DESIGN §4

### 예문은 고른 문장만
카드를 추가한 뒤 사용자가 고른 문장만 원문과 카드 위치로 `my_example`에 둔다. 번역·출처는 저장하지 않는다. 본인만 보고, 항목을 제외하면 함께 지운다.
- 이유: 저장하는 원문을 고른 몇 문장으로 줄이면서 카드 예문을 지킨다.
- 근거: 이력 24·26절 · ADR 0006 · `my_example`

### 병합·반려 때 항목 승계
용법을 합치면 항목과 예문을 합친 용법으로 옮긴다. 추가는 어느 쪽이라도 추가면 추가, 숨김은 양쪽 모두 숨겼을 때만이다. 반려된 용법·뜻의 항목은 웹에 내용 없이 예문만 보낸다.
- 이유: 반려돼도 사용자가 자기 원문을 지울 수 있어야 한다.
- 근거: ADR 0006 · `my_item`

### 구성 문법과 숨김
바깥 문법을 숨기면 그 안의 구성 문법도 숨는다. 구성 문법 하위 박스에서도 추가·제외·예문 저장·숨김을 하고, 하위 박스에서 숨기면 그 박스만 빠진다. 숨긴 문법은 형광펜·탭 개수에서 빠진다.
- 근거: FR-M10 · DESIGN §4

### 보류 (내 일본어)
- 태그 필터(FR-M10)
- 더 쓰지 않는 `user_sentence` 테이블을 없앨지(ADR 0006)

## 학습 카드

### 카드 단위
문법 카드는 용법당 한 장(회화체 패턴은 원형 용법을 함께 써 같은 카드), 단어 카드는 뜻당 한 장이다. 활용 카드는 따로 두지 않고 단어 카드 뒷면에 동사 그룹 태그와 활용표를 보이며 활용형을 묻는다. 그룹별 복습은 태그 필터로 한다.
- 이유: 설명이 용법 하나에 하나라 카드도 겹치지 않고, 활용은 단어와 함께 익힌다.
- 근거: 이력 18·19·20·48절 · FR-M03 · FR-M04
- 보류: 태그 필터 '1그룹만'에 예외 1그룹을 넣을지(이력 48절)

### 카드는 내 일본어에서 등록
학습 카드의 등록과 예문은 내 일본어 항목과 예문을 바탕으로 정한다. 카드 테이블은 Phase 2에서 만든다.
- 근거: ADR 0006 · FR-M03 · requirements 8장
- 보류: 등록 흐름과 카드 테이블

### 자동 추가는 주 해석만
'드래그한 항목 자동으로 카드 추가'는 기본 꺼짐이고, 켜면 주 용법과 주 뜻만 넣는다. 대안 해석·미확정 구간, 한자, 고유명사는 넣지 않는다.
- 이유: 정해지지 않은 해석을 카드로 굳히지 않는다.
- 근거: 이력 21·23절 · FR-M12

### '이미 앎' 상태와 병합 승계
카드는 지우지 않고 '이미 앎' 상태로 바꾸며, 자동 추가는 이 상태를 건너뛴다. 이 상태와 복습 이력은 용법·단어 병합 때 승계하고, 이미 중복된 카드는 복습 이력을 보존해 합친다.
- 이유: 병합 뒤 이미 아는 항목이 다시 자동 추가되면 안 된다.
- 근거: 이력 19·21·23절 · FR-M13

### 반려되면 일시 정지
카드 내용은 공유 DB를 참조해 설명 수정이 반영된다. 용법이 반려되면 시스템이 카드를 일시 정지하고 알리며 복습 기록은 유지한다.
- 이유: 반려된 지식을 복습하게 하지 않되 학습 이력은 잃지 않는다.
- 근거: 이력 28절 · FR-M04 · DESIGN §6

## 보관·개인정보·법적

### 공용 테이블에 원문을 두지 않는다
공용 테이블에는 문장 해시·구간 위치·ID·번역만 둔다. 공용 번역은 드래그했을 때만 보인다. 삭제 요청은 작품 문장의 해시로 처리한다.
- 이유: 남은 법적 위험을 공용 번역 하나로 줄인다.
- 근거: 이력 2·9·24절 · NFR-13

### 분석 원문은 저장하지 않는다
원문은 분석하는 동안만 서버와 OpenAI를 거친다. 남는 개인 원문은 사용자가 고른 예문(`my_example`)뿐이고 번역·출처·드래그 범위는 두지 않는다. 옛 `user_sentence` 행은 지웠다.
- 이유: 읽은 글이 전부 쌓이는 저작권·개인정보 부담을 없앤다.
- 근거: ADR 0006 · `my_example`·`user_sentence`

### 개인 데이터는 본인만
`my_item`·`my_example`·`designated_name`은 본인 user_id로만 다루고 admin·로그·공용 테이블·LLM 요청에 넣지 않는다.
- 이유: 내가 고른 것은 나만, 남이 고른 것은 나한테 안 보인다.
- 근거: 이력 26절 · NFR-11 · ADR 0006

### 큐·로그에 원문을 남기지 않는다
큐 입력은 ID·분석 텍스트·버전 값뿐이고 결과·실패는 남기지 않는다(`result_ttl=0`). Redis 영속화는 끈다. 사용 기록·로그·작업자 소식에 원문을 넣지 않는다.
- 이유: 큐는 원문에 가까운 텍스트를 다뤄 끝나는 즉시 사라져야 한다.
- 근거: 이력 9·51·53절 · NFR-12 · `usage_log`

### 관리자도 원문을 보지 않는다
공용 분석·구간은 admin에 없다. 승인은 새로 쓴 예문으로, 매칭 정정은 평가 문장에서만 한다. `admin_action_log`는 아직 없고 정정만 `django_admin_log`에 남긴다.
- 이유: 원문이 관리 화면으로 새어 나갈 길을 막는다.
- 근거: 이력 28·35·57·70절 · NFR-11·NFR-13

### 보류: 보관 기간과 남은 칸
보관 기간·접근 범위, `user_sentence` 테이블 삭제, 출처 기록(FR-A22), 사용자별 기록 수·요청 속도 제한은 미정이다.
- 근거: 이력 9·71절 · NFR-12 · FR-A22
