# 설계 결정 기록

> 시간순 기록이다. **절끼리 충돌하면 뒤 절이 이긴다**(예: 0절의 시드·JLPT는 13절에서 삭제, 14절 회화체 복사는 18절 원형 참조로 대체, 26절 user_sentence.sentence_hash는 analysis_id로 대체).
> 최종 상태의 기준은 `requirements.md`와 `schema/`이다. 이 문서는 "왜 그렇게 정했나"를 찾을 때 본다.

## 0. 목적과 범위
- 본질: 사용자가 직접 고른 글(기술 문서, 뉴스, 게임, 소설 등)에서 필요한 일본어를 집중해서 배우게 하는 것. 웹소설 전용 아님.
- MVP 언어 범위: 표준어 + 회화체. 시드 = JLPT N5~N1 문법 + 기본 축약형(てる, ちゃう, とく, なきゃ, ちゃ, じゃない, って) + 경어 대표 패턴(お〜になる, お〜する, ご〜いたす, 〜させていただく) + 특별 경어 동사 10개 정도.
- 나중: 방언, 인터넷 말투, 신조어, 과장된 캐릭터 말투, 수동태 세분화(수동/가능/존경 등 れる 세분은 MVP 제외), 말투(register) 칸.
- 결과 표시: 크롬 사이드 패널. 드래그 → 문장 끝(마침표)까지 자동 확장, 사용자가 실제 드래그한 범위는 따로 강조 표시.
- 사전: SudachiPy core 사전, SplitMode C. full 사전 전환은 OOV 비율 + 실제 분할·품사 오류를 보고 결정.
- 관리자 도구: Django admin (ModelAdmin/템플릿 오버라이드로 UI 수정 가능).

## 1. 정규화 (해시 기준 텍스트, normalize_version으로 기록)
1. 루비(rt, rp) 제거 (화면에는 원래 페이지 루비 그대로)
2. 폭 통일만: 전각 영숫자→반각, 반각 가나→전각. NFKC 전체 적용 안 함(위첨자 x² 같은 호환 분해 금지)
3. 일본어 문자 사이 공백 제거, 영어 단어 사이는 공백 1개 유지
4. 물결표(~ 〜) 제거
5. 문장 전체를 감싼 바깥 괄호/따옴표만 제거
6. 의미를 바꾸는 기호(！ ？ … 등)만 남기고 나머지 기호 제거
7. 숫자: 아라비아 숫자(0~9, 폭 통일 후)만 ⟨N1⟩, ⟨N2⟩ 자리표시자로 치환. 한자 숫자(一二三…)는 절대 치환하지 않음(二枚目, 一人前, 七夕, 一石二鳥 등 관용 표현 보호)
8. 두 텍스트: 분석 텍스트(숫자 그대로, SudachiPy 입력) / 키 텍스트(자리표시자, 해시·LLM 입력·번역 저장·위치 기준)
9. 공용 캐시 저장 조건: LLM 번역 출력에 자리표시자가 빠짐없이 그대로 있을 때만. 실패 시 숫자 넣고 분석한 결과는 공용 캐시에 저장하지 않음
10. 정규화 규칙 변경 시 마이그레이션으로 해시 재계산

## 2. 저장과 캐시
- 공용 테이블에 원문 미저장. sentence_analysis는 UNIQUE(sentence_hash)만 (SHA-256, char(64)). normalized_text 칸 없음.
- 개인 원문은 user_sentence에 저장, UNIQUE(user_id, original_hash). sentence_hash는 공용 분석 참조용.
- 출처는 사용자별: user_sentence_source (UNIQUE(user_sentence_id, url_hash)), 10분 내 재방문은 last_seen_at만 갱신하고 새 출처 연결은 누락 없이.
- 위치: 키 텍스트 코드포인트 기준 반열린 구간 [start, end). 원문 매핑은 서버가 계산(JS는 UTF-16이라 서버가 변환해 내려줌). LLM은 서버가 부여한 후보 ID만 고르고 구간은 서버가 계산.
- 문장 분리: 인용부호(「」『』 등) 안의 마침표에서는 나누지 않는 규칙부터. ？！ 줄바꿈 포함 대표 사례로 확정.
- 문장 단독 분석(MVP는 문맥을 입력에 넣지 않음). 문맥에 따라 갈리면 '판별 불가' + 복수 해석 표시. 번역은 재사용하되 정정 시 재번역 경로 있음.

## 3. 최신성(stale)과 재분석
- 판 번호(revision)를 조회 시 비교: grammar_pattern.revision, grammar_usage.revision ↔ span_match.basis_revision / usage_revision.
- is_stale 플래그는 번호가 없는 사건용으로만.
- matcher_version(패턴 세트 버전)이 sentence_analysis 값보다 높으면 로컬 매칭만 다시 돌림(LLM 없음). 후보나 용법 revision·판별 규칙이 바뀐 구간은 전부 재검토, 판정은 입력이 완전히 같을 때만 재사용.
- 표시: stale-while-revalidate. 옛 결과를 '재분석 중' 표시와 함께 보여주고 SSE로 갱신.
- 관리자 정정(match_correction)이 우선. 이미 오답으로 아는 결과는 재분석 중에도 그대로 노출하지 않음. 정정 우선순위는 '활성 정정만', suspended 제외.

## 4. 동시성과 장애 복구
- 같은 문장 동시 요청: 조건부 UPDATE로 status=processing 선점 → 단일 실행.
- 결과 쓰기 시 세대 번호(generation) 비교, span 묶음은 트랜잭션으로 통째 교체.
- 선점 만료 시간(processing_started_at 기준) + DB의 미완료 작업을 큐에 다시 넣는 복구 경로. SSE 응답은 결과 버전 포함, 재접속 시 DB 현재 결과 재조회.
- 동시 요청 약 10개에서 시작, 테스트로 조정. 최대 입력량·재시도 횟수·전체 작업 시간 상한은 처음부터 둠.

## 5. 매칭과 판별
- pattern_morpheme: lemma(= SudachiPy normalized_form + 예외 매핑), pos1, pos2, conjugation_form. NULL = 아무거나.
- 활용형: 과거/조건(食べた 終止形 vs 食べたら 仮定形)처럼 필요한 패턴은 conjugation_form 필수. usage_closed 패턴은 활용형 조건 검토 필수, 등록 시 성공 예문 + 실패 예문 테스트를 통과해야 활성화.
- 판별 순서: 후보 0개 → '대상 문법 없음'(정상 결과) / usage_closed → 확정(승인된 것만) / usage_rule → 확정(승인된 것만) / 통계(off) / LLM 1차 호출이 ID 선택('해당 없음', '판별 불가' 허용).
- 신규 문법 발견 에이전트: 큐 + 일일 상한 + 모든 호출·재시도 기록으로만 실행. pending만 생성.
- 겹침: 화면 접기와 분석 제외를 분리. 긴 패턴이 이겨도 내부 후보는 보존. 구성 관계가 명시된 패턴만 중복 표시 생략.
- 고유명사: 원래 형태소·문법 후보는 보존, name_spans(type: person/place/org/work/other)로 주석만. 이름은 번역에 맡김. OOV 전문 용어는 word에 저장.

## 6. 단어
- 내부 word_id가 식별자. jmdict_seq는 선택적 연결 키(NULL 허용). 같은 표기에 여러 사전 항목·뜻 가능 → 선택된 뜻/미확정 상태 보관.
- 정규형은 조회 열쇠로만 사용.
- 뜻 검수 상태(meaning_status): 검수 없으면 'AI 번역' 표시. JMdict CC BY-SA 4.0 출처·라이선스 링크 표기.

## 7. 승인과 품질
- LLM이 문법 설명을 처음 1회 작성 → 관리자 검수. 공용 문법 설명은 재사용.
- pending도 화면에는 'AI 생성·미검수' 배지로 표시. 확정 판별의 근거(usage_closed, usage_rule)로는 승인된 것만.
- 그림자 모드: 자동 승인 기준으로 '승인했을 것'만 기록(would_auto_approve, 근거, 평가 시각), status는 pending 유지. 관리자 결정과 비교해 일치율이 충분하면(예: 95%) 실제 자동 승인을 따로 켬.
- 관리자 정정은 평가 후보로 사용.
- 평가: 고정 평가 세트 50문장부터(정상 / 문법 없음 / 동형이의 / 축약 / 인용 / 기술 문서 / 범위 밖). 지표: 구간 정확도, 용법 정확도, 판별 보류 비율, 문장당 호출 수·비용. LLM 신뢰도 수치를 정확도로 취급하지 않음.

## 8. LLM과 비용
- OpenAI만. structured outputs, 프롬프트 캐싱(고정 접두부 ≥1024토큰)은 cached_tokens로 효과 확인.
- 목표: 공용 캐시·문법 재사용으로 비용이 0에 수렴.
- 확장 문장(축약어 원문 복원 등) 기능은 제외.

## 9. 보관·법적
- 작업 큐 입력은 완료 즉시 삭제, usage_log에 원문 미저장, Redis 영속화 끔.
- 공용 번역 저장이 남은 법적 위험. 삭제 요청은 작품 문장 해시로 처리. 한국 저작권법 적용, 일본 측 CODA.
- 번역·작업 입력·로그·평가 자료의 보관 기간과 접근 범위를 정함. 평가 세트 편입은 직접 작성 문장·이용 가능 자료·동의 확보 자료만.

## 10. 써 보며 정할 것 (보류)
- 분석 트리거 기본값(자동/버튼), 루비 없는 한자 후리가나, 수치 임계값들, 애매한 히라가나 단어, 〜の 표시 방식, core→full 전환, 말투 칸.

## 11. 구현 순서 (Codex 제안, 합의)
1. 문장 경계·캐시 동일성·구간 위치 → 2. 개인 원문·출처, 문법·용법·단어 식별자, 승인 상태, 분석·작업 버전 → 3. 작은 시드로 매칭·용법 판별 → 4. 번역·모호성 판별과 작업 실행 → 5. 사이드 패널·정정·stale 갱신, 이후 시드 확대.
첫 구현에서 미룰 것: 숫자 템플릿의 범위 확장, 구간별 정교한 LLM 재사용, 무조건적인 신규 문법 에이전트 실행.

## 14. grill-with-docs 세션 결정 (2026-10-17 16:14~17:16) — 앞 절과 충돌하면 14절이 이긴다
- 분석 호출: 새 문장은 LLM 1회 호출(structured output)로 번역 + 애매한 용법 판별 + 미발견 구간의 새 문법 찾기를 함께 수행. 큐는 실패 재시도용. '에이전트'라는 말은 나중 일괄 작업(중복 패턴 합치기 등)용으로 보류.
- 미검수 재사용: 미검수(pending) 패턴이 걸리면 LLM 없이 재사용하고 '미검수' 표시. 용법이 여러 개인 미검수 패턴은 LLM이 고름. 결과 상태 용어: 확정(승인 지식으로 정함) / 재사용(미검수). usage_rule은 승인된 것만.
- 해석 갈림(기존 '판별 불가' 대체): 번역과 용법은 한 호출에서 같은 해석으로 정함. 문장만으로 갈리면 주 용법 + 대안 해석(대안 용법 ID + 짧은 대안 번역) 저장·표시. LLM이 근거 없이 대안을 내면 그 구간만 한 번 재질문. 관리자 용법 정정 시 그 문장 번역도 재번역 대상.
- 패턴 생성: LLM은 서버가 부여한 토큰 ID로 핵심 토큰만 고르고 토큰마다 'lemma 고정 / 활용형도 고정 / 아무거나' 표시. 처음·끝 토큰은 '아무거나' 불가. 생성한 패턴으로 원래 문장을 재매칭해 걸려야 저장, 그 문장은 성공 예문으로 test_cases에.
- で→て 조건부 규칙(코드 상수): 접속조사 で는 앞 토큰이 1그룹(五段) 동사의 음편형(撥音便·イ音便)일 때만 て로 봄. ないで 등은 で 유지(별개 패턴). 테스트: 読んでしまう(합쳐짐), 行かないで(안 합쳐짐). SudachiPy는 だ→た, でる→てる, じゃう→ちゃう, ちゃ→て를 이미 정규화함. しまう의 lemma는 仕舞う(표시 이름 별도 필요).
- 중복 방지: grammar_pattern.morpheme_key = 형태소 행(lemma|pos1|pos2|conj, 아무거나는 *)을 순서대로 이은 문자열의 SHA-256, UNIQUE. Django get_or_create로 동시 생성 처리(Redis·락 없음). 충돌로 기존 패턴을 받은 쪽은 자기 용법을 버리고 기존 용법 목록으로 재질문(작은 LLM 호출). 의미상 중복은 Django admin 패턴 합치기(span_match 참조 이전 포함).
- 회화체 패턴: ちゃう·てる·とく·なきゃ 등은 별도 패턴. 원형 패턴이 있으면 그 용법·설명을 복사해 새 행으로 저장, grammar_pattern.register(standard/colloquial)로 '회화체' 배지, 설명 첫 줄에 "「〜てしまう」의 회화체 축약형…" 표시. 원형이 아직 없으면 LLM이 새로 쓰고 나중에 관리자가 정리. 원본 추적 칸(copied_from)은 두지 않음.
- 동사 그룹 표시: 1그룹(5단) / 2그룹(1단) / 3그룹(する·くる). SudachiPy 活用型에서 계산, DB 칸 없음.

## 24. JMdict 적재·단어 생성 (2026-10-18 08:09) — 23절 이후 결정, 앞 절과 충돌 시 우선
- JMdict는 1회 전체 적재(Django 관리 명령) 후 끝. 원본 파일·원본 json 보관 안 함. 재적재 없음(갱신은 범위 밖, 운영 한계로 문서화). 기록은 판본 이름 한 줄(설정값) + 적재 직후 DB 백업. 파일 해시·적재 이력 테이블 없음.
- 역할: 문장 번역은 LLM이 문장으로 하며 JMdict를 근거로 쓰지 않음. JMdict는 단어 정보 표시, sense 후보 목록, meaning_ko(그 sense의 일반 뜻) 1회 생성 근거로만 사용.
- word 1행 = JMdict 항목 1개: jmdict_seq UNIQUE(사전에 없으면 NULL), dictionary_form·reading(대표 표시용), forms text[]·readings text[](GIN), is_common(ichi1/news1/spec1 등 흔한 단어, 후보 순서 힌트), reading_restrictions json(re_restr: 읽기→표기 제한), tags text[](단어 전체 태그 + 검색용 sense 태그 합집합).
- word_sense: tags text[](자/타동사·경어·uk 등 sense 단위, JMdict pos/misc 변환), pair_form(자타 대응 동사, word에서 이동), applies_to json(stagk/stagr: 이 뜻이 적용되는 표기·읽기), sense_origin(jmdict/llm), sense_status(이 뜻 자체의 검수 상태; meaning_source·meaning_status는 한국어 뜻의 출처·검수로 별개). LLM이 만든 뜻은 JMdict 단어 아래에 붙어도 sense 단위로 'AI 생성·미검수' 표시(미검수가 검수로 보이면 안 됨). LLM 뜻을 별도 단어로 떼지 않음(카드 쪼개짐 방지).
- 제한 정보는 LLM에 뜻 후보를 넘기기 전 후보 거르기와 표기에 맞는 읽기 표시에만 사용.
- 매칭: 비활용어는 표기+읽기, 활용어는 사전형 표기만(SudachiPy reading_form은 활용형 읽기: 食べ=タベ), 히라가나·가타카나 통일, 가나 표기 단어는 readings에서도 조회, 후보 여럿이면 문장 분석 LLM 호출에서 sense 고를 때 같이 고름(is_common 순서 힌트), 못 찾으면 정규형·표층형 재시도.
- 새 단어 생성(두 단계): 문장 분석 호출은 못 찾은 토큰의 사전형·읽기만 받음 → 서버가 그 값으로 DB 재조회 → 있으면 기존 sense 재사용 또는 그 항목 아래 pending sense 추가('맞는 뜻 없음' 허용) → 없을 때만 word_gloss 호출로 뜻·태그·한국어 뜻 생성 후 jmdict_seq NULL로 저장. 동시 생성 중복은 DB UNIQUE로 방지. 나중에 같은 항목으로 밝혀지면 표기만으로 자동 병합하지 않고 관리자 검수 병합(문장 분석·카드·제외 상태 참조 승계). 웹 검색 툴은 MVP 분석 흐름에 넣지 않음(관리자 검수 때 확인).
- 개인 원문(user_sentence)은 서버에 그대로 저장(현행 유지). 문제가 생기면 그때 브라우저 저장 등으로 변경. 공용 번역 저장도 유지(드래그 시에만 제공, 별도 열람 불가).
- 예문 카드: user_sentence의 개인 원문 + 공용 번역(자리표시자 복원) + user_sentence_source 출처로 구성. LLM 새 생성 불필요. 문장 기록 삭제 시 예문 처리(같이 삭제 vs 카드에 복사)는 Phase 2에서 결정.

## 25. Codex 최종 확인 (2026-10-18 08:21) — "치명 없음, 마감 가능"
- 사전에 없는 단어(jmdict_seq NULL)의 중복 방지: 부분 UNIQUE (dictionary_form, reading) WHERE jmdict_seq IS NULL. 두 값은 저장 전 정규화(가나 통일), NOT NULL·빈 문자열 금지. 대표 표기는 처음 저장값 고정(별도 중복 판정 칸 없음, 바꿀 일이 생기면 그때 추가). 충돌 시 기존 단어 재사용, 뜻은 별도 판단.
- 재조회로 기존 단어를 찾은 경우에도 이 문장의 sense는 아직 선택되지 않았으므로, word_gloss 호출에 문장과 기존 sense 후보를 넘겨 선택(맞는 뜻 없음이면 pending sense 추가). 진짜 새 단어면 같은 호출에서 뜻 생성. (24절 '없을 때만 word_gloss' 대체)
- 벡터 DB(pgvector)는 단어 조회에 쓰지 않음(정확 일치 조회라 일반 인덱스가 맞음). 나중에 중복 패턴·뜻의 병합 후보 추천용으로 검토.

## 26. 최종 마감 토론 반영 (2026-10-18 09:21) — Codex "치명 없음, 6가지 보완 후 마감"

3. usage_rule.pattern_id 추가(FK→grammar_pattern): 규칙은 실제 매칭된 패턴의 승인된 규칙만 적용(회화체가 원형 용법을 공유해도 규칙은 패턴별).

## 28. 첫 기능 단위와 문서 모순 정리 (2026-10-18) — 앞 절과 충돌 시 우선
grill-with-docs 세션에서 정했다.

**구간 판정 상태**
1. '해당 없음'과 '미발견'을 나눈다. 해당 없음은 패턴에는 걸렸지만 그 자리에 배울 문법이 없는 구간(이름 속 の 등)이라 새 문법을 찾지 않는다. 미발견은 배울 문법이 있는데 기존 후보로 설명되지 않는 구간이라 새 문법을 등록한다. 둘을 합치면 쓸모없는 pending 패턴과 LLM 호출이 생기고, 미발견 비율(NFR-08)이 부풀고, "조건이 너무 넓은 패턴"이라는 신호가 사라진다.
2. 확정과 미검수 표시는 구간에 저장하지 않는다. 구간에는 고른 용법만 저장하고(state `decided`), 화면에서는 볼 때마다 그 용법의 검수 상태로 확정(배지 없음) / 'AI 생성·미검수'를 정한다. 저장하면 승인·반려 때마다 그 용법을 쓰는 모든 구간을 고쳐야 하고, 하나라도 빠지면 미검수가 검수처럼 보인다. '재사용(미검수)' 용어는 없애고 '미검수'로 부른다(ADR 0003). 14절 `confirmed`/`reused`, 26-5절 "확정·재사용이면 usage_id 필수"를 대체한다.
3. '애매함'은 '판별 대상'으로 바꾼다. DB만으로 용법을 정하지 못해 LLM 판별을 기다리는 처리 단계라 저장하지 않는다. state enum `ambiguous`(해석 갈림)는 `divergent`로 바꿔 이름 겹침을 없앤다.
4. state enum: `decided` / `not_applicable` / `divergent` / `unfound` / `unresolved`.

**작업 실행**
5. 첫 분석, 재분석, 재시도의 LLM 작업은 모두 큐에 넣어 작업자가 처리한다. HTTP 요청은 DB로 정해진 결과를 바로 돌려주고, LLM 결과는 SSE로 받는다. 선점 만료·세대 번호·미완료 작업 재투입이 작업자 모델을 전제하기 때문이다. 14절 "큐는 실패 재시도용"을 대체한다.

**패턴 활성화와 승인**
6. LLM이 새 패턴을 등록할 때 원래 문장과 같은 구조의 새 예문을 함께 쓴다. 원래 문장 재매칭과 새 예문 매칭을 둘 다 통과하면 바로 활성화하고(`is_active`), 새 예문은 `example_ja`와 `test_cases`의 첫 '걸려야 함' 항목이 된다. test_cases 전부 통과(관리자가 '걸리면 안 됨' 예문을 채움)는 승인과 용법 완결의 조건으로 옮긴다. 자동 등록 시점에는 test_cases를 쓸 주체가 없어 기존 규칙으로는 pending 패턴이 영원히 활성화되지 않았다.
7. 관리자는 드래그 원문 없이 LLM이 새로 쓴 예문과 설명을 보고 승인한다(원문 비노출 불변식 유지). 원문을 못 봐서 승인이 막히는 일이 실제로 생기면 사용자 동의 기반 공개를 다시 검토한다.
8. `grammar_pattern.status`(pending / approved / rejected)를 추가한다. 원형에 연결된 회화체 패턴은 자기 용법이 없어 용법에서 미검수 여부를 유도할 수 없기 때문이다. 반려된 패턴은 매칭에서 빼고(`is_active=false`), 그 패턴을 쓰던 문장 분석은 stale, 관련 학습 카드는 일시 정지한다.

**정규화 위치**
9. 확장은 선택 범위를 문장 경계까지 넓히고 루비를 뺀 원문을 보낸다. 정규화(분석 텍스트, 키 텍스트, 해시)는 서버만 한다. 확장 버전마다 규칙이 갈리면 같은 문장의 해시가 달라지고, 원문 위치 매핑과 개인 원문 저장에 원문이 필요하며, 클라이언트가 공용 캐시 키를 정하면 안 되기 때문이다.

**첫 기능 단위 (테스트 단계)**
10. 확장(우클릭 메뉴 "Dragram으로 분석") → 사이드 패널 → 백엔드로 이어지는 수직 슬라이스. 로그인 없이 구현하되 로그인 없는 사용을 정식으로 허용하는 결정은 아니다. 개인 원문(user_sentence)은 저장하지 않는다.
11. 실제 LLM을 동기로 호출한다(큐·SSE는 본 구현에서). LLM은 서버가 매긴 토큰 ID로만 답하고 구간 위치는 서버가 계산한다. 모델은 환경변수 `OPENAI_MODEL`. 테스트에서는 가짜 클라이언트를 쓴다.
12. 캐시는 본 테이블 `sentence_analysis`로 검증한다(해시, 정규화 버전, 상태, 번역). LLM이 쓴 문법·단어 설명은 임시 jsonb 칼럼에 둔다. 자리표시자가 모두 남은 결과만 저장한다. 본 구현을 시작할 때 마이그레이션을 다시 만들고 로컬 DB를 초기화한다. JMdict는 본 구현 때 적재한다.
13. 한 번에 분석하는 문장은 테스트 단계 3개. 넘는 문장은 안내 없이 분석하지 않는다. 본 구현에서는 상한을 크게 둔다(값 미정).
14. 사이드 패널 루비: SudachiPy 읽기를 히라가나로 바꾸고 오쿠리가나를 떼어 한자 위에만 올린다(食べる → 食(た)べる). 나눌 수 없으면 단어 전체 위에 올린다. 기본 켜짐, 토글로 끈다. 첫 단위에서는 SudachiPy 추정 읽기를 그대로 쓴다.
15. 선택 위에 뜨는 버튼은 모든 사이트에 스크립트를 상주시켜야 해서(`<all_urls>` 권한) 미룬다. 나중에 옵션으로 검토하며, 페이지 버튼 클릭에서 사이드 패널을 열 수 있는지 먼저 확인한다.

## 29. PR #9 Codex 리뷰 반영 (2026-10-18) — 28절 보완
1. 확정은 고른 용법과 실제로 매칭된 패턴이 **모두** 승인됐을 때만이다. 28절 requirements 문구가 용법 상태만 언급해, 승인된 원형 용법을 쓰는 미검수 회화체 패턴이 확정으로 보일 수 있었다.
2. LLM이 쓴 새 예문(28절 6)이 원문을 베꼈으면 거부한다. 키 텍스트가 원문의 키 텍스트와 같거나, 원문 키 텍스트의 연속된 일부를 기준 길이 이상 그대로 포함하면 베낀 것으로 본다. 기준 길이는 설정값으로 두고 구현 때 실제 예문으로 정한다. 거부되면 한 번 다시 쓰게 하고, 그래도 베끼면 예문 없이 등록한다(활성화 안 됨). "같은 구조의 예문"을 요구해 원문 복사 위험이 커졌기 때문이다.
3. 반려된 패턴이나 용법으로 정해진 구간은 재분석을 기다리지 않고 조회할 때 바로 응답에서 뺀다. stale만 표시하면 재분석이 끝날 때까지 관리자가 틀렸다고 판정한 결과가 '재분석 중'으로 계속 보인다. 반려된 용법도 같은 규칙을 따른다(이전 requirements의 "stale로 다시 만든다"에 더함).
4. [PR #11 Codex 리뷰] 3을 보완한다. 반려된 용법도 반려된 패턴처럼 그 용법을 쓰던 문장 분석을 stale로 만든다. 용법의 판 번호는 의미 정의가 바뀔 때만 올라서, 반려만으로는 캐시가 그대로 재사용되고 번역이 갱신되지 않기 때문이다. 해석 갈림의 대안 용법도 조회할 때 하나씩 검사한다(미검수면 배지, 반려면 그 대안만 뺌). 예문 복사 검사(2)에 "원문 키 텍스트 전체를 포함하면 길이와 무관하게 거부"를 더한다. 원문이 기준 길이보다 짧으면 원문을 통째로 넣고 앞뒤에 말을 붙여도 통과했기 때문이다. 아주 짧은 원문은 예문 없이 등록돼 활성화되지 않을 수 있지만 원문 비노출을 우선한다.
5. [PR #11 Codex 2차 리뷰] FR-A10·NFR-06의 배지 대상에 "실제로 매칭된 패턴이 미검수인 구간"을 넣어 용어표(1)와 맞춘다. 주 용법이 반려된 분석의 번역은 재분석이 끝날 때까지 **숨기지 않고 경고를 붙여** 보여 준다. 번역이 사라지면 문장 전체를 이해할 수단이 없어져 불편이 크기 때문이다(문구는 DESIGN §7). 매칭 정정의 "오답은 재분석 중에도 그대로 노출하지 않는다"와 달리, 번역은 경고를 단 채로 보인다. 예문 재작성 호출은 `usage_log.purpose`에 전용 값 `example_rewrite`로 기록한다. 원문 복사가 얼마나 잦은지와 그 비용을 따로 보기 위해서다.
6. [PR #11 Codex 3차 리뷰] 패턴이 활성인 채 용법만 반려되면, 그 용법은 DB 판정(용법 완결, 판별 규칙)과 LLM 후보 목록에서 모두 뺀다. 빼지 않으면 재분석 때 LLM이 같은 반려 용법을 다시 고른다. 승인과 용법 완결에는 새로 쓴 '걸려야 함'·'걸리면 안 됨' 예문이 각각 하나 이상 있어야 하고, 빈 test_cases는 통과가 아니다(28절 6의 "관리자가 '걸리면 안 됨'을 채운다"를 조건으로 명시). 원문 복사로 예문 없이 등록된 패턴이 아무 예문 없이 승인되는 길을 막는다. 'AI 생성·미검수' 배지 대상은 pending으로 한정하고, rejected는 배지 없이 응답에서 뺀다(NFR-06, DESIGN §5).
7. [PR #11 Codex 4차 리뷰] FR-A12의 배지 대상도 pending으로 한정하고 반려된 용법은 보여주지 않는다(6과 맞춤). 용법을 반려하면 그 용법을 정정 후 용법으로 가리키는 활성 정정을 suspended로 바꾼다. 정정이 재분석보다 우선해서, 그대로 두면 반려된 용법이 다시 적용된 뒤 숨겨져 구간이 영영 복구되지 않는다. 반려가 취소돼 pending·approved로 돌아오면 그 패턴을 쓰던 문장 분석을 stale로 만든다(판 번호는 상태 변경으로 오르지 않아서, 이 규칙이 없으면 반려 동안 굳은 캐시가 되살아난 지식을 다시 보지 않는다). requirements의 기본 시나리오와 분석 흐름 1단계는 드래그만으로 자동 분석하는 것처럼 적혀 있어, 첫 단위는 우클릭 메뉴로 시작하고 자동 분석은 나중에 검토한다고 고친다(28절 10·15).
8. [PR #11 Codex 5차 리뷰] 반려·반려 취소 규칙을 문장으로 하나씩 덧붙이니 반대 방향과 옆 경우가 계속 빠졌다. 그래서 requirements '패턴 매칭 규칙'에 상태 전이표 하나로 묶는다. 영향 범위는 그 패턴과 그 패턴을 원형으로 가리키는 회화체 패턴의 분석이다(원형 용법을 쓰는 회화체 구간을 놓치지 않게). 반려 취소 때 활성화 근거를 다시 검증해 `is_active`를 되돌리고, 관리자가 보완한 '걸려야 함' 예문도 활성화 근거로 인정한다. 7의 "반려 시 정정을 suspended로 바꾼다"는 **대체**한다. 정정은 상태를 고쳐 쓰지 않고 적용할 때 정정 후 용법·패턴이 반려 상태인지 검사한다. 고쳐 쓰면 복구할 때 반려 때문에 멈춘 정정과 관리자가 멈춘 정정을 구분해야 하므로, ADR 0003처럼 조회·적용 시점에 판단한다.
9. [PR #11 Codex 6차 리뷰] 전이표를 보완한다. (1) 반려 취소를 패턴·용법 두 행으로 나누고, 용법은 자기와 소속 패턴이 모두 반려 상태가 아닐 때만 유효하다고 정한다. 한쪽만 복원했을 때 반려 상태인 다른 쪽까지 돌아오지 않게 하기 위해서다. (2) 반려·반려 취소 때 영향 범위 분석의 세대 번호를 올린다. stale만 표시하면 전환 전에 시작한 작업이 옛 후보로 결과를 저장하며 stale을 풀 수 있다. 기존 세대 번호 장치를 그대로 쓴다. (3) `is_active`가 바뀌면 패턴 세트 버전을 올린다. 비활성인 동안 분석된 문장에는 그 패턴의 구간이 없어, "그 패턴을 쓰던 분석" stale로는 찾을 수 없기 때문이다.
10. [PR #11 Codex 7차 리뷰] 현재 패턴 세트 버전을 둘 곳이 없었다. 한 행짜리 테이블 `pattern_set_version`을 두고, `is_active`를 바꾸는 트랜잭션 안에서 행을 잠가 1 올린다(재시작·다중 서버에서도 값 하나). 설정값이나 메모리 값은 재시작 때 사라지고, `max(matcher_version)` 같은 계산값은 증가를 원자적으로 보장하지 못한다. 전이표에 승인 취소(approved → pending)를 더해 stale·세대 번호 증가를 똑같이 적용한다. 승인 취소를 pending과 rejected 중 어디로 되돌릴지는 여전히 미결(requirements 8장)이며, rejected로 가면 반려 행을 따른다.
11. [PR #11 Codex 8차 리뷰] (1) 조회 규칙에 용법이 속한 패턴의 상태도 넣는다. 회화체 구간은 패턴 칸에 회화체 패턴, 용법 칸에 원형 용법을 저장해서, 원형 패턴만 반려되면 반려된 결과가 확정으로 보였다(불변식 위반). (2) 활성 패턴의 형태소 조건이 바뀌어도 패턴 세트 버전을 올린다. 새로 걸리는 캐시 문장은 판 번호 비교로 찾을 수 없다. (3) 버전이 올라 다시 매칭했을 때 판별 대상인 새 구간이 생기면 stale로 만들고 LLM 재판정을 큐에 넣는다. 일괄 재처리는 하지 않고 **그 문장을 조회할 때만** 한다(사용자 결정). 새 패턴이 등록될 때마다 버전이 올라서, 일괄로 하면 캐시가 늘수록 LLM 호출이 폭증하기 때문이다. 이전의 "로컬 매칭만(LLM 없음)" 문구를 대체한다.
12. [PR #11 Codex 9차 리뷰] 정정을 적용할 때도 조회 규칙(11-1)과 같은 세 가지를 본다: 정정 후 용법, 그 소속 패턴, 그 위치 구간의 실제 매칭 패턴. 회화체 구간은 용법의 소속 패턴이 원형이라, 회화체 패턴만 반려되면 앞의 두 가지로는 걸러지지 않았다.
13. [PR #11 Codex 10차 리뷰] FR-A10의 배지 조건도 조회 규칙(11-1)의 세 가지(고른 용법, 소속 패턴, 실제 매칭 패턴)로 맞춘다. 원형 패턴만 pending일 때 회화체 구간이 배지 없이 보일 수 있었다. 다시 매칭 후 새 판별 대상 구간을 판정하는 호출(11-3)은 `usage_log.purpose`에 전용 값 `rematch_judge`로 기록한다(29-5의 목적별 비용 집계 원칙).

## 30. 정규화에서 숫자의 뜻을 지키는 기호 (2026-10-19) — PR #20 Codex 리뷰
1. 6단계에서 숫자 사이의 기호(. : / 등)와 숫자 앞 부호(- +)는 지우지 않는다. 이 판정들에서 숫자는 한자 숫자도 포함한다(-三度, 五％, ￥五百, 三/五). 숫자 바로 뒤의 단위 기호(% ％ ‰ ° ℃)와 바로 앞의 통화 기호(¥ ￥ $ ＄ € £ ₩)도 남긴다. 지우면 50%가 50과 같은 키가 되어 백분율이라는 뜻이 사라진다. 기호는 목록으로 정해 둔다. 지우면 1.5倍가 15倍, -3度가 3度, 10:30이 1030이 된다. 그러면 첫 응답부터 숫자가 틀리고, 실제 15倍 등과 캐시 키도 같아진다. 남긴 기호는 자리표시자 사이에 그대로 있어(⟨N1⟩.⟨N2⟩倍) 번역에 되돌릴 수 있다.
2. 4단계에서 숫자 범위를 잇는 물결표는 남긴다. 바로 뒤가 숫자(한자 숫자 포함)이고, 앞 3글자 안에 숫자가 있으면 범위로 본다(3〜5人, 3人〜5人, 10時〜12時, 三〜五人). 그보다 멀면 늘인 말투(そうだね〜)로 보고 지운다. 3글자는 조수사(人, 時)를 넘기 위한 값이다. 늘인 말투의 물결표를 드물게 남기는 손해(캐시 키가 갈라짐)가 범위를 잃는 손해(번역이 틀림)보다 작다고 봤다(사용자 결정). 〜5人처럼 앞에 숫자가 없는 경우는 범위로 보지 않는다.
3. 번역에 숫자를 되돌릴 때, 숫자 바로 뒤의 조사를 숫자 발음에 맞춘다. 1は와 2は는 같은 ⟨N1⟩は로 번역을 함께 쓰는데, LLM이 고른 조사(⟨N1⟩는)는 둘 중 하나에서 틀린다(1는). 숫자는 한자어로 읽는다고 보고 끝소리(일, 이, 십, 만 …)를 계산한다. 고유어 읽기(두 개 등)는 조수사가 붙어 조사가 숫자에 바로 붙지 않으므로 다루지 않는다. 한국어 글자만으로는 조사와 소리가 같은 명사(제2과의 과=課)를 가를 수 없어, 원문에서 숫자 바로 뒤 형태소가 조사(助詞)일 때만 교정한다. 그래서 캐시를 재사용할 때도 형태소 분석을 한다. 받침 정보를 캐시 키에 넣는 방법은 캐시 재사용이 줄고 LLM이 조사를 맞게 골라야 하는 문제가 그대로라 고르지 않았다(사용자 결정).
4. 부호와 통화 기호가 겹친 금액(-¥500, ¥-500)은 부호나 통화 기호 하나가 지워진다. 사용자가 읽는 글에서는 드물고(일본어 회계 표기는 ▲500円, マイナス500円), 기호 묶음 판정은 경계 사례가 끝없이 늘어나 알려진 한계로 둔다(사용자 결정).
5. 숫자 사이 기호의 뜻은 숫자값에 따라 갈린다(10:30은 시각, 1:2는 비율, 10/18은 날짜, 1/2는 분수). 그런데 키는 ⟨N1⟩:⟨N2⟩로 같다. 먼저 저장된 번역이 표기를 말로 풀면(⟨N1⟩시 ⟨N2⟩분), 나중 문장이 틀린다. 키를 나누지 않고, LLM 지침에 숫자 표기(⟨N1⟩:⟨N2⟩, ⟨N1⟩/⟨N2⟩, ⟨N1⟩.⟨N2⟩)를 원문 모양 그대로 두라고 적는다. 번역은 조금 덜 자연스러워지지만 어느 해석에도 틀리지 않고, 캐시 재사용도 유지된다. 이런 문장을 공용 캐시에서 빼는 방법은 시각·날짜 문장이 흔해 LLM 호출이 늘어서 고르지 않았다(사용자 결정). 지침은 가짜 LLM으로 확인할 수 없어 실제 모델의 동작은 따로 본다.

## 31. 첫 기능 단위 구현 중 결정 (2026-10-19~20) — #13~#18·#27 PR 리뷰와 논의, 앞 절과 충돌 시 우선
테스트 단계(28절 10~15)를 구현하며 정했다. 출처는 각 항목 끝의 PR·이슈다.

**LLM 응답 검증 (테스트 단계, 임시 칼럼)**
1. 임시 jsonb 칼럼은 `draft_analysis = {grammar, words}` 하나로 둔다(28절 12 보완). 위치는 키 텍스트 코드포인트 기준이다. NULL인 행은 다시 분석하고, 채울 때는 NULL일 때만 조건부로 갱신한다(동시에 채운 다른 요청의 값을 덮어쓰지 않게). (#15)
2. LLM이 쓴 글(문법 이름·설명, 단어 사전형·읽기·뜻)이 문장 전체(키 텍스트)를 인용하면 거부하고 저장하지 않는다. 이 글들은 공용 테이블에 들어가기 때문이다. 양쪽에서 문장부호·기호·공백·형식 문자(유니코드 P·S·Z·C)를 지운 뒤 포함 여부로 본다. 형태소 사이에 공백·가운데점·보이지 않는 문자를 끼워(私・は・学生) 피하는 것을 막기 위해서다. 기호·공백을 뺀 형태소가 하나뿐인 문장(です, 行く！)은 예외다. 그 토큰을 인용하는 것과 같고, 단어 하나는 사전 표제어 수준의 공용 정보다. 기호를 지워 키가 비면 모든 글에 "포함"되므로 인용으로 보지 않는다. LLM 지침에서 인용은 그 문법 토큰으로 한정한다. (PR #21, #24)
3. LLM이 쓴 글의 숫자 자리표시자는 응답할 때 번역과 같은 규칙(30절 3의 조사 교정 포함)으로 이 원문의 숫자로 되돌린다. 없는 번호의 자리표시자는 거부한다. (PR #21)
4. 단어 읽기는 가나(히라가나·가타카나, 장음 ー, 반복 부호)로만 받고 가나가 한 글자 이상 있어야 한다. 자리표시자도 받지 않는다. 외래어(사전에 없는 새 말 포함)는 가타카나 그대로 두고 히라가나로 바꾸지 않는다. 강조하려고 가타카나로 쓴 말은 본래 표기로 쓴다(ヤバい → やばい / やばい). (PR #24, #26)
5. 단어로 고르면 안 되는 토큰을 고른 항목은 실패 대신 그 항목만 빼고 저장한다. 숫자열과 겹치는 토큰, 품사가 補助記号·空白·助詞·助動詞인 토큰, 같은 토큰을 다시 고른 항목이 여기에 해당한다. 지침을 어긴 단어 하나 때문에 번역·문법까지 버리면 같은 문장마다 LLM을 다시 불러야 하기 때문이다. 숫자열과 겹치는 토큰을 빼는 것은, 사전형에 숫자를 지어내면 숫자만 다른 문장에 잘못 재사용되기 때문이다. %·℃·‰는 SudachiPy가 명사로 분석해 단어로 보일 수 있지만 단위 이름이라 허용한다. (PR #24, #26)
6. 형태소 하나로 된 문장에서 단어 사전형이 문장과 같아도 원문 인용으로 보지 않는다(2의 예외와 같은 이유). (PR #24)
7. 테스트 단계의 단어 뜻은 JMdict 없이 LLM이 만들므로 'AI 번역'이 아니라 'AI 생성·미검수'로 표시한다. 'AI 번역'은 사전(JMdict 단어 뜻, KANJIDIC2 한자 훈음)을 근거로 옮긴 한국어 뜻이 아직 검수되지 않았을 때만 쓴다(FR-A10, FR-A17, DESIGN §5와 맞춤). (PR #24)

**형태소와 위치**
8. 형태소가 숫자열 가운데에서 나뉘면(X12 → X1 / 2) 뒤 토큰의 구간은 숫자열의 시작(자리표시자)으로 당겨 숫자열 전체를 덮는다. 키 텍스트 구간을 분석 텍스트로 되돌릴 때도 자리표시자를 덮는 구간은 숫자열 전체를 덮는다. (PR #21)
9. SudachiPy가 입력을 바꿔(… → ...) 덧붙이는 길이 0인 형태소는 원문에 대응하는 글자가 없어 토큰에서 뺀다. (PR #26)

**API 오류**
10. API 오류는 `BusinessError` 하나로 던지고 DRF 핸들러 하나가 응답한다. 코드는 `도메인:이름`(`ANALYSIS:FAILED` 502, `ANALYSIS:TEXT_REQUIRED` 400)이고, 응답에는 사용자 문구를 넣지 않는다(화면 문구는 클라이언트가 코드로 정한다). 사유는 로그에만 남긴다. 외부 라이브러리(SudachiPy, OpenAI 등)의 예외만 바꾸고, 우리 코드의 버그는 500으로 드러낸다. (PR #22)

**문장 넓히기와 여러 문장 (28절 13 변경)**
11. 선택 범위는 。！？, 블록 경계, 줄바꿈(`<br>`, `white-space: pre` 계열의 화면에 보이는 개행)까지 양쪽으로 넓힌다. 글자 수 상한은 두지 않고, 서버 쪽 문장 길이 상한도 두지 않는다. 한 번에 분석하는 문장 수 상한도 없앤다. 드래그한 문장을 모두 바로 분석하고 문장별 페이지(1 / N, 이전·다음)로 보인다. 비용은 문장 수·길이가 아니라 사용자별 토큰 사용량으로 제한한다(#28, 사용자 결정). #28 전에는 서버 쪽 비용 안전장치가 없으므로(분석 API는 로그인 없이 열려 있고, 패널의 동시 요청 제한은 API를 직접 부르면 피할 수 있다), #28을 넣기 전에는 분석 API를 외부에 공개하지 않는다(사용자 결정, PR #34 리뷰). 그 전까지는 사이드 패널이 서버에 동시에 5개까지만 요청한다(패널 전체가 한도를 공유하고, 이전 회차의 진행 중 요청도 센다). (#16)
12. 문장 첫머리에서 열린 인용(대사)은 。」 뒤에서 문장을 끝내고, 문장 가운데에서 열린 인용은 안의 마침표에서 나누지 않는다(「行く。」次だ。 → 둘, 彼は「行く。」と言った。 → 하나). ！？처럼 이어진 끝 부호와 바로 뒤의 닫는 괄호는 앞 문장에 붙인다. 겹친 괄호는 묶음째 건너뛰고 앞 글자를 본다. (PR #29)
13. 화면에 보이지 않는 글자(rt·rp·script·style, `display: none`, `visibility`가 visible이 아닌 글자)는 문장에서 뺀다. 정규화는 하지 않는다(28절 9). (PR #29)
14. 주입할 수 없는 페이지(크롬 내부 페이지, 크롬 내장 PDF 뷰어 등)이거나 문장을 찾지 못하면 고른 글자를 문장 하나로 분석한다(문장 넓히기 없음). PDF 전용 지원이 범위 밖이라는 것과는 별개다. 모든 사이트 권한(`<all_urls>`)은 받지 않고, 메뉴를 누른 탭에만 주입한다(`activeTab`). (PR #29)
15. 새 회차가 오면 이전 회차의 늦은 응답과 아직 보내지 않은 요청은 버린다. 같은 회차에서 같은 문장은 한 번만 분석하고 결과를 함께 쓴다. 같은 창에서 연달아 분석하면 가장 최근 선택의 추출 결과만 넘긴다. (PR #29)

**드래그 범위 표시**
16. 원문에는 실제로 드래그한 범위의 시작·끝 자리에 핸들만 끼워 넣는다. 범위를 감싸 형광펜을 경계에서 쪼개면 조각마다 여백과 모서리가 생기기 때문이다. 핸들이 루비 단어 안에 걸리면 단어 바깥(시작은 앞, 끝은 뒤)에 붙인다. 테스트 단계에서 드래그 범위는 화면에서만 쓰고 서버에 보내지 않는다(개인 문장을 저장하지 않으므로). 본 구현에서는 개인 문장 저장에만 보내고 공용 분석에는 넣지 않는다(schema `user_sentence.selected_start`·`selected_end`). (PR #30, #31)
17. 드래그 범위와 겹친 문법 카드와 단어 행을 맨 위에 두고 선택 링과 "드래그한 부분"을 붙인다. 나머지는 원문 순서다. 단어 행은 사용자 요청으로 더했다. 범위 끝에 닿기만 한 항목은 겹친 것으로 보지 않는다(반열린 구간). 칩 색은 카드 순서가 아니라 원문 순서로 매겨 형광펜과 맞춘다. (PR #30)
18. 원문의 드래그 핸들은 "드래그 표시" 버튼으로 켜고 끈다. 처음엔 켜져 있고 고른 값을 기억한다. 꺼도 카드의 "드래그한 부분" 표시와 순서는 그대로다. 드래그가 의미 단위로 딱 떨어진다는 보장이 없어 사람에 따라 읽기에 방해가 되기 때문이다(사용자 요청). (PR #30)

**루비 (28절 14 보완)**
19. 루비는 요청마다 SudachiPy 읽기로 계산해 응답에 싣고 저장하지 않는다(LLM을 거치지 않음). 앞뒤에서 같은 가나만 떼고 가운데 가나는 함께 덮는다(取り扱い → 取り扱 / とりあつか). 한자는 CJK 통합 한자(확장 포함)·호환 한자와 〇로 판정한다. 읽기가 가나가 아닌 말(사전에 없어 표기 그대로 나오는 말)에는 달지 않는다. 루비를 끈 값도 드래그 표시처럼 기억한다. (PR #31)

**분석 결과 스트리밍 (28절 11 변경)**
20. LLM 호출 한 번을 스트림으로 받아, 번역이 끝나면 검증해 먼저 보내고 문법·단어는 검증·저장한 뒤 이어 보낸다. 호출을 번역과 문법·단어로 나누지 않는다. 입력 비용이 두 배가 되고 번역과 문법 해석이 어긋날 수 있기 때문이다. 28절 11의 "SSE는 본 구현에서"를 앞당겼다. (#27)
21. 응답은 줄 단위 JSON(`application/x-ndjson`, 한 줄에 이벤트 하나)이다. `translation`(번역, 루비) → `analysis`(번역, 문법, 단어) 순서이고, `analysis`에는 저장된 번역을 함께 싣는다(동시 요청이 먼저 저장한 결과를 쓸 수 있어서). 분석은 POST라 GET만 되는 EventSource를 쓸 수 없어 SSE 형식의 이점이 없다. 서버는 동기 WSGI 그대로다. 캐시를 재사용하는 문장은 두 이벤트를 한 번에 보낸다. (PR #32)
22. 번역을 보내기 전의 실패는 아직 응답을 시작하지 않았으므로 다른 API 오류처럼 상태 코드(502 등)로 알린다. 번역을 보낸 뒤의 실패만 상태 코드를 바꿀 수 없어 `error` 이벤트로 알린다. 이때 사이드 패널은 번역을 그대로 두고 "문법·단어를 분석하지 못했습니다"를 보이며, 서버는 저장하지 않는다(다음 요청에서 다시 분석). 번역만 저장해도 `draft_analysis`가 NULL이면 다시 분석하므로 얻는 것이 없다. 스트림이 끊겨도 받은 번역은 남긴다. (PR #32)
23. 조각이 계속 오면 조각 사이 대기 상한(30초)에 걸리지 않으므로 스트림 전체에 60초 상한을 둔다. 상한은 조각을 받을 때 검사하므로, 60초 직전에 조각이 온 뒤 멈추면 조각 사이 대기까지 최악 약 90초가 걸린다. 운영 Gunicorn 작업자 타임아웃은 이보다 길게(120초) 둔다. 기본 30초면 응답 도중에 sync 작업자가 죽는다. (PR #32)

**문법 설명의 단위 (사용자 결정, 2026-10-20)**
24. 문법·용법 설명에 문장을 기준으로 한 해설은 넣지 않는다. 설명은 용법마다 하나이고 모든 문장이 함께 쓴다. 같은 글자라도 용법이 다르면 따로 둔다(수식의 の / 명사화의 の). 테스트 단계의 문장별 설명(`draft_analysis`)은 같은 용법이 문장마다 중복 저장되고, 문장 내용을 풀어 쓴 해설이 공용 테이블에 쌓이며, 새 문장마다 LLM이 설명을 다시 써서 출력 토큰 비용이 든다. 그래서 LLM 지침만 바꾸는 중간 단계 없이 본 설계의 패턴·용법 구조(`grammar_pattern` / `grammar_usage` / `span_match`)로 바로 옮긴다. 설명을 용법 단위로 다시 쓰면 이미 등록된 용법에서는 LLM이 설명을 쓰지 않아 비용이 준다. 함께 검토한 중간안(LLM이 정한 용법 이름으로 묶는 임시 용법 테이블)은 고르지 않았다. 검토 때 든 이유는 LLM이 같은 용법을 매번 다른 이름으로 불러 묶이기 어렵고, 본 구현의 형태소 패턴 매칭으로 바뀌면 버리게 된다는 점이다. (#33)

## 32. 문법을 패턴·용법 구조로 옮기며 정한 결정 (2026-10-20) — #35, PR #42, 앞 절과 충돌 시 우선
#35에서 31절 24를 구현하며 정했다. 패턴·용법·구간 매칭의 기본 경로(등록과 매칭 재사용)만 다루고, 탁음화 규칙·재질문(#36), 예문 일부 복사 검사(#37), 승인·반려(#38)는 하위 티켓에서 한다.

1. 새 구문 제안의 토큰은 문법의 처음부터 끝까지 빠짐없이 차례로 나열하고, 토큰마다 `lemma`(lemma 고정) / `form`(활용형도 고정) / `any`(아무거나)로 표시한다. 빈틈이 있거나 순서가 거꾸로면 그 제안은 등록하지 않는다. 핵심 토큰만 고르고 사이를 서버가 '아무거나'로 채우는 방법보다 검증이 단순하다(사용자 결정).
2. 새 패턴·용법의 이름·설명에는 숫자 자리표시자(⟨N1⟩)를 받지 않는다. 있으면 응답 검증 실패다. 용법은 모든 문장이 함께 쓰므로, 31절 3처럼 이 문장의 숫자로 되돌리면 다른 문장에서 틀린 숫자가 보인다. 31절 3은 단어 글(사전형·읽기·뜻)에만 남는다(사용자 결정). 칸 길이(255자)를 넘는 이름도 검증 실패로 처리한다. 그대로 두면 DB 오류로 스트림이 error 이벤트 없이 끊긴다(PR #42 리뷰).
3. LLM에 주는 판별 대상 구간에는 서버가 매긴 구간 ID, 토큰 범위, 후보 ID와 그 용법의 이름·설명을 넣는다. 이름만 주면 입력은 줄지만 같은 패턴의 용법을 구별하기 어렵다. 요구사항은 정확도를 입력 토큰보다 우선한다(사용자 결정).
4. 숫자와 겹치는 토큰은 lemma·활용형으로 고정할 수 없다. 고정한 제안은 등록하지 않는다. 형태소 분석은 숫자가 그대로인 분석 텍스트로 하므로 lemma가 원문 숫자가 된다. 그러면 공용 패턴에 원문 숫자가 들어가고, 숫자만 달라 키 텍스트가 같은 문장에는 걸리지 않는다(사용자 결정).
5. 기호·공백을 뺀 형태소가 하나뿐인 원문(です 등)은, 예문이 원문 키 텍스트를 포함해도 베낀 것으로 보지 않는다. 그 패턴의 예문은 그 토큰을 쓸 수밖에 없다. 31절 2의 원문 인용 예외와 같은 이유다(사용자 결정). 다만 예문의 키 텍스트가 원문과 같으면(기호·공백을 지우고 비교) 형태소 수와 상관없이 거부한다. 원문 그대로인 예문은 새로 쓴 문장이 아니어서 공용 예문에 넣을 수 없다(PR #45 리뷰).
6. 임시 칼럼 `draft_analysis`는 `{words}`만 담는다(31절 1 보완). 문법은 `span_match`에 키 텍스트 위치와 패턴·용법 ID로만 저장한다. `grammar`가 든 기존 행은 마이그레이션에서 NULL로 만들어 다시 분석한다. 문장마다 쓴 설명은 패턴·용법으로 옮길 수 없기 때문이다.
7. 새 테이블은 #35에서 쓰는 칼럼만 만들고, 나머지 칼럼은 그 칼럼을 쓰는 하위 티켓에서 일반 마이그레이션으로 더한다. 전체 초기화는 하지 않는다(28절 12의 "본 구현을 시작할 때 마이그레이션을 다시 만들고 로컬 DB를 초기화한다"를 대체, 사용자 결정 2026-10-20).
8. 분석 행, 구간 매칭, 새 패턴·용법을 한 트랜잭션에 저장한다. 다른 요청이 먼저 저장한 문장이면 이번 결과의 구간·패턴은 저장하지 않는다. 새 패턴은 `morpheme_key` 순서로 등록하고, 패턴 세트 버전 행은 등록을 마친 뒤 마지막에 잠가 올린다. 동시 요청이 패턴을 서로 다른 순서로 등록하거나, 버전 행을 잠근 채 다른 패턴을 기다리면 교착이 나기 때문이다(PR #42 리뷰).

**미정**(requirements 8장)
- LLM 응답 실패 범위. 지금 구현은 형식이 틀린 응답(후보에 없는 ID, 범위 밖 토큰 ID, 구간 답 누락·중복 등)이면 문장 전체를 실패로 하고, 패턴 생성 규칙만 어긴 새 구문은 그 제안만 빼고 미발견으로 남긴다.
- 한 요청에서 패턴 여러 개가 활성화될 때 버전을 얼마나 올릴지. 지금 구현은 1이다.

## 33. 패턴 매칭 세부 (2026-10-21) — #36, PR #46, 앞 절과 충돌 시 우선
#36에서 탁음화 규칙, 같은 형태소 조건의 재질문, 기존 패턴에 새 용법 더하기를 구현하며 정했다. 모두 사용자 결정이다(#47).

**탁음화**
1. 앞 토큰이 동사이고 활용형이 `連用形-撥音便`·`連用形-イ音便`이면, 뒤 기능어(조사·조동사)의 lemma를 청음형으로 본다(で→て, でる→てる, じゃう→ちゃう, だ→た). 促音便 뒤는 원래 청음이라 해당하지 않는다(走って). だら는 SudachiPy 원형이 だ라서 だ→た로 함께 처리된다. 패턴 조건과 매칭이 같은 lemma를 쓰도록 형태소 단계에서 바꾼다. 이 규칙 이전에 등록된 패턴은 보정하지 않는다. 운영 데이터가 없고, 저장된 패턴만으로는 그 で가 음편 뒤였는지 가를 수 없다(PR #46 리뷰).

**다시 묻기 (FR-A11)**
2. 새 구문의 `morpheme_key`가 이미 있으면 새 용법은 버리고, 그 패턴의 반려되지 않은 용법을 후보로 같은 요청 안에서 한 번 더 묻는다. 두 번째 호출은 번역을 보낸 뒤 저장 트랜잭션 밖에서 스트림 없이 보내고, 번역을 함께 넣어 같은 해석으로 고르게 한다. 답은 첫 호출과 같은 규칙으로 검증한다. 다음 요청으로 미루는 방법은 부분 완료·재분석 장치가 아직 없어 고르지 않았다.
3. 저장 도중 다른 요청이 같은 패턴을 먼저 만들면(동시 생성) 저장을 되돌리고, 다시 물은 뒤 한 번만 다시 저장한다. LLM 호출은 트랜잭션 밖에서 한다.
4. 다시 묻지 않는 경우: 같은 조건의 기존 패턴이 반려 상태면 미발견으로 남긴다. 원문 인용으로 거부될 응답은 다시 묻기 전에 실패시킨다. 첫 호출을 기다리는 사이 다른 요청이 같은 문장을 저장했으면 그 결과를 쓴다. 셋 다 버려질 유료 호출을 막기 위해서다.
5. 다시 묻는 경우: 예문이 없어 비활성인 패턴도 다시 묻는다. `is_active`는 서버 매칭에 쓸지만 정하고, 화면 표시는 검수 상태로 정하므로(ADR 0003) 고른 구간은 미검수로 보인다. 반려되지 않은 용법이 하나도 없는 패턴도 다시 묻는다. 그 패턴 아래 새 용법을 받을 수 있다.

**기존 패턴에 새 용법**
6. 미발견 판정에는 새 용법(이름·설명·예문)이 함께 와야 한다. 첫 호출과 다시 묻기 모두 같고, 빠지거나 형식이 틀리면 응답 검증 실패다. 새 용법은 같은 패턴 아래 미검수(`origin=llm`)로 더한다. 예문은 패턴에 걸리고 원문을 베끼지 않았을 때만 `example_ja`에 넣고, `test_cases`와 활성 상태는 바꾸지 않는다.
7. 같은 이름의 용법이 이미 있으면 더하지 않고 미발견으로 남긴다. 동시에 같은 이름을 더한 경우도 같다. 이름이 같다고 같은 용법으로 묶지 않는다(31절 24에서 이름으로 묶는 방법을 고르지 않음).
8. 동시 요청이 같은 이름의 용법을 서로 다른 순서로 더하면 교착이 날 수 있어, 새 용법은 (패턴 `morpheme_key`, 용법 이름) 순서로 더한다(32절 8과 같은 이유).

**한 응답 안의 중복**
9. 같은 조건이 한 문장의 여러 자리에서 제안되면 패턴은 한 번만 등록하고 모든 자리를 보인다. 용법 이름이 같으면 그 용법을 함께 쓰고, 다르면 같은 패턴 아래 새 용법으로 더한다.
10. `(morpheme_key, 시작 토큰)`이 같은 자리에서 이미 판정한 후보 구간이나 앞서 낸 새 구문과 같으면 같은 구간이라 뺀다. 새로 등록하든 다시 묻든 한 행만 저장한다.
11. 같은 조건의 제안 중 검사를 통과한 첫 예문을 패턴의 첫 `test_cases` 항목과 활성화 근거로 쓴다. 같은 (패턴, 용법 이름)의 제안 중 통과한 첫 예문을 그 용법의 예문으로 쓴다. 다른 용법의 예문은 용법 예문으로 쓰지 않는다.

## 34. 새 예문 원문 복사 검사와 다시 쓰기 (2026-10-21) — #37, PR #49, 앞 절과 충돌 시 우선
#37에서 29절 2의 '원문의 연속된 일부를 기준 길이 이상 포함'을 구현하며 정했다. 1~8은 사용자 결정이다(#50). 29절 2의 "기준 길이는 구현 때 실제 예문으로 정한다"와 "거부되면 한 번 다시 쓰게 한다"를 아래 1·5로 대체한다.

**기준 길이**
1. 기준 길이는 설정값 `EXAMPLE_COPY_LENGTH`(기본 8자)다. 원문 키 텍스트와 예문에 함께 있는 연속 구간의 글자를 원문 인용 검사처럼 문장부호·기호·공백을 지우고 센다. 8자는 실제 모델 예문으로 확인하지 않은 시작값이라 설정으로 바꿀 수 있게 했다.
2. 패턴에서 고정한 토큰('lemma 고정'·'활용형도 고정')의 원문 글자는 세지 않는다. 예문은 그 문법을 쓸 수밖에 없기 때문이다. 다만 고정 토큰을 사이에 두고 앞뒤를 이어 베낀 것은 한 번의 복사로 센다. 고정 토큰으로 원문을 잘라 조각마다 세면 고정 토큰 양쪽을 나눠 베끼는 것을 놓친다(PR #49 리뷰). 구간 안의 '아무거나' 토큰은 원문 글자라 센다.
3. 고정 토큰은 두 방식으로 비교하고, 어느 쪽이든 기준 이상이면 베낀 것이다. 예문의 패턴 매치 자리와 맞춘 비교는 같은 lemma를 다른 표기로 쓴 경우(くる·来る)를 잡고, 글자 그대로의 비교는 매치 밖에서 같은 글자로 베낀 경우를 잡는다(PR #49 리뷰).
4. 새 예문은 200자를 넘으면 쓰지 않는다. 형태소 분석 한도를 넘는 예문이 분석 전체를 실패시키는 것과, 부분 복사 비교가 원문 길이 × 예문 길이로 길어지는 것을 함께 막는다(PR #49 리뷰). 200자를 넘는 예문은 원문 복사가 아닌 이유로 쓸 수 없는 예문이라 다시 쓰게 하지 않는다(5).

**다시 쓰기**
5. 원문을 베껴 거부된 예문만 다시 쓰게 한다. 한 응답의 거부된 예문은 한 호출로 묶어 한 번만 보내고, 다시 쓴 예문도 같은 검사를 통과해야 쓴다. 다시 써도 원문 복사만 고쳐지므로, 패턴에 걸리지 않거나 자리표시자가 있어 거부된 예문은 다시 쓰지 않는다.
6. 버려질 유료 호출은 보내지 않는다. 같은 용법에 이미 통과한 예문이 있으면 다시 쓰지 않고 그 예문을 쓴다. 기존 패턴에 같은 이름의 용법이 이미 있어 더하지 않을 새 용법(33절 7)은 예문을 검사하지도 다시 쓰지도 않는다. 다른 요청이 같은 문장(원문)의 분석을 먼저 저장했으면 다시 쓰기를 보내지 않는다.
7. 다시 쓰기 호출이 실패하거나 응답 형식이 틀리면 분석 전체를 실패로 하지 않고 그 예문 없이 계속한다. 같은 조건의 다른 제안에 통과한 예문이 있으면 그 예문이 활성화 근거가 되고(33절 11), 통과한 예문이 하나도 없을 때만 비활성으로 등록한다. 보조 호출(스트림 없는 다시 묻기·예문 다시 쓰기) 하나 때문에 번역·문법을 버리지 않기 위해서다.

**요청 시간 상한**
8. 요청 하나의 LLM 대기 전체(스트림 + 다시 묻기·예문 다시 쓰기)에 110초 마감을 둔다. 호출을 시작하기 전에만 남은 시간을 보고, 진행 중인 호출을 마감에 맞춰 취소하지는 않는 소프트 마감이다. 요청마다 LLM 클라이언트 하나를 쓰고 클라이언트를 만든 때부터 세며, 보조 호출은 min(30초, 남은 시간)만 기다리며, 마감이 지났으면 보내지 않고 실패로 둔다(다시 쓰기는 7처럼 예문 없이 계속, 다시 묻기는 분석 실패). 보조 호출이 늘어 운영 Gunicorn 작업자 타임아웃(120초)을 넘으면 저장도 오류 이벤트도 없이 끊기기 때문이다(PR #49 리뷰). 110초는 120초보다 저장할 시간만큼 짧게 잡았다. 소프트 마감이라 120초를 넘지 않는다고 보장하지는 않는다(아래 한계).

**알려진 한계 (미정)**
- 고정 토큰 바로 뒤에 원문에 없는 토큰을 끼워 넣으면(ている → ていた) 연속 복사가 끊겨 따로 센다. 기준이 '연속 N자'라 다루지 않는다. 막으려면 비교 방식을 바꾸는 별도 결정이 필요하다.
- 기준 길이 8자와 다시 쓰기 지침이 실제 모델 예문에서 적절한지는 실제 API로 확인하지 않았다.
- SDK 타임아웃은 요청 전체가 아니라 연결·읽기 단계마다 걸려, 마감 직전에 시작한 보조 호출이 남은 시간을 넘길 수 있다. 응답 조각이 읽기 타임아웃보다 짧은 간격으로 계속 오면 크게 넘길 수도 있다. 호출 전체를 취소하는 하드 상한은 구현하지 않았다.

## 35. 패턴·용법 승인과 반려 (2026-10-21) — #38, PR #51, 앞 절과 충돌 시 우선
#38에서 FR-A13과 requirements '패턴 매칭 규칙'의 전이표를 구현하며 정했다(#52). 표시가 없는 내용은 트리아지(#38 Agent Brief)에서 사용자가 정했다. '(PR #51 리뷰)'는 리뷰 지적을 고치며 구현이 정했고 리뷰를 통과한 것, '(PR #51 리뷰, 사용자 결정)'은 리뷰 중 사용자가 정한 것이다.

**stale과 세대 번호**
1. stale은 이번엔 `sentence_analysis.is_stale`로만 기록하고, 판 번호(revision·basis_revision·usage_revision)는 조건·용법 정의를 수정하는 티켓으로 미룬다. 지금은 판 번호를 바꾸는 사건이 없어서다. stale 분석은 다음 요청에서 캐시 미스처럼 처음부터 다시 분석해 번역·단어·구간을 통째로 바꾸고 stale을 푼다. 옛 결과를 '재분석 중'으로 먼저 보이는 것은 #44에서 한다.
2. 사건이 일어나면 같은 트랜잭션에서 영향 범위 분석의 `is_stale`을 켜고 `generation`을 올린다. 한 사건에서 여러 번 오를 수 있어(예: 용법 완결 패턴의 반려는 해제와 반려 각각에서 올린다) 값이 같은지만 비교한다. 분석 요청은 시작할 때 읽은 `generation`이 저장할 때와 다르면 응답은 보내고 저장(새 패턴·용법 등록 포함)은 되돌린다. stale이 남아 다음 요청이 다시 분석한다.
3. 영향 범위는 둘로 나뉜다. 용법 반려와 용법 승인 취소는 그 용법으로 정해진 구간이 있는 분석이다. 패턴 반려, 패턴 승인 취소, 반려 취소(패턴·용법), 용법 완결 표시·해제는 그 패턴의 구간이 있는 분석이다. 후보로만 들어갔던 용법(`span_match.candidates`)은 넣지 않는다. 회화체 패턴과 대안 해석은 아직 없어 넣지 않는다(#41, #40).

**상태 전이**
4. 반려 취소는 항상 미검수(pending)로 되돌린다. 전이표의 "→ pending·approved"를 좁힌 것이다. 승인은 승인 동작으로 따로 한다.
5. test_cases 통과('걸려야 함'·'걸리면 안 됨' 각각 하나 이상, 모두 매칭기 결과가 기대와 같음, 빈 배열은 통과 아님)는 패턴 승인과 용법 완결 표시에만 건다. 용법 승인은 소속 패턴이 반려 상태가 아니면 된다. test_cases는 패턴에만 있기 때문이다.
6. 용법 완결은 패턴 승인 + test_cases 통과 + 반려되지 않은 용법이 정확히 하나이고 그 용법이 승인 상태일 때만 붙인다. 새 용법 추가(LLM의 미발견 새 용법 경로 포함), 용법이나 패턴의 승인 취소·반려, 용법 반려 취소 때 같은 트랜잭션에서 떼고 그 패턴의 분석을 stale로 만든다. 용법 반려 취소는 반려되지 않은 용법을 다시 둘로 만들 수 있어 더했다(PR #51 리뷰). 활용형 조건 검토(requirements 용어표)는 관리자가 판단하고 서버가 검사하지는 않는다.
7. 패턴 반려는 `is_active`를 false로, 패턴 반려 취소는 활성화 근거(매칭기를 통과하는 '걸려야 함' 예문이 하나 이상)를 다시 확인해 정한다. 패턴 세트 버전은 `is_active`가 실제로 바뀔 때만 올린다.

**admin**
8. '걸리면 안 됨' 예문은 관리자가 admin에서 쓴다. LLM은 '걸려야 함' 예문 하나만 쓴다.
9. admin에서 test_cases를 고치면, 승인·용법 완결 패턴은 통과하지 못하게 바꿀 수 없다(먼저 승인을 취소한다). 반려되지 않은 패턴은 저장 때 활성화 근거를 다시 확인해 `is_active`와 패턴 세트 버전을 맞춘다(PR #51 리뷰, 사용자 결정: 승인 상태를 자동으로 취소하는 대신 저장을 거부하는 쪽). 승인 상태가 조건을 잃은 채 남거나, 예문을 보완해도 활성화되지 않는 것을 막는다.
10. 원문 위치를 담은 `sentence_analysis`·`span_match`는 admin에 올리지 않는다. 패턴은 이름·test_cases, 용법은 설명·예문만 고친다. 저장은 그 칸만 쓴다. 폼을 연 뒤 액션이 바꾼 상태를 덮지 않게 하기 위해서다(PR #51 리뷰). 상태는 액션으로만 바꾼다. 패턴·용법은 LLM이 만들므로 admin에서 더하거나 지우지 않는다. 용법 설명·예문을 바꿔도 stale로 만들지 않는다(조회할 때마다 용법 행에서 읽는다).

**잠금**
11. (PR #51 리뷰) 상태 전이와 분석 저장은 패턴(·용법) → 패턴 세트 버전 → 분석 행 순서로 잠근다. 분석 저장은 분석 행을 패턴 쪽을 다 쓴 뒤 마지막에 잠그고, `add_usage`는 용법을 넣기 전에 패턴 행을 잠근다(용법 완결 표시가 커밋 전 용법을 못 보지 않게). 명시 잠금은 모두 `FOR NO KEY UPDATE`다. Django의 FK는 커밋 때 검사해 패턴·용법 행에 KEY SHARE를 거는데, `FOR UPDATE`로 쥐면 분석 저장의 커밋과 교착한다(PR #51 리뷰, 두 연결로 재현). 영향 범위 분석 행은 id 순서로 잠근다.

**구현이 정한 것 (확인 필요)**
- 상태별 허용 동작: 승인은 미검수에서만, 반려는 미검수·승인에서, 반려 취소는 반려에서만, 승인 취소는 승인에서만 한다. 승인 취소를 pending과 rejected 중 어디로 되돌릴지는 여전히 미결이고(requirements 8장), 지금 구현은 pending으로 되돌린다.

**알려진 한계 (미정)**
- 처음 분석하는 문장은 시작할 때 분석 행이 없어 세대 번호로 경합을 막지 못한다. 분석하는 사이 반려된 용법으로 정한 구간이 stale 표시 없이 저장될 수 있다(조회 때 반려는 숨겨진다).
- stale 분석을 다시 분석하는 사이 새 결과에만 있는 패턴의 상태가 바뀌면, 그 행에 옛 구간이 없어 세대 번호가 오르지 않는다.
- admin에서 여러 행을 골라 액션을 실행하면 행마다 따로 처리해 일부만 거부될 수 있다.
- test_cases를 빈 목록으로 저장하는 것은 Django 폼이 막는다(필요한지 미정).

## 36. 용법 완결 패턴의 단일 후보 확정 (2026-10-21) — #39, PR #57, 앞 절과 충돌 시 우선
#39에서 requirements '구간 판정 절차' 2단계를 구현하며 정했다. 1~6은 트리아지(#39 Agent Brief와 그 질문 과정)에서 사용자가 정했다(#58). 5는 확정 구간이 있는 경우에 한해 31절 21의 이벤트 순서(`translation` → `analysis`) 앞에 `grammar`를 더하고, 31절 22(번역을 보내기 전의 실패는 상태 코드)를 바꾼다.

1. 이번에는 2단계(용법 완결 패턴의 단일 후보)만 구현한다. 3단계(판별 규칙)는 규칙의 조건 형식·등록·승인을 따로 정해야 해서 #55로 나눴다.
2. 패턴이 용법 완결이고 승인 상태이며, 반려되지 않은 용법이 승인된 하나뿐인 구간만 LLM 없이 그 용법으로 확정한다(`decided_by = single_usage`). 용법 완결 표시(35절 6)가 이 조건을 보장하지만 분석 때도 다시 확인한다. 미검수 단일 용법은 여전히 LLM에 묻는다(requirements 처리 흐름 4).
3. 판 번호(`basis_revision`)는 두지 않는다. 확정 구간이 틀려질 수 있는 사건(용법 완결 표시·해제, 승인 취소·반려, 반려 취소, 새 용법 추가)은 모두 35절의 stale로 다시 분석된다.
4. 확정 구간은 LLM 후보에서 빼고, 같은 요청에 `decided_spans`(토큰 범위, 용법 이름)로 알려 답하지도 새 구문으로 다시 내지도 않게 한다. 빼기만 하면 LLM이 그 문법을 새 구문으로 다시 내고, 같은 조건의 패턴이 있어 다시 묻기(유료 보조 호출)로 이어지기 때문이다. 그래도 같은 자리·같은 조건(`morpheme_key`, 시작 토큰)의 새 구문이 오면 버리고 다시 묻지 않는다.
5. 확정 구간이 하나라도 있으면 LLM을 부르기 전에 `grammar` 이벤트를 먼저 보낸다. 항목은 `analysis.grammar`와 같은 모양(이 요청 원문 기준 UTF-16 위치, 이름·설명·검수 상태)이다. 이 이벤트로 응답이 시작되므로 이후 실패는 상태 코드가 아니라 `error` 이벤트로 알린다. 확정 구간이 없으면 번역이 첫 이벤트이고 그 전 실패는 상태 코드다(31절 22). 캐시된 문장은 그대로 한 번에 보낸다.
6. `grammar` 뒤 LLM이 실패하면 지금처럼 아무것도 저장하지 않는다(부분 완료 저장 장치가 아직 없다). 사이드 패널은 먼저 온 문법을 남긴 채 실패를 보인다. 다시 시도하는 버튼은 #56에서 다룬다.

**알려진 한계 (미정)**
- 처음 분석하는 문장은 분석 행이 없어 세대 번호 검사가 없다. 분석하는 사이 그 패턴의 용법 완결이 해제되거나 용법이 반려되면, 요청 시작 때 기준의 `single_usage` 구간이 stale 없이 저장될 수 있다(35절의 같은 한계). 반려된 용법은 조회할 때 숨겨진다.
- `decided_spans` 지침이 실제 모델에서 재제안을 막는지는 실제 API로 확인하지 않았다(막지 못해도 서버가 버린다).
