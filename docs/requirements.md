# Dragram 요구사항 정의서

작성 2026-10-11 · Claude Docs rev 193에서 내보냄. 이후 변경은 이 파일에서 직접 한다.

## 1. 개요

Dragram은 웹페이지의 일본어 문장을 드래그하면 형태소 단위로 문법을 분석해 크롬 사이드 패널로 보여주는 크롬 확장 프로그램이다. 개인 프로젝트로, 분석 → 회원 → 결제 순서로 구현한다.

**목적**: 사용자가 직접 고른 글(기술 문서, 뉴스, 게임, 소설 등)을 읽으면서 자기에게 필요한 일본어를 그 자리에서 집중해서 배울 수 있게 한다. 웹소설 전용 서비스가 아니다.

**설계 원칙**: AI를 쓸수록 AI가 덜 필요해지는 시스템. 문법·단어·한자 지식과 문장 분석 결과를 DB에 쌓아 전체 사용자와 공유한다. 처음 보는 문장의 첫 응답에 필요한 번역과 용법 판별은 LLM 요청 한 번으로 묶고, 지식이 쌓일수록 그 요청이 가벼워지게 한다.

**범위**

- 포함: 크롬 확장(extension/), Django 백엔드(backend/), React 웹(web/) 모노레포
- 분석 방향: 일본어 문장 → 한국어 설명·번역
- MVP 언어 범위: 표준어와 회화체. 미리 넣어 두는 시드 문법 없이 시작하고, DB에 없는 문법은 LLM 분석으로 pending 패턴을 등록해 쌓는다
- 나중에: 방언, 인터넷 말투, 신조어, 과장된 캐릭터 말투, 수동태 세분화(れる의 수동·가능·존경 구분), 말투(register) 표시
- 범위 밖: 다국어 설명, 역방향(한국어 → 일본어) 분석, PDF 분석, 모바일에서의 분석(붙여넣기 분석 페이지, 웹 PDF 뷰어), 축약어의 원래 형태를 복원해 보여주는 확장 문장 기능. 향후 검토
- 미정: 다른 브라우저 지원 (드래그 분석은 크롬 확장 전용, 복습·작문은 모바일 웹 지원)

**용어**

| 용어 | 뜻 |
| --- | --- |
| 형태소 | SudachiPy가 나눈 최소 의미 단위 (품사, 원형 포함) |
| 문법 패턴 | 규칙 매칭에 쓰는 형태소 시퀀스 (예: 명사 + で) |
| 용법 | 하나의 패턴이 가질 수 있는 의미 단위 (예: で-장소, で-수단). 설명과 승인은 용법 단위로 관리하며, LLM이 고르는 문법 ID도 용법 ID다 |
| 용법 완결 | 관리자가 용법이 하나뿐이라고 확인한 패턴의 표시. 이 패턴만 후보 1개로 바로 확정한다. 활용형 조건 검토와 예문 테스트를 통과해야 붙일 수 있다 |
| 구간 | 문장 안에서 문법 판정 대상이 되는 형태소 범위. 패턴 매칭으로 찾거나, LLM이 후보로 설명되지 않는 문법으로 표시한다 |
| 확정 | 승인된 지식만으로 구간의 용법이 하나로 정해진 결과. 구간에 저장하지 않고 조회할 때 정한다. 고른 용법과 실제로 매칭된 패턴이 모두 승인됐을 때만 확정이고, 하나라도 미검수면 'AI 생성·미검수'로 표시한다 |
| 판별 대상 | DB만으로 구간의 용법을 하나로 정하지 못해 LLM 판별을 기다리는 단계. 저장하지 않는다. 후보가 1개여도 용법 완결 패턴이 아니면 포함한다 |
| 미발견 | 배울 문법이 있지만 기존 후보로 설명되지 않는 구간. 같은 LLM 요청에서 새 문법을 찾아 미검수 패턴·용법으로 등록한다. 어떤 패턴에도 안 걸린 조사·조동사·보조동사는 LLM에 주는 힌트일 뿐 그 자체로 미발견은 아니다 |
| 해당 없음 | 패턴에는 걸렸지만 그 자리에 배울 문법이 없는 구간(이름 속 の 등). 새 문법을 찾지 않는다 |
| 문맥 키 | 판정 통계를 모으는 단위. 조사 패턴은 (패턴, 앞 내용어 원형, 뒤 첫 동사·형용사 원형) |
| 문장 분석 | 한 문장에 대한 번역과 구간별 용법 매칭의 묶음. 함께 저장되고 함께 무효화되며, 완료 / 부분 완료 상태를 가진다 |
| 부분 완료 | 미발견 구간의 새 문법 등록이 실패하거나 상한에 걸려 미해결 구간이 남은 문장 분석 |
| stale | 다시 만들어야 하는 문장 분석. 참조하는 문법 패턴·용법의 판 번호가 분석에 기록된 번호보다 높거나, 패턴 세트 버전이 올랐거나, 판 번호가 없는 사건(매칭 정정 등)으로 stale 표시가 붙은 경우 |
| 패턴 승인 | LLM이 만든 패턴(형태소 조건)과 용법(설명)을 각각 `pending` → `approved` / `rejected`로 검토하는 절차. LLM이 만든 패턴·용법은 pending(미검수)으로만 등록된다 |
| 분석 텍스트 | 숫자를 그대로 둔 정규화 문장. SudachiPy 입력으로만 쓴다 |
| 키 텍스트 | 정규화 문장의 아라비아 숫자를 ⟨N1⟩, ⟨N2⟩ 자리표시자로 바꾼 것. 해시, LLM 입력, 번역 저장, 구간 위치의 기준이다 |
| 판 번호 | 문법 패턴과 용법이 바뀔 때마다 오르는 번호(revision). 문장 분석에 기록된 번호와 조회 시 비교해 최신 여부를 판단한다 |
| 대상 문법 없음 | LLM이 확인한 결과 분석할 문법이 없는 문장(명사만 있는 제목 등). 정상 결과다. 화면에는 문법 칸을 숨기지 않고 "문법 요소 없음" 한 줄로 표시해 실패와 구분한다. 새 문장은 번역 때문에 LLM을 반드시 한 번 부르므로 문법 확인도 그 요청에서 함께 한다 |
| 그림자 모드 | 자동 승인 기준으로 '승인했을 것'만 기록하고 상태는 pending으로 두는 방식. 관리자 결정과 비교해 기준을 검증한다 |
| 이름 구간 | 고유명사로 표시한 구간(사람, 장소, 조직, 작품, 기타). 형태소와 문법 후보는 그대로 두고 주석만 붙인다 |
| 해석 갈림 | 문장만으로 용법이 하나로 정해지지 않는 구간. 번역과 같은 해석을 주 용법으로, 나머지를 대안 해석(대안 용법 + 짧은 대안 번역)으로 함께 보인다. 예전의 '판별 불가'를 대체한다 |
| 미확정 | 재질문 후에도 근거가 부족하거나 지원 범위 밖이라 주 용법을 정하지 못한 구간(unresolved). 해석 갈림과 구분한다 |
| 회화체 패턴 | 다른 패턴의 축약된 말투 형태(예: ちゃう ← てしまう). 패턴은 따로 두되 자기 용법 없이 원형 패턴의 용법·설명을 그대로 쓰고(원형 참조), 화면에서만 '회화체'로 표시한다 |
| 동사 그룹 | 동사의 활용 방식에 따른 분류. 1그룹(5단), 2그룹(1단), 3그룹(する·くる)으로 부른다 |
| 단어 태그 | 단어에 붙는 분류 꼬리표. 품사, 동사 그룹, い형용사·な형용사, 고유명사, 예외 활용(SudachiPy)과 자동사·타동사, 경어, 의성어·의태어, 외래어(JMdict 태그 우선, 부족분은 LLM)가 있다 |
| 예외 활용 | 그룹 규칙대로 활용하지 않거나 모양과 그룹이 어긋나는 단어(帰る는 1그룹, 行く의 て형 行って, いい의 부정형 よくない 등). 화면에 '주의'로 표시한다 |
| 자타 대응 동사 | 뜻이 짝을 이루는 자동사·타동사 한 쌍(예: 開く ↔ 開ける). 상대 표기만 글자로 저장하고, 웹페이지 단어 화면에서만 "타동사: 開ける" / "자동사: 開く"처럼 관계로 표시한다 |
| 내 일본어 | 사용자가 드래그한 문장에 나온 단어·한자·용법 전부. 본인만 볼 수 있다 |
| 학습 카드 | 내 일본어 중 사용자가 골라 복습 대상으로 등록한 것 |

## 2. 사용자 정의

주 사용자는 히라가나와 가타카나를 읽을 수 있고, 기술 문서, 뉴스, 게임, 소설처럼 자기에게 필요한 일본어 글을 읽으며 공부하는 학습자다. 시험 대비보다는 읽고 싶은 글을 읽다가 막히는 부분을 바로 이해하는 데 초점을 둔다.

| 역할 | 설명 | 주요 행동 |
| --- | --- | --- |
| 학습자 | 가나를 읽을 수 있는 학습자 | 문장 드래그, 문법 설명 확인, 번역 확인 |
| 관리자 | 개발자 본인 | LLM이 찾은 신규 용법 승인·반려, 매칭 정정 (Django admin) |

**기본 사용 시나리오**

1. 학습자가 Google 계정으로 로그인한 뒤 일본어 웹페이지를 읽다가 모르는 문장을 드래그하고 우클릭 메뉴 "Dragram으로 분석"을 누른다(드래그만으로 자동 분석하는 방식은 나중에 검토).
2. 확장이 선택한 텍스트를 문장 단위로 나누고 분석을 요청한다.
3. DB로 바로 정해지는 문법, 단어, 한자 설명이 사이드 패널에 먼저 표시된다. 처음 보는 문장이면 번역과 판별 대상 구간의 판별 결과가 이어서 채워진다.
4. 학습자가 번역과 문법을 확인하고, 페이지에서 분석한 문법이 하이라이트된다. 같은 문장은 다음부터 누가 드래그해도 저장된 결과로 바로 표시된다.

**확인할 점**: 한자 읽기는 어느 수준으로 가정할지, 후리가나를 제공할지 정해야 한다.

## 3. 기능 요구사항 — Phase 1 분석

첫 단계는 Google 로그인과, 드래그한 일본어 문장의 문법·단어·한자 설명과 한국어 번역을 보여주는 데까지다. 우선순위는 초안이니 표에서 바로 바꿔도 된다.

### 분석 흐름

1. 사용자가 분석을 시작하면(첫 기능 단위는 우클릭 메뉴, 자동 분석은 나중에 검토) 확장이 선택 범위를 문장 경계까지 넓히고 문장 단위로 나눈다. 실제로 드래그한 범위는 따로 기억해 강조한다.
2. 문장마다 분석 텍스트와 키 텍스트를 만들고, 키 텍스트의 SHA-256으로 문장 분석을 찾는다. 재사용할 수 있으면 LLM 없이 응답하고, 판 번호가 뒤처졌으면 옛 결과를 '재분석 중'으로 보여주며 갱신한다. 같은 문장이 처리 중이면 그 결과를 기다린다.
3. 없으면 분석 텍스트로 형태소를 분석하고 패턴을 매칭해 구간별 용법 후보를 찾는다. 단어·한자 정보는 DB에서 조회한다.
4. 구간마다 아래 판정 절차로 DB만으로 정해지는 구간과 판별 대상을 가린다. 새 문장은 번역 때문에 LLM을 한 번 반드시 부르므로, 승인된 용법 완결 패턴을 제외한 모든 후보 구간(미검수 단일 용법 포함)을 그 요청에서 확인하고 문장 전체에서 새 구문 제안도 받는다. 어떤 패턴에도 안 걸린 조사·조동사·보조동사는 LLM에 주는 힌트로만 쓴다. LLM 없이 재사용하는 것은 이미 분석이 캐시된 문장뿐이다.
5. DB로 확정된 결과(확정 구간, 단어, 한자)를 즉시 표시한다.
6. 새 문장은 LLM 요청 한 번(structured output)으로 번역, 후보 구간의 용법 확인·선택(번역과 같은 해석), 문장 전체의 새 구문 제안, 문장에 나온 단어의 뜻(sense) 선택을 함께 받아 이어서 채운다. LLM은 서버가 부여한 후보·토큰 ID만 고르고, 구간 위치는 서버가 계산한다.
7. 응답을 검증해 문장 분석으로 저장한다. 번역에 숫자 자리표시자가 빠짐없이 있을 때만 공용 캐시에 넣는다. 미해결 구간이 남으면 부분 완료로 저장한다.
8. LLM이 찾은 새 문법은 패턴 생성 규칙에 따라 미검수(pending) 패턴·용법으로 등록하고 'AI 생성·미검수' 배지로 바로 표시한다. LLM 작업(첫 분석, 재분석, 재시도)은 큐에 넣어 작업자가 처리하고, 일일 상한과 호출 기록을 비용 안전장치로 둔다. 시드 없이 시작하므로 초반 상한은 넉넉히 잡는다. 관련된 부분 완료 분석은 다시 판정한다.

### 구간 판정 절차

| 단계 | 조건 | 판정 |
| --- | --- | --- |
| 1 | 새 문장 LLM 요청에서 확인한 결과 분석할 문법이 없음 | 대상 문법 없음 (정상 결과) |
| 2 | 후보 1개이고, 패턴이 용법 완결로 표시됨 (승인된 용법만) | 확정 (단일 용법) |
| 3 | 후보 2개 이상이고, 승인된 규칙 조건에 맞는 후보가 정확히 1개 | 확정 (규칙) |
| 4 | 판정 통계를 쓰는 경우, 같은 문맥 키의 판정 기록이 N회 이상이고 한 용법의 비율이 P% 이상 | 확정 (통계) |
| 5 | 위 어디에도 해당하지 않음 (후보 1개지만 용법 완결이 아닌 경우 포함) | 판별 대상 → 새 문장의 첫 LLM 요청에서 판별 |

LLM은 후보 중 번역과 같은 해석의 용법을 고를 수 있다. 후보가 모두 부적합하면, 그 자리에 배울 문법이 없을 때는 '해당 없음'(새 문법을 찾지 않음)으로, 후보로 설명되지 않는 문법이 있을 때는 '미발견'(새 문법 등록)으로 답한다. 문장만으로 해석이 갈리면 주 용법과 대안 해석(대안 용법 + 짧은 대안 번역)을 함께 낸다('해석 갈림'). 근거 없이 대안을 낸 구간은 한 번 다시 묻는다. 다시 물어도 근거가 부족하거나 지원 범위 밖이면 '미확정'으로 저장하고, 재질문으로 주 용법이 바뀌면 번역도 함께 갱신한다. 기존 용법이 맞지 않으면 같은 패턴 아래 새 pending 용법을 추가한다(예: ながら의 동시 동작만 등록돼 있을 때 知っていながら의 역접). 새 문장은 번역 때문에 첫 LLM 요청이 반드시 일어나므로, 늘어나는 입력 토큰보다 정확도를 우선해 승인된 용법 완결 패턴이 아닌 구간은 미검수 단일 용법을 포함해 모두 그 요청에서 확인한다.

MVP는 문장 단독으로 분석하며 앞뒤 문맥은 입력에 넣지 않는다. 문맥에 따라 해석이 갈리면 '해석 갈림'으로 두고 주 용법과 대안 해석을 함께 보여준다. 관리자가 용법을 정정하면 그 문장의 번역도 재번역 대상이 된다. 확정 판별의 근거(용법 완결, 규칙)로는 승인된 용법·규칙만 쓴다. 규칙은 실제로 매칭된 패턴의 승인된 규칙만 적용한다(회화체 패턴이 원형의 용법을 공유해도 규칙은 패턴별로 둔다). 새 문장에서 미검수 패턴이 걸리면 용법이 하나라도 첫 LLM 요청에서 확인하고 '미검수'로 표시한다. LLM 없이 재사용하는 것은 이미 분석이 캐시된 문장뿐이다.

Phase 1은 판정 통계(4단계)를 쓰지 않고 바로 LLM 판별로 넘긴다. 나중에 켤 때는 같은 문장의 재처리를 1건으로 세고, 정정된 판정은 제외하며, 평가 문장 세트와 통계 자료를 분리하고, 통계로 확정한 구간의 정확도를 따로 측정한다. N, P, confidence 기준은 설정값으로 둔다.

새 구문은 LLM이 문장 전체에서 제안하고, 어떤 패턴에도 걸리지 않은 조사·조동사·보조동사는 힌트로 준다. 이 방식이 문법 누락이 없음을 보장하지는 않는다.

### 패턴 매칭 규칙

- 패턴의 형태소 조건은 lemma(조사·조동사는 SudachiPy 원형(dictionary\_form), 동사·형용사 등 내용어는 정규형(normalized\_form), 탁음화 조건부 규칙 적용), 품사 대분류·중분류, 활용형이다. 빈 칸은 '아무거나'이며 정확히 1토큰이다. 패턴은 연속한 토큰만 다루고, 〜ば〜ほど 같은 불연속 문법은 MVP에서 제외한다.
- 食べた(終止形)와 食べたら(仮定形)처럼 활용형으로 과거와 조건이 갈리는 패턴은 활용형 조건을 반드시 지정한다.
- 용법 완결 패턴은 활용형 조건 검토가 필수다. 패턴은 원래 문장 재매칭과 새로 쓴 예문 매칭을 둘 다 통과하면 활성화한다(아래 '활성화 근거'). 맞아야 하는 예문과 걸리면 안 되는 예문 테스트(test\_cases) 통과는 패턴 승인과 용법 완결 표시의 조건이다. test\_cases가 비어 있으면 통과로 보지 않는다. LLM이나 관리자가 새로 쓴 '걸려야 함' 예문과 '걸리면 안 됨' 예문이 각각 하나 이상 있고 모두 맞아야 한다.
- 반려·반려 취소는 아래 표 하나로 처리한다. **영향 범위**는 그 패턴과, 그 패턴을 원형으로 가리키는(variant\_of) 회화체 패턴을 쓰던 문장 분석 전부다(대안 해석 포함). 용법이면 그 용법이 속한 패턴을 기준으로 한다.
- 패턴과 용법은 따로 반려될 수 있다. 용법은 **자기와 소속 패턴이 모두 반려 상태가 아닐 때만 유효**하고, 유효한 용법만 판정·규칙·LLM 후보에 들어가며 그 용법의 학습 카드만 일시 정지가 풀린다. 그래서 한쪽을 복원해도 다른 쪽이 아직 반려 상태면 그 부분은 복원되지 않는다.

  | 상태 변화 | 매칭(`is_active`) | 판정·규칙·LLM 후보 | 영향 범위의 문장 분석 | 학습 카드 |
  | --- | --- | --- | --- | --- |
  | 패턴 반려 | false | 그 패턴의 용법 전부 제외 | stale | 그 패턴의 용법 카드 일시 정지 |
  | 용법 반려 | 그대로 | 그 용법만 제외 | stale | 그 용법 카드 일시 정지 |
  | 패턴 반려 취소(→ pending·approved) | 활성화 근거를 다시 검증해 통과하면 true | 유효한 용법만 다시 포함(반려된 용법은 계속 제외) | stale | 유효한 용법의 카드만 해제 |
  | 용법 반려 취소(→ pending·approved) | 그대로 | 패턴이 반려 상태가 아니면 다시 포함 | stale | 패턴이 반려 상태가 아니면 해제 |
  | 승인 취소(패턴·용법 approved → pending) | 그대로 | 계속 포함하되 확정 판별(용법 완결, 판별 규칙)의 근거로는 쓰지 않음 | stale | 그대로 |

  승인 취소를 pending과 rejected 중 어디로 되돌릴지는 미결이다(8장). rejected로 되돌리면 반려 행을 따른다.

- **진행 중인 작업 무효화**: 위 상태 변화가 일어나면 영향 범위 문장 분석의 세대 번호(generation)를 함께 올린다. 변화 전에 시작한 작업이 끝나도 세대 번호가 맞지 않아 옛 후보로 만든 구간·번역을 저장하지 못하고, stale도 풀지 못한다.
- **활성화 근거**: 등록 때의 원래 문장 재매칭 통과, 그리고 새로 쓴 '걸려야 함' 예문(LLM이 쓴 것이든 관리자가 보완한 것이든) 하나 이상의 매칭 통과. 근거가 생기거나(관리자가 예문을 보완함) 패턴 반려가 취소되면 서버가 다시 검증해 `is_active`를 정한다. 반려된 패턴은 근거가 있어도 false다.
- **활성 여부가 바뀌면 패턴 세트 버전을 올린다.** 현재 패턴 세트 버전은 DB에 한 행으로 보관하고(`pattern_set_version`), `is_active`를 바꾸는 트랜잭션 안에서 그 행을 잠가 1 올린다. 서버를 다시 시작하거나 여러 서버가 동시에 바꿔도 값이 하나로 유지된다. 캐시된 분석의 `matcher_version`이 이 값보다 낮으면 로컬 매칭을 다시 돌린다. 새 패턴 등록, 반려 취소, 예문 보완으로 `is_active`가 false → true가 되거나 반려로 true → false가 될 때 모두 해당한다. 비활성인 동안 분석된 문장에는 그 패턴의 구간이 없어서 "그 패턴을 쓰던 분석"으로는 찾을 수 없기 때문이다. 버전이 오르면 캐시된 분석은 조회 때 로컬 매칭을 다시 돌려 새로 걸린 구간을 찾는다(FR-A24).
- **관리자 정정은 상태를 바꾸지 않고 적용할 때 검사한다.** 정정 후 용법이나 그 패턴이 반려 상태면 그 정정은 적용하지 않고 재분석 결과를 쓴다. 반려가 취소되면 따로 복구하지 않아도 다음 분석부터 다시 적용된다. `match_correction.status`(active / suspended)는 관리자가 직접 바꿀 때만 쓴다. 정정의 상태를 반려에 맞춰 고쳐 쓰면, 복구할 때 "반려 때문에 멈춘 정정"과 "관리자가 멈춘 정정"을 구분해야 하기 때문이다(ADR 0003과 같은 이유).
- 반려된 패턴이나 용법으로 정해진 구간은 재분석을 기다리지 않고 조회할 때 바로 응답에서 뺀다. 관리자가 틀렸다고 판정한 결과는 '재분석 중'으로도 보이지 않는다. 해석 갈림의 대안 용법도 하나씩 같은 규칙으로 본다: 미검수면 그 대안에 'AI 생성·미검수'를 달고, 반려됐으면 그 대안만 뺀다. 주 용법이 반려된 분석의 번역은 그 해석으로 만들어졌으므로, 재분석이 끝날 때까지 번역을 숨기지 않고 경고 표시와 함께 보여 준다(문구는 DESIGN §7).
- 겹침: 화면에서 접어 보여주는 것과 분석에서 빼는 것을 분리한다. 긴 패턴이 이겨도 안쪽 후보는 보존하고, 구성 관계가 명시된 패턴만 중복 표시를 생략한다.
- 고유명사: 원래 형태소와 문법 후보는 그대로 두고 이름 구간(사람, 장소, 조직, 작품, 기타)만 주석으로 붙인다. 이름의 뜻은 번역에 맡긴다.
- 사전에 없는 전문 용어(OOV)는 단어로 저장해 공유한다.
- 패턴 생성: LLM은 서버가 부여한 토큰 ID로 핵심 토큰만 고르고 토큰마다 'lemma 고정 / 활용형도 고정 / 아무거나'를 표시한다. 서버가 SudachiPy 토큰에서 형태소 조건을 만든다. 처음과 끝 토큰은 '아무거나'일 수 없다. 만든 패턴으로 원래 문장을 다시 매칭해 걸려야 저장한다. 같은 요청에서 LLM은 원래 문장과 같은 구조의 새 예문을 하나 쓰고, 서버가 이 예문에도 패턴이 걸리는지 확인한다. 예문이 원문을 베꼈으면 거부한다: 키 텍스트가 원문의 키 텍스트와 같거나, 원문 키 텍스트 전체를 포함하거나(길이와 무관), 원문 키 텍스트의 연속된 일부를 기준 길이 이상 그대로 포함하면 베낀 것으로 본다(기준 길이는 설정값, 구현 때 실제 예문으로 정한다). 거부되면 한 번 다시 쓰게 하고(사용 기록 목적은 `example_rewrite`), 그래도 베끼면 예문 없이 등록한다(예문이 없으면 활성화하지 않는다). 이 예문은 용법 예문(example\_ja)과 test\_cases의 첫 '걸려야 함' 항목이 되며, 관리자는 원문 대신 이 예문으로 승인을 판단한다. 드래그한 원문은 이 재매칭 검증에만 쓰고 공용 데이터(용법 예문, 패턴 테스트 예문)에는 저장하지 않는다. 공용 예문과 테스트 예문은 LLM이나 관리자가 새로 쓴 문장을 매칭기로 확인한 뒤에만 저장한다.
- 탁음화 조건부 규칙: 앞 토큰이 1그룹(5단) 동사의 음편형(撥音便·イ音便)이면 탁음 기능어를 청음형으로 본다(で→て, でる→てる, じゃう→ちゃう, だ→た, だら→たら. 読んでしまう는 てしまう 패턴). ないで 같은 그 밖의 で는 그대로 두어 별개 패턴이 된다. 조사·조동사는 원형을 쓰므로 SudachiPy가 ちゃ를 て로 바꾸는 정규화는 따르지 않는다(ちゃいけない와 ていけない는 다른 패턴). 패턴의 표시 이름은 lemma(仕舞う 등)와 따로 둔다.
- 중복 방지: 형태소 조건(lemma·품사·활용형, 아무거나는 \*)을 순서대로 이은 값의 해시(morpheme\_key)가 같으면 같은 패턴이다. 동시에 같은 패턴이 생기면 DB 유일성으로 하나만 남기고, 기존 패턴을 받은 쪽은 자기 용법을 버리고 기존 용법 목록으로 다시 묻는다. 이름만 다른 사실상 같은 패턴은 관리자가 Django admin에서 합친다(구간 참조 이전 포함).
- 회화체 패턴: ちゃう·てる·とく·なきゃ 등은 별도 패턴으로 두고 원형 패턴을 가리킨다(variant\_of, 1단계만). 자기 용법 없이 원형의 용법·설명을 그대로 써서 설명은 한 벌, 학습 카드는 용법당 한 장이 된다. 화면에서만 '회화체' 배지와 안내 한 줄을 붙인다. 새 용법을 발견하면 원형 아래에 만들고, 구간의 용법은 연결됐으면 원형 소속, 미연결이면 자기 소속만 허용한다. 용법 완결·패턴 승인·판별 규칙은 실제로 매칭된 패턴 기준이라, 원형이 승인됐다고 미검수 회화체 패턴까지 확정하지 않는다. 원형이 아직 없으면 회화체 패턴에 임시 pending 용법을 두고, 원형이 생기면 관리자가 연결하며 용법을 원형으로 합친다(패턴은 유지하고 용법만 병합, 기존 판정·대안·정정의 참조도 옮김). 연결·해제·용법 추가·병합도 관련 문장의 재분석 대상이며, 변경 전에 시작한 작업이 옛 소속으로 결과를 저장하지 못하게 한다.

### 단어 사전과 단어 매칭

- **JMdict 1회 적재**: JMdict 전체를 Django 관리 명령으로 한 번 적재하고 끝낸다. 원본 파일과 원본 내용은 보관하지 않고, 재적재도 하지 않는다(사전 정정이 자동 반영되지 않는 것은 감수하는 운영 한계). 판본 이름 한 줄과 적재 직후 DB 백업만 남긴다.
- **JMdict의 역할**: 문장 번역은 LLM이 문장만 보고 하며 JMdict를 근거로 쓰지 않는다. JMdict는 단어 정보 표시, 문장에서 고를 뜻(sense) 후보, 그 뜻의 일반적인 한국어 뜻을 처음 한 번 만드는 근거로만 쓴다.
- **단어 단위**: 단어 1개 = JMdict 항목 1개. 항목의 모든 표기·읽기를 함께 저장하고, 흔한 단어 표시(ichi1 등)는 후보 순서 힌트로 쓴다.
- **매칭**: 활용하지 않는 단어는 표기 + 읽기로, 활용하는 단어는 사전형 표기로 찾는다(SudachiPy 읽기는 활용형 읽기라 食べた의 食べ는 タベ). 히라가나·가타카나는 통일하고, 가나로 쓴 단어는 읽기로도 찾는다. 후보가 여럿이면 새 문장 LLM 요청에서 뜻을 고를 때 함께 고르고, 못 찾으면 정규형·표층형으로 한 번 더 찾는다.
- **제한 정보**: JMdict의 읽기→표기 제한과 뜻→표기·읽기 제한은 저장하되, LLM에 넘길 뜻 후보를 거르고 표기에 맞는 읽기를 보여주는 데만 쓴다.
- **새 단어 생성(두 단계)**: 사전에서 못 찾은 단어는 새 문장 LLM 요청에서 사전형과 읽기만 받는다. 서버가 그 값으로 다시 찾은 뒤, 단어 뜻 생성 요청에 문장과 (있으면) 기존 뜻 후보를 함께 넘긴다. 기존 단어면 그 후보 중에서 이 문장의 뜻을 고르고, 맞는 뜻이 없으면 그 항목 아래 미검수 뜻을 추가한다. 기존 단어가 없으면 같은 요청에서 뜻·태그·한국어 뜻을 만들어 사전 항목 없이 저장한다. 사전 항목 없는 단어의 동시 생성 중복은 (사전형, 읽기) 부분 고유 제약(사전 항목 번호가 없는 행만 대상)으로 막는다. 두 값은 저장 전에 정규화(가나 통일)하고 빈 값을 허용하지 않으며, 대표 표기는 처음 저장한 값으로 고정한다. 충돌하면 기존 단어를 쓰되 뜻은 따로 판단한다. 나중에 사전 항목과 같은 단어로 밝혀지면 표기만으로 자동 병합하지 않고 관리자가 검수해 병합한다(문장 분석·카드·제외 상태 참조 승계). 벡터 DB는 단어 조회에 쓰지 않는다(정확히 일치하는 조회라 일반 인덱스가 맞다).
- **뜻 단위 출처**: 뜻마다 출처(JMdict / LLM)와 뜻 자체의 검수 상태를 둔다(한국어 뜻의 출처·검수 상태와 별개). LLM이 만든 뜻은 JMdict 단어 아래에 붙어도 'AI 생성·미검수'로 표시하며, 별도 단어로 떼지 않는다(카드가 쪼개지지 않게).
- **태그 분리**: 단어 전체에 해당하는 태그(품사, 동사 그룹, い·な형용사, 고유명사, 예외 활용)와 뜻마다 다른 태그(자동사/타동사, 경어, 보통 가나로 씀 등)를 나눠 저장한다. 사이드 패널은 문장에서 고른 뜻의 태그를 보여준다(夜が明ける → 자동사, ドアを開ける → 타동사). 자타 대응 동사도 뜻 단위이며 고른 뜻에 대응 동사가 있을 때만 웹페이지에 표시한다.
- **웹 검색 제외**: MVP 분석 흐름에는 웹 검색 도구를 넣지 않는다. LLM이 만든 단어는 미검수로 표시하고 관리자 검수 때 확인한다.
- **개인 원문과 예문**: 개인 원문은 지금처럼 서버에 저장하고, 문제가 생기면 그때 저장 위치를 바꾼다. 공용 번역은 드래그했을 때만 보여주고 따로 열람할 수 없다. 예문 카드는 개인 원문 + 공용 번역(숫자 자리표시자 복원) + 출처로 만들며 LLM을 새로 부르지 않는다. 사용자 예문은 본인의 문장 기록에서 계산해 본인만 본다. 기준: 내가 드래그한 건 나만 보고, 남이 드래그한 건 나한테 보이지 않는다. 문장 기록을 지울 때 예문을 같이 지울지 카드에 복사할지는 Phase 2에서 정한다.

### 선택 범위와 문장 경계

- 선택의 시작 지점은 앞쪽으로, 끝 지점은 뒤쪽으로 넓혀 온전한 문장을 만든다. 여러 문장에 걸치면 문장별로 나눠 일괄 분석한다.
- 넓히다가 멈추는 지점은 문장 끝 부호(。！？), 블록 경계(문단 끝), 최대 글자 수다.
- 끝 부호 바로 뒤의 닫는 괄호(」』）)는 앞 문장에 포함한다.
- 인용부호(「」『』 등) 안의 마침표에서는 문장을 나누지 않는다. ？！와 줄바꿈이 섞인 대표 사례로 분리 규칙을 확정한다.
- 루비 읽기(rt, rp)는 텍스트 추출에서 제외한다. 화면에는 원래 페이지의 루비가 그대로 보인다.
- 원문은 사용자별 개인 문장으로만 보존하고 공용 테이블에는 저장하지 않는다.
- 구간 위치는 키 텍스트의 코드포인트 기준 반열린 구간 \[start, end)로 저장한다. 원문 매핑은 서버가 계산해, 응답할 때 사용자의 원문 위치(브라우저의 UTF-16 기준)로 변환한다.
- 크롬 내장 PDF 뷰어, canvas나 이미지 속 텍스트는 지원하지 않는다. PDF는 향후 웹 PDF 뷰어로 검토한다.

### 정규화 규칙

캐시 키는 아래 규칙을 순서대로 적용한 키 텍스트의 SHA-256이다. 규칙 버전을 기록하고, 규칙이 바뀌면 마이그레이션으로 해시를 다시 계산한다. 정규화 규칙이 바뀌면 같은 공용 분석을 공유하던 원문들이 다른 키로 나뉠 수 있으므로, 원문(user\_sentence.original\_text)별로 새 키를 계산하고 해당 분석이 준비되면 analysis\_id를 재연결한다. 개인 문장의 ID·중복 기준(user\_id, original\_hash)은 그대로다.

| 순서 | 규칙 | 예 |
| --- | --- | --- |
| 1 | 루비(rt, rp) 제거 | 漢字(かんじ) → 漢字 |
| 2 | 폭 통일만 적용: 전각 영숫자 → 반각, 반각 가나 → 전각. NFKC 전체는 적용하지 않는다(위첨자 같은 호환 분해 금지) | ＡＢＣ１２ → ABC12, ｶﾅ → カナ, x²는 그대로 |
| 3 | 일본어 문자 사이 공백 제거, 영어 단어 사이는 공백 1개 유지 | 私　は → 私は |
| 4 | 물결표(\~ 〜) 제거 | あれ〜 → あれ |
| 5 | 문장 전체를 감싼 바깥 괄호·따옴표만 제거 | 「行こう」 → 行こう |
| 6 | 의미를 바꾸는 기호(！？… 등)만 남기고 나머지 기호 제거 | 行こう。 → 行こう, 行こう！는 그대로 |
| 7 | 아라비아 숫자(0\~9)만 ⟨N1⟩, ⟨N2⟩로 치환. 한자 숫자는 치환하지 않는다 | 3人で → ⟨N1⟩人で, 二枚目·一人前·七夕·一石二鳥는 그대로 |

- 문장마다 두 텍스트를 만든다. 분석 텍스트(1\~6단계, 숫자 그대로)는 SudachiPy 입력, 키 텍스트(1\~7단계)는 해시·LLM 입력·번역 저장·구간 위치의 기준이다.
- LLM 번역에 자리표시자가 빠짐없이 그대로 있을 때만 공용 캐시에 저장한다. 실패해서 숫자를 넣고 분석한 결과는 공용 캐시에 넣지 않는다.

### 캐시와 승인 원칙

- 문장 분석에는 설명 텍스트가 아니라 문법 ID와 구간만 저장하고, 설명과 승인 상태는 조회할 때 확인한다.
- 문법 지식(용법 설명)은 승인 대상이고, 문장 분석(번역과 매칭)은 승인 대상이 아니다. 용법 설명은 LLM이 처음 한 번 쓰고 관리자가 검수하며, 공용으로 재사용한다.
- 번역과 매칭은 한 문장 분석으로 묶어 함께 저장한다. 번역은 재사용하되 정정 시 재번역 경로를 둔다.
- 문장 분석은 완료 / 부분 완료 상태를 가지며, 부분 완료는 미해결 구간을 기록한다.
- 공용 문장 분석은 키 텍스트 해시로만 유일하다. 개인 원문은 사용자별 원문 해시로 구분해 저장하고, 출처는 사용자별로 기록한다.
- 최신 여부는 판 번호로 판단한다. 조회할 때 문법 패턴·용법의 판 번호를 분석에 기록된 번호와 비교하고, 판 번호로 알 수 없는 사건(매칭 정정 등)에만 stale 표시를 쓴다.
- 패턴 세트 버전이 분석에 기록된 버전보다 높으면 로컬 매칭만 다시 돌린다(LLM 없음). 후보나 용법 판 번호·판별 규칙이 바뀐 구간은 전부 재검토하고, 판정은 입력이 완전히 같을 때만 재사용한다.
- 다시 만들어야 하는 분석은 옛 결과를 '재분석 중' 표시와 함께 보여주고 SSE로 갱신한다.
- 관리자 정정이 LLM 결과보다 우선한다. 활성 정정만 적용하고(suspended 제외), 이미 오답으로 알려진 결과는 재분석 중에도 그대로 노출하지 않는다.
- LLM 요청 실패나 상한 도달 구간은 '설명 준비 중'으로 표시하고, 큐로 재시도한다(횟수 상한).
- 같은 문장의 동시 요청은 조건부 갱신으로 처리 중 상태를 선점해 한 번만 실행하고, 나머지는 진행 중인 결과를 공유한다. 결과를 쓸 때 세대 번호를 비교하고, 구간 묶음은 트랜잭션으로 통째 교체한다.
- 선점에는 만료 시간을 두고, DB에 남은 미완료 작업을 큐에 다시 넣는 복구 경로를 둔다. SSE 응답은 결과 버전을 포함하고, 재접속하면 DB의 현재 결과를 다시 읽는다.
- 미검수(pending) 용법도 모든 사용자에게 'AI 생성·미검수' 배지와 함께 보여준다. 검수되지 않은 단어 뜻은 'AI 번역'으로 표시한다.
- LLM이 만든 패턴·용법은 pending(미검수)으로만 등록된다. 그림자 모드로 자동 승인 기준에 맞는 용법은 '승인했을 것'만 기록하고 pending으로 두며, 관리자 결정과의 일치율이 충분해지면(예: 95%) 실제 자동 승인을 따로 켠다.

### 핵심 수용 기준

| 상황 | 기대 결과 |
| --- | --- |
| 재사용 가능하고 stale이 아닌 문장 분석이 있는 문장 | LLM 호출 없이 번역과 설명을 표시한다 |
| `私は学`처럼 문장 일부만 드래그 | 문장 전체로 넓혀 분석하고, `私は学生です`의 저장된 분석을 재사용한다 |
| 문장 끝 。의 유무만 다른 문장 | 같은 문장으로 보고 저장된 분석을 재사용한다 |
| 앞 공백 등이 다른 원문에서 캐시 재사용 | 원문의 정확한 위치에 하이라이트한다 |
| 루비가 달린 본문을 드래그 | 읽기 텍스트가 문장에 섞이지 않는다 |
| 같은 새 문장을 여러 사용자가 동시에 요청 | LLM 요청은 한 번만 발생한다 |
| 모든 구간이 용법 완결 패턴으로 확정되는 새 문장 | 용법 판별 없이 번역, 새 구문 제안, 단어 뜻 선택만 LLM에 요청한다 |
| 후보는 하나지만 용법 완결 패턴이 아님 | 자동 확정하지 않고 LLM이 판별한다 |
| で의 용법을 확정하지 못한 새 문장 | 하나를 정답처럼 단정하지 않고 후보를 표시한 뒤, LLM 판별 결과로 채운다 |
| 모든 후보가 부적합함 | 잘못된 후보를 강제로 고르지 않는다. 그 자리에 배울 문법이 없으면 해당 없음, 후보로 설명되지 않는 문법이 있으면 미발견으로 처리한다 |
| 이름 속 の처럼 패턴은 걸렸지만 배울 문법이 없음 | 해당 없음으로 처리하고 새 문법을 찾지 않는다 |
| LLM이 등록한 새 패턴 | 원래 문장과 LLM이 새로 쓴 예문에 모두 걸릴 때만 활성화되고, 다음 문장부터 매칭에 쓰인다 |
| 미검수 용법으로 정해진 구간의 용법이 승인됨 | 구간을 고치지 않아도 다음 조회부터 배지 없이 표시된다 |
| 패턴이 반려됨 | 그 패턴은 매칭에 쓰이지 않는다. 그 패턴의 구간은 재분석 전에도 바로 보이지 않고, 문장 분석은 다음 요청 때 다시 만든다 |
| 용법이 반려됨 | 그 용법을 쓰던 문장 분석은 stale이 된다. 그 용법으로 정해진 구간은 재분석 전에도 바로 보이지 않고, 번역과 매칭은 다음 요청 때 다시 만든다 |
| 주 용법이 반려된 분석을 재분석 전에 조회 | 반려된 구간은 보이지 않고, 번역은 경고 표시와 함께 보인다 |
| LLM에게 베낀 예문을 다시 쓰게 함 | 그 호출은 사용 기록에 예문 재작성(`example_rewrite`)으로 따로 남는다 |
| 패턴은 활성인데 그 패턴의 용법 하나만 반려된 상태에서 재분석 | 반려된 용법은 DB 판정과 LLM 후보에 나오지 않는다 |
| 예문 없이 등록된 패턴(test\_cases가 빔)을 관리자가 승인하려 함 | 새로 쓴 '걸려야 함'·'걸리면 안 됨' 예문이 생기기 전에는 승인되지 않는다 |
| 관리자 정정이 가리키는 용법이나 그 패턴이 반려됨 | 그 정정은 적용되지 않고 재분석 결과가 그 구간을 채운다. 반려가 취소되면 정정이 다시 적용된다 |
| 반려된 용법의 반려가 취소됨 | 그 용법이 속한 패턴과 그 패턴을 원형으로 쓰는 회화체 패턴의 문장 분석이 stale이 되어, 다음 요청 때 되살아난 용법을 다시 검토한다 |
| 반려된 패턴의 반려가 취소됨 | 활성화 근거를 다시 검증해 통과하면 매칭에 다시 쓰인다 |
| 패턴과 용법이 둘 다 반려된 상태에서 용법만 반려 취소 | 패턴이 아직 반려 상태라 그 용법은 후보로 돌아오지 않고 카드도 일시 정지 상태로 남는다 |
| 분석 작업이 도는 중에 그 문장이 쓰던 패턴·용법이 반려됨 | 그 작업은 끝나도 결과를 저장하지 못하고, 다음 요청 때 새로 분석한다 |
| 사용 중인 용법의 승인이 pending으로 취소됨 | 그 용법이 확정 근거였던 분석은 stale이 되고, 취소 전에 시작한 작업은 결과를 저장하지 못한다 |
| 비활성이던 패턴이 활성화됨 | 패턴 세트 버전이 올라, 활성화 전에 캐시된 문장도 다음 조회 때 그 패턴으로 다시 매칭된다 |
| 예문 없이 등록돼 비활성인 패턴에 관리자가 '걸려야 함' 예문을 보완함 | 서버가 다시 검증해 통과하면 활성화된다 |
| 해석 갈림의 대안 용법이 미검수이거나 반려됨 | 미검수 대안에는 'AI 생성·미검수' 배지가 붙고, 반려된 대안은 보이지 않는다 |
| LLM이 짧은 원문 전체를 넣고 앞뒤에 말만 붙인 예문을 돌려줌 | 원문을 담은 예문으로 보고 거부한다 |
| 승인된 원형 용법을 쓰는 미검수 회화체 패턴의 구간 | 확정으로 보이지 않고 'AI 생성·미검수' 배지와 함께 표시된다 |
| LLM이 새 예문으로 원문을 그대로(또는 긴 구절을 그대로) 돌려줌 | 예문으로 저장하지 않고 다시 쓰게 한다. 그래도 베끼면 예문 없이 등록하고 활성화하지 않는다 |
| LLM이 후보에 없는 문법 ID를 반환 | 저장하지 않고 후보를 나열한다 |
| 다른 사용자가 만든 미승인 용법이 있는 문장 | 'AI 생성·미검수' 배지와 함께 표시되고, 확정 판별의 근거로 쓰이지 않는다 |
| 캐시 저장 후 신규 용법이 발견·승인됨 | 관련 미해결 구간이 다시 판정된다 |
| 사용 중인 용법의 승인이 취소됨 | 해당 문장 분석은 stale이 되고 다음 요청 때 번역과 매칭을 함께 다시 만든다 |
| 누적 판정이 오판정으로 정정됨 | 정정된 판정이 자동 확정의 근거로 남지 않는다 |
| 새 문장을 선택한 뒤 이전 요청이 완료됨 | 이전 결과가 현재 선택의 결과를 덮어쓰지 않는다 |
| 숫자만 다른 문장(3人で / 5人で) | 저장된 분석을 재사용하고 번역의 숫자만 바꿔 넣는다 |
| 한자 숫자가 든 표현(二枚目, 一人前) | 자리표시자로 바꾸지 않고 그대로 분석한다 |
| LLM 번역에서 숫자 자리표시자가 빠짐 | 그 결과를 공용 캐시에 저장하지 않는다 |
| 食べた와 食べたら | 활용형 조건으로 과거와 조건을 다른 용법으로 판정한다 |
| 인용부호 안에 마침표가 있는 문장 | 인용부호 안에서 문장을 나누지 않는다 |
| 판 번호가 뒤처진 분석 | 옛 결과를 '재분석 중'으로 보여주고 갱신 결과로 바꾼다 |
| 관리자가 오답으로 정정한 구간이 재분석 중 | 오답을 그대로 노출하지 않는다 |
| 처리 중에 작업자가 멈춤 | 선점 만료 후 다시 큐에 넣어 처리한다 |
| 명사만 있는 제목처럼 분석할 문법이 없는 새 문장 | 번역 요청에서 문법도 확인하고, 분석할 문법이 없으면 '대상 문법 없음'으로 처리한다 |
| DB에 패턴이 없는 초기 상태에서 조사·조동사가 있는 문장 | LLM이 문법을 찾아 pending 용법으로 등록하고 'AI 생성·미검수' 배지로 바로 표시한다 |
| 読んでしまった와 食べてしまった | 같은 てしまう 패턴으로 매칭된다 |
| 行かないでください | で를 て로 바꾸지 않고 ないで로 분석한다 |
| 같은 새 문법이 든 문장을 두 사용자가 동시에 처음 요청 | 패턴은 하나만 생기고, 늦은 쪽은 기존 용법 목록에서 다시 고른다 |
| 용법이 하나뿐인 미검수 패턴이 걸린, 이미 분석이 캐시된 문장 | LLM 없이 재사용하고 '미검수'로 표시한다 |
| あの人は子供のようだ처럼 문장만으로 해석이 갈림 | 번역과 같은 해석을 주 용법으로, 다른 해석을 대안으로 함께 보여준다 |
| 帰る가 든 문장 | 단어 밑에 '동사' '1그룹' '주의' 태그를 보여준다 |
| これを食べちゃいけない와 その給料じゃ食べていけない | ちゃ와 て가 다른 lemma라 금지(〜ちゃいけない)와 〜ていけない를 다른 패턴으로 매칭한다 |
| ながら의 동시 동작 용법만 있는데 知っていながら黙っていた가 새로 들어옴 | 첫 LLM 요청에서 기존 용법이 맞지 않음을 확인하고 ながら 패턴 아래 역접 pending 용법을 추가한다 |
| 手を取る와 休みを取る | 같은 取る라도 문장마다 다른 JMdict 뜻(잡다 / 내다)을 골라 보여준다 |
| 夜が明ける와 ドアを開ける | 같은 開ける(あける)라도 고른 뜻에 따라 태그가 자동사 / 타동사로 다르게 표시된다 |
| 食べた | 활용형 읽기(タベ)가 아니라 사전형 표기 食べる로 JMdict 항목을 찾는다 |
| 사전 조회에 실패한 단어 | LLM이 준 사전형·읽기로 다시 찾아 기존 항목이 있으면 재사용하고, 없을 때만 새 단어로 저장하며 중복 단어가 생기지 않는다 |

## 4. 기능 요구사항 — Phase 2 회원·학습

두 번째 단계는 사용량 집계와 계정 관리, 그리고 분석한 문법·단어·한자를 플래시카드로 복습하고 Anki로 내보내며, 직접 쓴 일본어 문장을 평가받는 개인 학습 기능이다. 복습과 작문은 모바일 웹에서도 쓸 수 있게 한다.

| ID | 요구사항 | 설명 | 우선순위 |
| --- | --- | --- | --- |
| FR-M01 | 사용량 집계 | FR-A18 계측 데이터를 바탕으로 사용자별 사용량을 집계한다. 캐시 적중, 실패, 재시도를 몇 회로 셀지 정의한다 | 필수 |
| FR-M02 | 계정 관리 | 정보 수정과 회원 탈퇴를 지원한다 | 권장 |
| FR-M03 | 학습 카드 등록 | 사이드 패널에서 문법·단어·한자를 학습 카드로 등록한다. 학습 카드는 내 일본어 중 골라 등록한 것이다. 드래그한 원문 문장과 출처를 예문으로 함께 저장한다. 문법 카드는 용법당(용법 ID 참조), 단어 카드는 단어 뜻(sense)당(고정 단어 뜻 ID 참조) 한 장이다(회화체 패턴은 원형 용법을 공유하므로 같은 카드). 활용을 위한 별도 카드는 두지 않는다. 같은 용법·단어·한자는 사용자당 카드 하나로 두고(이미 중복된 카드는 복습 기록을 보존해 합침), 다른 문장에서 다시 등록하면 예문만 추가한다 | 필수 |
| FR-M04 | 카드 유형별 구성 | 문법(용법 설명, 예문), 단어(읽기, 뜻), 한자(음독, 훈독, 뜻) 카드의 앞면·뒷면 구성을 정의한다. 문법 카드 예문에는 사용자가 만난 여러 활용 형태가 쌓인다. 단어 카드 뒷면에는 동사 그룹·예외 활용 태그와 활용표(규칙 코드로 계산)를 보여주고, 복습 문제로 활용형을 물을 수 있다(예: 読む의 て형은?). 그룹별 규칙 복습은 태그 필터(1그룹만, 예외 활용만 등)로 한다. 내용은 공유 DB를 참조해 설명 수정이 카드에도 반영된다. 용법이 반려되면 카드를 일시 정지하고 알리며 복습 기록은 유지한다. 예문의 매칭이 정정되면 그 예문을 제거한다 | 필수 |
| FR-M05 | 플래시카드 복습 | 간격 반복 알고리즘으로 복습 일정을 정하고, 사용자의 응답(다시, 어려움, 좋음, 쉬움)에 따라 다음 복습일을 갱신한다 | 필수 |
| FR-M06 | Anki 내보내기 | 카드를 Anki 덱으로 내보낸다. 지원하는 Anki 버전에서 재가져오기 시 중복 없음, 내용 갱신, 기존 복습 유지를 실제 가져오기 테스트로 확인한다 | 권장 |
| FR-M07 | 작문 평가 | 사용자가 쓴 일본어 문장을 LLM이 평가해 문법 오류, 어색한 표현, 고친 문장을 한국어 설명과 함께 제공한다. 매번 LLM을 호출하므로 사용량 집계 대상이다 | 필수 |
| FR-M08 | 작문 기록 | 작문과 평가 결과를 사용자별로 저장해 다시 볼 수 있다 | 권장 |
| FR-M09 | 모바일 웹 지원 | 복습, 카드 관리, 작문 화면을 모바일 브라우저에서 쓸 수 있도록 반응형으로 만든다 | 권장 |
| FR-M10 | 내 일본어 보기 | 웹페이지에서 사용자가 드래그한 문장에 나온 단어·한자·용법을 본인만 볼 수 있다. 단어는 문장 분석에 기록한 단어 뜻 ID 목록(sense\_ids, 단어는 뜻에서 유도), 한자는 본인 원문에서 직접 추출(사전형이 아님), 용법은 구간에서 계산하며, 단어 태그로 필터링한다(필터 구현은 나중) | 권장 |
| FR-M11 | 활용표 | 웹페이지의 단어 화면에서 동사·형용사의 활용표(ない형·ます형·て형·た형·가능형·의지형 등)와 그룹별 활용 설명을 보여준다. 규칙 코드(그룹별 규칙 + 예외 목록)로 계산하고 사이드 패널에는 표시하지 않는다. 자타 대응 동사도 이 화면에서만 "타동사: 開ける" / "자동사: 開く"처럼 관계로 보여준다(라벨은 그 단어의 자동사·타동사 태그로 정한다). 그룹별 설명문은 관리자가 검수한다 | 권장 |
| FR-M12 | 카드 자동 추가 | 설정에서 '드래그한 항목 자동으로 카드 추가'를 켜면 드래그한 문장에서 선택된 주 용법과 주 단어 뜻(sense)을 학습 카드로 자동 추가한다. 대안 해석·미확정 구간, 한자, 고유명사는 제외한다. 기본값은 꺼짐이며, 꺼져 있으면 사용자가 골라서 추가한다 | 권장 |
| FR-M13 | 카드 제외 상태 | 카드 삭제는 실제 삭제가 아니라 '제외(이미 앎)' 상태로 바꾸고, 자동 추가는 이 상태인 항목을 건너뛴다. 다시 공부하려면 사용자가 직접 다시 추가한다. 제외 상태와 복습 이력은 내 일본어 계산과 독립적으로 보관해 원문 삭제·재분석으로 초기화되지 않고, 용법·단어 병합 시 승계한다 | 권장 |

**확인할 점**: Anki로 내보낼 때 복습 기록까지 옮길지, 카드 앞면을 일본어로 할지 한국어로 할지 정해야 한다.

## 6. 비기능 요구사항

가장 중요한 비기능 요구사항은 비용이다. 처음 보는 문장은 LLM을 한 번 부르되, 문법 패턴과 판정 통계가 쌓일수록 그 호출이 가벼워져야 설계 원칙과 수익 모델이 함께 성립한다. 그래서 호출 횟수보다 새 문장당 토큰과 미발견(새 문법 찾기) 비율을 본다. 목표치는 아직 비워 두었다.

## 7. 제약사항 및 가정

**제약사항**

- 1인 개발이므로 기능 범위는 단계별로 끊어서 진행한다.
- 문법 분석의 정확도와 비용은 외부 LLM API(OpenAI)에 의존한다.
- 형태소 분석 품질은 SudachiPy 사전에 의존한다(core 사전, 분할 모드 C).
- DB는 MVP 우선으로, 지금 필요한 테이블만 만든다. 예산 관련 테이블은 핵심 기능 완성 후로 미룬다.
- 분석 방향은 일본어 → 한국어만 지원한다. 다국어와 역방향은 범위 밖이다.

**가정**

- 사용자는 히라가나와 가타카나를 읽을 수 있다.
- 사용자는 크롬 확장을 설치해 쓸 수 있고, Google 계정이 있다.
- 초기 패턴 승인은 관리자 1인이 감당할 수 있는 양이다.

## 8. 릴리스 단계와 미결 사항

DB 스키마·요구사항 마감(2026-10-18). 학습 카드 테이블은 Phase 2에서 추가한다.

&#91;embedded content: 릴리스 단계 · 3단계\]

Phase 1 분석을 먼저 완성하고, Phase 2의 사용량 집계가 Phase 3 결제 한도의 기준이 된다. 각 단계의 완료 기준은 아직 정하지 않았다.

**구현 순서** (Phase 1 안에서)

1. 문장 경계, 캐시 동일성, 구간 위치
2. 개인 원문·출처, 문법·용법·단어 식별자, 승인 상태, 분석·작업 버전
3. 패턴 매칭·용법 판별(시드 없이 LLM이 등록한 패턴으로)
4. 번역·모호성 판별과 작업 실행
5. 사이드 패널·정정·stale 갱신

첫 구현에서는 숫자 템플릿의 범위 확장, 구간별 정교한 LLM 재사용, 불연속 문법(〜ば〜ほど 등)을 미룬다.
